# Inkling (Мыслящие машины 975B MoE) colibri

`c/inkling.c` запускает [Мыслящие машины намекают](https://huggingface.co/thinkingmachines/Inkling)
(всего 975 байт / 41 байт активных, Apache 2.0) с экспертным потоковым подходом colibri:
резидентные плотные веса (RAM или VRAM), маршрутизированные эксперты, передаваемые в потоковом режиме с диска с помощью
LRU + закрепленный кеш. Аудиовход поддерживается при наличии аудиотензоров.
(см. [Аудиовход](#audio-input-dmel) ниже); видеокодер и MTP
голова не загружена.

<a id="quickstart"></a>
## Быстрый старт

Предварительно конвертированные веса (эксперты int4 + жители bf16, 514 ГБ, как указано в репозитории Hugging Face):

```sh
hf download nbeerbower/Inkling-colibri-int4 --local-dir ~/Models/inkling_i4
```

или самостоятельно преобразовать исходную контрольную точку bf16 (shard-resumable; `--watch`
преобразуется во время загрузки):

```sh
python3 c/tools/convert_inkling_int4.py --indir <bf16-checkpoint> --outdir ~/Models/inkling_i4
```

Сборка и запуск:

```sh
make -C c inkling                # pure CPU (dependency-free, like glm)
make -C c inkling CUDA=1         # + bf16 residents in VRAM (needs ~37 GB free)

SNAP=~/Models/inkling_i4 ./c/inkling -p "The capital of France is" -n 64
```

Требования: ~120 ГБ ОЗУ (сборка процессора сохраняет в ОЗУ ~86 ГБ резидентов bf16;
сборка CUDA перемещает их во VRAM и использует освобожденную оперативную память для более крупного эксперта
кэш), хранилище NVMe для моментального снимка.

<a id="if-you-have-less-ram-than-that"></a>
## Если у вас меньше оперативной памяти

Предварительно преобразованный контейнер имеет **int4 маршрутизируемых экспертов, но плотные веса bf16**, и
плотный набор является резидентным: каждый токен нуждается в нем целиком. Измерено на реальном
размер моментального снимка составляет **49,4 ГБ**, а `load_w` при загрузке расширяет bf16 до f32, поэтому
пик составляет ~99 ГБ. При объеме ОЗУ менее 64 ГБ процесс завершается до того, как сгенерируется.
что угодно.

Квантование только плотного набора до **int4-gs64** приводит к получению **15,3 ГБ**, что соответствует
Коробка на 25 ГБ. Один проход по осколкам, оригиналы нетронуты, ~14 минут:

```sh
python3 c/tools/convert_inkling_dense_int4.py --dir ~/Models/inkling_i4 --plan   # estimate first
python3 c/tools/convert_inkling_dense_int4.py --dir ~/Models/inkling_i4

mkdir -p ~/Models/inkling_i4/dense-int4g64
mv ~/Models/inkling_i4/dense-int4g64.safetensors \
   ~/Models/inkling_i4/dense-int4g64/dense.safetensors
```

Движок автоматически подхватывает контейнер (он печатает `[dense]Container
int4-gs64: …`); `INK_DENSE_Q4=0` игнорирует его и возвращается к bf16. **При достаточном объеме оперативной памяти
вам ничего из этого не нужно** — оставьте контейнер, и ничего не изменится.

Ошибка квантования, измеренная относительно реальных весов bf16:

| Тензоры | Формат | Отн. Ошибка L2 |
|---|---|---|
| внимание, общие эксперты, плотный MLP | int4-gs64 | ~11% |
| `embed_tokens`, `lm_head` | int8 для каждой строки | ~0,9% |
| нормы, предубеждения, роутер, conf1d | нетронутый | 0 |

11% — это то, чего стоят 4 бита при таком распределении весов (шум квантования ≈ 0,135σ для
16 уровней выше ±amax в группах по 64) — не дефект преобразования. Этого достаточно
для согласованного вывода: 975B правильно отвечает на хосте 25 ГБ. `embed`/`lm_head` являются
сохраняется в int8, потому что они вводят *каждый* токен. `ATTN_BITS=8` переводит внимание на int8
тоже (ошибка 11% → 1,1%, +4 ГБ), если вы предпочитаете тратить оперативную память.

**Скорость, честно говоря:** после плотного набора для экспертного кэша осталось всего ~8 ГБ,
резидентность составляет ~1,7% от экспертного банка объемом 464 ГБ, поэтому декодирование привязано к диску — десятки
секунд на каждый токен на одном NVMe, а не в интерактивном режиме. Именно этот путь делает модель
*работает и тестируется* на небольшом хосте, не быстро. Закрепление (`PIN`) и больший кеш
помогите пропорционально оперативной памяти, которую вы можете им предоставить.

<a id="audio-input-dmel"></a>
## Аудиовход (DMel)

Inkling слышит через дискретизированные логарифмические кадры («DMel»): 80 мел-диапазонов на
Звук длительностью 50 мс, каждый из которых квантован до 16 уровней. Его звуковая «башня» одна
таблица встраивания плюс одна норма — встраивание кадра — это RMSNorm суммы
из 80 строк таблицы, замененных местами в позиции `<|audio|>` этого фрейма. Нет
Кодер в стиле шепота, без дополнительного времени работы: при наличии двух аудиотензоров
движок воспринимает голосовой ввод с полной точностью, и без них это
тот же текстовый движок, что и раньше.

Два способа получить тензоры:

- **Преобразование себя**: добавьте `--keep-audio` к `convert_inkling_int4.py`.
  Он проходит через `model.audio.*` (~10 МБ bf16 на Inkling-Small).
- **У вас уже есть текстовый контейнер?** Два тензора можно вытащить.
  шардов исходной контрольной точки с HTTP-запросами диапазона — ~10 МБ
  перемещен вместо повторной загрузки полной контрольной точки bf16 — и записан как
  коляска `audio.safetensors` рядом со снимком. Индексы движка
  каждый `*.safetensors` в каталоге, поэтому его просто подхватывают:

```python
import json, struct, urllib.request

REPO = "https://huggingface.co/thinkingmachines/Inkling-Small/resolve/main"
NAMES = ["model.audio.encoder.weight", "model.audio.final_norm.weight"]

def rng(url, a, b):
    req = urllib.request.Request(url, headers={"Range": f"bytes={a}-{b}"})
    return urllib.request.urlopen(req).read()

index = json.loads(urllib.request.urlopen(f"{REPO}/model.safetensors.index.json").read())
header, blobs, off = {}, [], 0
for name in NAMES:
    url = f"{REPO}/{index['weight_map'][name]}"
    n = struct.unpack("<Q", rng(url, 0, 7))[0]
    info = json.loads(rng(url, 8, 7 + n))[name]
    a, b = info["data_offsets"]
    raw = rng(url, 8 + n + a, 8 + n + b - 1)
    header[name] = {"dtype": info["dtype"], "shape": info["shape"],
                    "data_offsets": [off, off + len(raw)]}
    blobs.append(raw)
    off += len(raw)
hdr = json.dumps(header).encode()
with open("audio.safetensors", "wb") as f:
    f.write(struct.pack("<Q", len(hdr)) + hdr + b"".join(blobs))
```

Входной формат: моно 16 кГц. Через шлюз отправьте WAV (PCM16 или
float32) как часть содержимого OpenAI `input_audio` — шлюз вычисляет
DMel создает сам себя (numpy необходим только для этого пути). Через CLI пройдите
предварительно закодированные кадры как необработанные байты с `--audio`. Обратите внимание, что звук увеличивает
подсказка: ~5 секунд речи — это ~100 позиций, поэтому скорость предварительного заполнения учитывается вдвое
разговорные обороты.

```sh
curl localhost:8000/v1/chat/completions -d '{
  "model": "inkling-colibri",
  "messages": [{"role": "user", "content": [
    {"type": "input_audio", "input_audio": {"data": "<base64 wav>", "format": "wav"}}
  ]}]
}'
```

<a id="expert-cache-size"></a>
## Размер экспертного кэша

`cap` (первый позиционный аргумент или от `--cap` до `coli`) — сколько экспертов каждый
слой хранится в оперативной памяти. Каждый слот на 975B занимает ~28 МБ, поэтому необходимо `cap × n_layers × 28 MB`.
помещается рядом с резидентным плотным набором — с плотным контейнером int4 на хосте размером 25 ГБ, который
означает `cap` около 2.

Маленькие значения **правильны**, но медленны: движок обрабатывает перенаправленных экспертов в раундах.
`cap` и накапливается, поэтому эксперт, вытеснивший средний токен, перечитывается, а не молча
заменен на неправильный. (Раньше его заменяли молча: приобретя все `S×topk`
слоты вперед означали полное вытеснение кэша слотов, которые уже были распределены для
текущий токен, и модель рассчитывается с учетом того, что в них попало. Предварительное заполнение 18
для токенов на уровне `topk=6` требуется до 108 отдельных экспертов на уровень, поэтому все, что ниже этого уровня
выдал бессвязный вывод без сообщения об ошибке.)

<a id="cache-warming-same-idea-as-glms-coli_usage"></a>
## Нагрев кэша (та же идея, что и у glm `.coli_usage`)

Выбор экспертов подсчитывается по `(layer, expert)` и записывается в
`SNAP/.coli_usage` после каждого запуска поколения. При запуске вверху `PIN_N`
эксперты на каждом уровне закреплены (не вытесняются, загружаются одним параллельным пакетом).
Подсчеты **накапливаются в ходе каждого прогона**, поэтому рейтинг приближается к вашему реальному результату.
рабочая нагрузка — выводы, обученные на одной подсказке, плохо подходят (см. тест
таблицу), поэтому важна разнообразная разминка:

```sh
SNAP=~/Models/inkling_i4 ./c/inkling -f warmup_prompts.txt -n 32
```

| Окружение | Эффект |
|---|---|
| `PIN=off` | полностью отключить потепление: без раздачи, без закреплений, без перезаписи истории |
| `PIN=<path>` | альтернативный файл истории |
| `PIN_N=<n>` | пинов на слой (по умолчанию `cap/2`; 0 = только исходный рейтинг) |
| `USAGE_SAVE=0` | не переписывайте историю (тестирование) || `NOGPU=1` / `GPU_DEV=<n>` | отключить CUDA/выбрать устройство |
| `IDOT=0` | скалярные целочисленные ядра с точностью до байта (отладка) |
| `INK_SHARED_BATCH=0` | отключить пакетное заполнение с общим экспертом для контролируемых A/B; положительные значения ограничивают количество строк на фрагмент. По умолчанию используется до 64 МБ ограниченного нуля и никогда не меняется декодирование (`S=1`) |
| `TOPP=<p>` | адаптивная маршрутизация: держите обращенных в бегство экспертов до совокупного веса `p`, опускайте хвост. **Урезает маршрутизацию** — меньше экспертов читает каждый токен (рычаг, который имеет значение на хосте с привязкой к диску), но вычисления отличаются от заявленного top-k. По умолчанию выключено; результат прогона составляет `[topp] … N/M routed used (X% trimmed)`, поэтому сделка измерима. Та же семантика, что и `TOPP` в `colibri.c` и `K3_TOPP` в `kimi_k3.c` |
| Первый позиционный аргумент | ограничение экспертного кэша на слой (`0` = автоматический размер из свободной оперативной памяти) |

<a id="vulkan-the-routed-experts-on-the-gpu"></a>
## Vulkan: разгромленные эксперты по графическому процессору

`make -C c inkling VK=1`, затем `COLI_VULKAN=1`: перенаправленные эксперты переходят в общий
Уровень эксперта Vulkan ([vulkan.md](vulkan.md#inkling-and-olmoe)), кэш экспертов по
устройство которое заполняется при запуске из истории прогрев кэша выше держит
(`SNAP/.coli_usage` или `PIN=<path>`; оракул `ref.json` ничего не читает) и адаптируется
пока вы болтаете. Каждый уровень Министерства образования отправляет пары резидентных экспертов (токен, ранг) в
устройство как один пакет, в то время как CPU вычисляет остальные и общие эксперты, а затем добавляет
каждый ранг в порядке маршрутизации, поэтому порядок суммы не зависит от того, что было резидентным.

- Эксперты перебираются по мере их хранения в кеше, ничего не переквантуется: int4
  контейнер (упакованные полубайты, одна шкала в строке), контейнер int8, среда выполнения
  квантование (`bits` от 2 до 8) и f32 (`bits=0`). Слитый тензор `gate_up`
  читайте как две матрицы: ворота из строки 0 и вверх из строки I.
- Плотные матрицы (внимание, плотный MLP, общие эксперты, lm_head) переходят в
  устройство в форме оперативной памяти, int8 контейнера `dense-int4g64/` и int4-g64
  включен, за исключением графического процессора, который совместно использует оперативную память CPU, когда уровень включен: там
  они остаются в CPU, если только `COLI_VK_DENSE=1`.
- При включенном бэкэнде CUDA (`CUDA=1` и устройстве) или Metal уровень Vulkan остается.
  выключено: побеждает другой сервер.
- Одна строка за проход и ход подачи, прогон уровня [VK]: устройство N из M маршрутизировано
  эксперты...`; На карте экспертов панели мониторинга резидентный эксперт устройства отображается как уровень 2.
  Ручки — `COLI_VK_TIER*` в [ENVIRONMENT.md](ENVIRONMENT.md#vulkan-any-gpu-with-a-vulkan-12-driver).

Статус: правильный, скорость еще не измерялась. CI проверяет крошечный прибор на Lavapipe.
каждый экспертный формат выше, при выселении, с теплым стартом и сквозной подачей, и
снова под ASan и UBSan; 975B на нем не работал.

<a id="performance-975b-ryzen-9-7900-24t-187-gb-ddr5-rtx-a6000-nvme"></a>
## Производительность (975B, Ryzen 9 7900/24t, 187 ГБ DDR5, RTX A6000, NVMe)

Жадное декодирование с 24 токенами, промпт с 5 токенами, прогоны с тегами фиксации, по одному прогону каждый.
«Обученный» = история использования создается по тому же запросу; «роман» = никогда не встречавшаяся подсказка.

| Конфигурация | Предварительное заполнение | Декодировать | Попадание в кэш |
|---|---|---|---|
| Этап A (обычный LRU, последовательный ввод-вывод, CPU) | 150,2 с | 0,06 tok/s | ~0% |
| + кэш упакованного-int4, параллельное заполнение, выводы (CPU) | 21,1 с | 0,25 tok/s | 81,5% |
| + Резидентный уровень CUDA (A6000) | 18,4 с | 0,32 tok/s | 83,6% |
| + глубокие булавки, обученная подсказка (`PIN_N=64`) | 1,9 с | 2.51 tok/s | 100,0% |
| глубокие булавки, новая подсказка (булавки с насадкой) | 33,8 с | 0,17 tok/s | 79,8% |
| **стационарное состояние: разнообразная история с 11 подсказками, булавки по умолчанию, новая подсказка** ¹ | **35,4 с** | **0,25 tok/s** | **82,2%** |¹ Генерация 48 токенов, промпт на 13 токенов. Имея лишь небольшой разминочный корпус,
рейтинг едва опережает простой LRU; частота попаданий (и, следовательно, скорость декодирования)
растет в сторону числа обученных подсказок по мере накопления истории реального использования.

Фазовый профиль при высоких показателях попадания: ~90% экспертов по CPU — следующий рычаг
экспертные вычисления на графическом процессоре, а не дополнительная работа ввода-вывода.

<a id="validation"></a>
## Проверка

Каждый режим точен по отношению к ВЧ-трансформаторам на крошечном оракуле со случайной инициализацией.
(`c/tools/make_tiny_inkling.py`): f32, int4-контейнер (VNNI и `IDOT=0`
скаляр), резиденты bf16 на CPU и резиденты bf16 через ядро CUDA.
Токенизатор (семейство o200k, автоматически определяется `tok.h`) кодирует тест 357/357.
струны идентичны ВЧ `tokenizers`. Преобразователь совершает обход изготовленного
GGUF TML-макета возвращается через движок ровно (`--selftest-e2e`).
