<a id="gguf-models"></a>
# модели GGUF

colibri запускает файлы GGUF, которые уже есть на диске. Блоки ggml вычисляются по мере их хранения в файле, от IQ1_S до Q8_0 и MXFP4: ничего не преобразуется и не квантовается во второй раз.

```bash
./coli import ~/models/GLM-5.3-UD-IQ1_S-00001-of-00006.gguf   # first part of a split model
./coli chat --model ~/models/GLM-5.3-UD-IQ1_S.colibri         # or coli serve / coli web
```

`coli import` записывает каталог модели рядом с GGUF, названный в его честь, или там, где говорит `--out`. В каталоге содержится `config.json`, токенизатор, шаблон чата и `gguf.json`, указывающий на файл. Далее `coli chat`, `coli serve`, `coli web`, `coli plan` и `coli doctor` относятся к ней как к любой другой модели.

<a id="two-modes"></a>
## Два режима

- **`--mode link`** (по умолчанию): движок считывает GGUF там, где он находится. Ничего не копируется.
- **`--mode copy`**: также записывает `model.colibri.gguf`, при этом каждый плотный тензорный байт за байтом и маршрутизируемые эксперты каждого уровня перераспределяют один эксперт на слот, выровненный по 4 КиБ (ворота, смежные вверх и вниз), так что эксперт представляет собой одно выровненное чтение. Он работает для любой архитектуры с перенаправленными экспертами, кроме `qwen4exp`, чей движок читает только на месте.

Оба без потерь: одни и те же блоки, одни и те же токены.

<a id="what-the-engines-do-with-the-blocks"></a>
## Что движки делают с блоками

- **CPU чередует строки по 16.** Матрицы, тип которых имеет вид (Q4_K, Q5_K, Q6_K, Q3_K, IQ4_XS, Q8_0, Q4_0, IQ4_NL), хранятся с чередованием строк по 16, что ускоряет запросы и спекулятивную проверку. Эксперты упаковываются при чтении, плотные матрицы один раз при загрузке. Переключатель каждого механизма сохраняет строки файла, как это делает `GQ_EXACT=1`:

  | Движок | Переключатель |
  |---|---|
  | qwen36 | `Q36_ILV16=0` |
  | qwen38 | `Q38_ILV16=0` |
  | deepseek_v4 | `COLI_V4_ROWS16=0` |
  | deepseek_v41 | `V41_ILV16=0` |
  | подозрение | `INK_ILV16=0` |
  | глм53 | `G53_ILV16=0` |
  | colibri | `GLM_ILV16=0` |
  | олмо | `OLM_ILV16=0` (плотные матрицы; эксперты сохраняют строки файла) |

- **Уровень экспертов Vulkan** (`COLI_VULKAN=1`) включает экспертов GGUF в том виде, в котором они есть в файле. Каждый слой сохраняет свои типы, поскольку опубликованные файлы смешивают их. Слои типов, которые имеет большинство слоев, сохраняют своих экспертов на устройстве и в пуле хостов своего размера, и только несколько других слоев занимают место самого большого из них ([vulkan.md](vulkan.md#the-routed-expert-tier-vk_tierc): на 25–31 % больше экспертов, GLM-5.3 Flash UD-IQ2_XXS с 2,50–3,14 до 2,92–3,40 tok/s декодирования, Inkling-Small с 7.87-8.11 по 10.92-11.53).- **Эксперты MXFP4** (DeepSeek V4 и V4.1, MiMo) представляют собой FP4 своих контрольных точек, поэтому они работают на собственных ядрах и формах устройств этих движков.
- **Другие типы MiMo.** MiMo GGUF K-квантов или типов IQ (MiMo-V2.6-Flash Q2_K_S от ggml-org, 106 ГБ) хранит свои блоки: магистраль в целочисленных ядрах CPU и в форматах блоков цепочки Vulkan, каждый эксперт накладывает свои типы на CPU и на уровень Vulkan. На RTX PRO 4000 с 62 ГБ ОЗУ: 7,8 tok/s декодирования и 8,2 запроса, жадный текст процессора. Раньше движок отказывался от всех типов, кроме экспертов MXFP4 и багажника BF16.
- **Специалисты OLMoE сохраняют строки файла**: они умещаются в оперативной памяти, а чередование одной по ее чтению обходится дороже, чем 16-строчные ядра отдают свои матрицы. Файлы `olmoe` llama.cpp не содержат `norm_topk_prob`; импорт пишет false, поскольку это есть в официальных контрольных точках и как их вычисляет llama.cpp.
- **Таблицы энграмм DeepSeek V4.1** считываются построчно, начиная с контрольной точки: файл `deepseek41` содержит значения e4m3 каждой строки и их масштабы вместе. Опубликованные файлы K-quant и IQ хранят каждую таблицу в одном тензоре типа ggml (`per_layer_token_embd`, IQ4_NL), читаемом одинаково, строке из 256 значений в 144 байтах. Они несут конфигурацию в виде ключей, а не `config.json` контрольной точки: импортер записывает ее из них, а вспомогательный код энграммы (`dsv41_engram.json`) из ключей `ple`, чьи простые числа, хеш-множители и смещения являются теми, которые `tools/prepare_dsv41.py` получают из контрольной точки. Их `engram_gate` — это умноженные на два нормальных веса инграммы, и это все, что считывают из них ворота.
- **Голова DSpark DeepSeek V4.1** поставляется как отдельный GGUF (архи `dflash`, `dspark-*.gguf`: три этапа под именами слоев V4.1, эксперты MXFP4, проекции Q8_0 или BF16, а также `fc` головы, нормы, достоверность и тензоры Маркова). `--mtp dspark-....gguf` связывает его: импортер сверяет его с ключами `dspark` модели и называет его `gguf.json`, движок считывает его этапы как `mtp.<s>.*`, его эксперты MXFP4 — как FP4 контрольной точки в собственных слотах, а планировщик оценивает их как контрольную точку. Головка рядом с моделью названа только по имени, потому что ее черновики измерялись медленнее: UD-IQ1_S с головкой Q8_0 на RTX PRO 4000 (24 ГБ) с 62 ГБ ОЗУ, цепочка Vulkan, подсказка на 163 токена и 128 токенов, принимала 22–33% своих черновиков, а декодирование происходило с 5.01–5.29. tok/s без головки до 4,29-4,64 с ней (1,72-1,89 с `V41_DSPARK_MINACC=0`). Голова обучалась на полной модели, а 1-битная с ней меньше согласна; строки проверки также привлекают больше экспертов, которые ОЗУ не может вместить. Жадный текст — это одни и те же байты с ним и без него.
- **Kimi K3** (`kimi-k3`). Импортер записывает конфигурацию контрольной точки из ключей: слой, у которого `head_count_kv` равен 0, является слоем KDA, остальные — MLA. Движок принимает тензоры файла в качестве их аналогов контрольных точек:
  - `attn_res_score`, `ffn_res_score` и `output_res_score` — это норма AttnRes и уже умноженная проекция, и это все, что движок считывает из них.
  - `ssm_a` содержит -exp(A_log): скорость затухания движка A = exp(A_log) является отрицательной.
  - `attn_k_b` (транспонированные) и `attn_v_b` MLA возвращаются в `kv_b_proj`.
  - Маршрутизируемые эксперты находятся в скрытых проекциях (`ffn_routed_down` и `ffn_routed_up` — это скрытые проекции) и хранят блоки файла в CPU и на уровне Vulkan. `lm_head` GGUF остается на хосте.- работает UD-IQ1_S от unsloth (594 ГБ: F32, Q6_K, Q8_0, IQ2_XXS и IQ1_S). На RTX PRO 4000 (24 ГБ) с 62 ГБ ОЗУ, подсказкой на 181 токен и 128 токенами: CPU 0,4–0,5 tok/s подсказки и 0,18–0,22 декодирования, Vulkan 1.0 и 0,28. Цепочка содержит 45 из 93 слоев (21,3 ГиБ) и 106 экспертов уровня на карте и 2839 в пуле хостов; большинство экспертов по-прежнему исходят из диска. UD-TQ1_0 и UD-Q1_0 используют ggml типов 65 и 66, который colibri не знает: `coli import` отказывает им («неподдерживаемый ggml типа 65»).
  - Шарды экспертов читаются без упреждающего чтения ядра (`POSIX_FADV_RANDOM`), три среза на эксперта. С его помощью на двух-NVMe md-массиве, опережающее чтение которого составляет 2 МБ, декодировать чтение 17,3 ГБ токена для 6,7 ГБ экспертов. Без него чтение составляет 5,8 ГБ, а 96-токенный ответ на Vulkanе декодируется на 0,349tok/s против 0,269, его 31-токенный подсказ за 46,5 с против 54-57 с.
- **Эксперты GGUF читают без упреждающего чтения ядра.** Эксперты слоя располагаются в трех тензорах, поэтому эксперт представляет собой три среза, считываемые по отдельности через кэш страниц, а упреждающее чтение считывается после каждого из них. Файлы, которые их содержат, занимают `POSIX_FADV_RANDOM` на каждом диске, а также зеркала (`st_no_readahead` в `c/st.h`): colibri (GLM-5.2), glm53, mimo и kimi_k3. У движков, которые читают своих экспертов с `O_DIRECT` (deepseek_v4, deepseek_v41), его никогда не было. GLM-5.2 UD-IQ1_S (202 ГБ) на Vulkan, RTX PRO 4000 с 62 ГБ ОЗУ и двух-NVMe md массивом с упреждающим чтением 2 МБ, ответ на 96 токенов, два прогона без упреждающего чтения и три с ним, чередуются: 2,3-3,6 ГБ читают декодированный токен против 4,7-6,6 с таким же количеством загруженных экспертов, 0,633-0,658tok/s против 0,567-0,602, и 41 Гб чтения подсказки против 64-67.
- **MLA GLM**: `k_b` / `v_b` (llama.cpp разделяется на `kv_b_proj`) остаются блоки файла в CPU; цепочка Vulkan (glm53 и colibri) принимает их как числа с плавающей запятой, поскольку ядро ​​MLA считывает их поголовно.
- **Плотная цепочка Vulkan** (qwen36, qwen38, glm53, colibri, deepseek_v4, deepseek_v41, olmoe, inkling, mimo и kimi_k3) принимает плотные матрицы GGUF, поскольку они тоже есть в файле. Q8_0, Q4_K, Q5_K, Q6_K, IQ2_XXS, IQ2_S, IQ3_S, IQ4_NL и IQ4_XS работают на GEMV с одним декодером каждого типа (`shaders/chain_gemv_bd.comp`), а остальные типы — на общем блочном декодере. Сгруппированная проекция вывода V4.1 (`wo_a`) не считывает блоки, поэтому она увеличивается как int8 из Q8_0 и как float из других типов. Перенаправленные эксперты выполняются внутри одного и того же кадра, когда уровень содержит каждого эксперта слоя. Здесь выполняется этап декодирования или проверка до 16 строк; более длинные фрагменты промпта проходят через CPU и экспертный уровень.
- **Бэкэнд CUDA также принимает блоки GGUF** (`cuda_bd.cuh`): каждый тип блока ggml с весом 32 или более, каждая строка в файле. Шаг декодирования и спекулятивная проверка (до 8 строк с разделением каждой весовой нагрузки, каждая строка с битами шага декодирования) выполняются в целочисленной форме CPU на Q8_0, от Q2_K до Q6_K, IQ1_S, IQ1_M, IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S, IQ4_NL, IQ4_XS и Q2_0 (коды CPU, шкалы и целочисленные суммы: они отличаются только порядком сумм с плавающей запятой), остальные типы — с плавающей запятой. Быстрый фрагмент проходит через тайлы тензорного ядра f16 (`COLI_CUDA_BD_TILES`).- **Матрицы F16 и BF16 представляют собой блочные форматы на обоих устройствах** (fmt 101 и 130: блоки по 32 значения, 64 байта, без масштаба; `blockdec_host.h`), поэтому они принимают те же GEMV и мозаичные GEMM, что и квантованные типы: GEMV для каждого типа цепочки Vulkan и ее 64 и 128 плиток в модулях матрицы, CUDA float GEMV и тайлы тензорного ядра f16 (`hcm_dense_k`; здесь BF16 преобразован в f16, сохраняется до +-65504). qwen36 сохраняет такую ​​матрицу в f32 для CPU и возвращает устройствам обратно 16 бит файла (точно). Раньше Vulkan читал их как строки f32 вне мозаичных GEMM, а CUDA сохраняла их в CPU. Qwen3-0.6B (GGUF F16 и BF16 от ggml-org) на RTX PRO 4000, промпт на 470 токенов и 128 декодированных токенов: CUDA 137 -> 15 921 tok/s промпта и 17,6 -> 221 декодирования (F16), 139 -> 15 578 и 17,7 -> 221 (BF16); Vulkan 925 -> 11601 и 37,2 -> 204 (F16), 977 -> 11654 и 37,8 -> 205 (BF16). Жадный текст — это процессоры на каждом сервере.
- **цепочка CUDA qwen36 запускает на карте весь GGUF**: ее эксперты на уровне CUDA, как они есть в файле (типы ворота/вверх и вниз по слою, одна арена на устройство: `QT_GGUF_ARENA`), вычисляемые в кадре цепочки (без цепочки, через экспертные группы уровня, промахи на CPU), а также ее плотные матрицы, lm_head и проекции DeltaNet в качестве их блоков. Qwen3.6-35B-A3B на RTX PRO 4000 (24 ГБ), на карте каждый эксперт:

  | | Цепочка CUDA | Цепь Vulkan |
  |---|---|---|
  | UD-IQ2_XXS: декодирование, предварительное заполнение 467 токенов | 118 tok/s, 1356 tok/s | 100 tok/s, 1600 tok/s |
  | UD-IQ2_XXS: правка кода на 400 токенов (быстрый поиск) | 2,38 с | 3,3 с |
  | UD-Q4_K_M: декодирование, предварительное заполнение | 96 tok/s, 1388 tok/s | 75 tok/s, 1450 tok/s |
  | UD-Q4_K_M: редактирование кода | 2,67 с | 3,1-3,7 с |

  Жадный текст — это процессоры (те же целые числа). Раньше при запуске GGUF с помощью CUDA вычислялся каждый перенаправленный эксперт на CPU (UD-IQ2_XXS: 13,7 tok/s декодирования).
- **цепочка CUDA qwen38 также запускает GGUF**: магистральный канал и эксперты на уровне CUDA в том виде, в каком они есть в файле (теплые из истории), эксперты, которые карта оставляет в хост-пуле оперативной памяти со страничной блокировкой, которую карта считывает по шине (`COLI_CUDA_CHAIN_POOL`: сначала на карте выполняется этап декодирования, слой фрагмента запроса копируется через DMA, в то время как слои перед ним выполняются), маршрутизируется и вычисляется в цепочке кадр без шага хоста. Qwen3.8-Flash-Next IQ2_XS (68 ГБ) на RTX PRO 4000 (24 ГБ): подсказка 209-213 tok/s, декодирование 49,6-50,8 (ранее: 19-21 и 11,6; цепочка Vulkan 194-197 и 44-51). Жадный текст — это процессоры и цепочка Vulkan. Запуск такого GGUF с помощью CUDA остается на CUDA в сборке с обоими бэкэндами.- **colibri (GLM-5.2, Mistral-Large-4) также запускает GGUF на CUDA**: маршрутизируемые эксперты на общем уровне через серверную часть CUDA, как они есть в файле, резидентные плотные матрицы на карте, насколько хватает половины ее свободной памяти (устанавливает ее `COLI_CUDA_DENSE_GB`), внимание на CPU. Mistral-Large-4 UD-IQ1_S на RTX PRO 4000: 888 экспертов на карте, где уровень Vulkan рядом с плотной цепочкой содержит 156, промпт на 240 токенов за 66–82 с, а затем 1,34–1,36 tok/s декодирования по сравнению с 36,5–36,9 у цепочки Vulkan. s и 1.16-1.17 (чередуются, одна и та же сборка): более быстрое декодирование, более медленная подсказка, плотную часть которой (17 ГиБ, последняя половина карты) считывает CPU. Сборка без Vulkan (`make CUDA=1`) идет по тому же пути.
- **Плотные матрицы других движков остаются в CPU** в CUDA, а их уровни CUDA пока не принимают типы блоков ggml.
- **Путь CUDA этих движков GGUF не запускается на Vulkan на карте NVIDIA** (qwen38 для файла, экспертный тип которого отсутствует в кадре цепочки CUDA, colibri для GLM-5.2 и Mistral-Large-4, чья цепочка Vulkan привлекает внимание и поэтому читает промпт быстрее, чем его путь CUDA (`COLI_VULKAN=0` запускает его там, см. выше), deepseek_v4, чей уровень CUDA отражает только собственные эксперты FP4, и qwen36 для файла, типы экспертов которого отсутствуют в кадре цепочки CUDA). Запуск CUDA такого GGUF вычислил каждого перенаправленного эксперта на CPU (Qwen3.8 IQ2_S/Q2_0 на RTX PRO 4000: 28 tok/s запроса, 9 декодирования). Сборка с обоими бэкендами переключает такой запуск на Vulkan на той же карте, когда CUDA запрошена и `COLI_VULKAN` не установлено (114-118 и 46-49 tok/s); `COLI_VULKAN=0` поддерживает CUDA. `coli setup` также собирает механизм CUDA этих движков с помощью Vulkan, где есть набор инструментов Vulkan (в Linux; пакет Windows CUDA имеет и то, и другое).

## Файлы Олламы

Большие двоичные объекты, которые Ollama извлекает для Qwen3.5/Qwen3.6 (`qwen3.6:35b`: 23,9 ГБ, Q4_K_M, под `/usr/share/ollama/.ollama/models/blobs/sha256-...` в Linux), поступают из собственного конвертера Ollama, а не из llama.cpp, и отличаются в трёх местах: `coli import` и движок qwen36 знает: `attention.head_count_kv` — это массив. на уровень (0 на уровнях DeltaNet), максимум которого соответствует конфигурации; смещение dt DeltaNet составляет `blk.N.ssm_dt` (`ssm_dt.bias` llama.cpp, те же значения); а голова MTP (`mtp.*`) и обзорная башня (`v.*`, `mm.*`) находятся в файле модели, который движок оставляет непрочитанным. `ssm.v_head_reordered` и `rope.mrope_interleaved` не меняют компоновку. Символическая ссылка с суффиксом `.gguf` на большом двоичном объекте служит файлом импорта:

```bash
ln -s /usr/share/ollama/.ollama/models/blobs/sha256-<digest> ~/models/qwen3.6-35b-ollama.gguf
./coli import --out ~/models/qwen3.6-35b-ollama ~/models/qwen3.6-35b-ollama.gguf
```

Qwen3.6-35B-A3B из этого блоба на RTX 3070 (8 ГБ) с цепочкой CUDA, 2619 экспертов на карте: 73-78 tok/s декодирования, где Ollama 0.40.3 декодирует тот же файл в 38 на той же карте.

## Проверка GGUF перед его загрузкой

`tools/gguf_header.py` извлекает только заголовок модели на Hugging Face Hub (несколько МБ). С помощью `GGUF_CHECK=1` импортер записывает каталог модели только из этого заголовка, поэтому вы видите конфигурацию, которую он получит. Движки qwen36, deepseek_v4 и deepseek_v41 затем проверяют папку на предмет каждого загружаемого тензора, не читая ни одного:

```bash
python3 tools/gguf_header.py unsloth/Qwen3.6-35B-A3B-GGUF Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf /tmp/hdr
GGUF_CHECK=1 python3 tools/gguf_import.py /tmp/hdr/Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf /tmp/hdr/imp
GGUF_CHECK=1 SNAP=/tmp/hdr/imp ./qwen36
```
