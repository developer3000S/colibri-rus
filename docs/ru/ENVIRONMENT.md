**Существует десять двоичных файлов движка, и у них нет общего набора ручек.** Основной
движок `c/colibri` (построенный на основе `c/colibri.c`, ранее `glm.c`) читает большую часть
что следует дальше, но родственные движки читают свое:

| Движок | Источник | Собственные переменные |

## Веса с диска вместо оперативной памяти

Каждый движок передает перенаправленные эксперты с диска и сохраняет их в кэше.
ОЗУ. Некоторые могут также оставлять веса на диске вместо того, чтобы копировать их, что является
рычаг, когда модель не подходит даже при самом маленьком экспертном кэше (#1764).
Что может каждый движок:

| Движок | Плотные гири | Разгромленные эксперты |
|---|---|---|
| `colibri` (GLM-5.2) | `TRUNK_RESIDENT_LAYERS=0`: внимание, плотный MLP и общий эксперт каждого слоя, отображенного с диска. только процессор; Linux, macOS, FreeBSD. | `COLI_MMAP=1`: отображается кэш страниц. Linux, macOS, FreeBSD. |
| `kimi_k3` | `K3_MMAP=1`: отображены все подготовленные матрицы, включая головку LM. В любом случае вложение считывается по одной строке на токен. Только процессор. | Кэш хотя бы одного слота на слой (`K3_EXPERT_GB`). |
| `deepseek_v4` | Автоматически: когда плотный ствол или голова BF16 не помещается в `RAM_GB`, они считываются с диска снова при каждом использовании. Строка `ram_tiers` в stderr говорит `dense=streamed`. | Кэш как минимум k верхних слотов на уровне. |
| `glm53` | Резидентный (`GLM53_BITS` выбирает 4, 8 или 32 бита). | `COLI_MAP_EXPERTS=1`: просмотр сопоставления каждого сегмента, работает только CPU. |
| `qwen38` | Резидент (`Q38_TRUNK_CPU_INT8` сохраняет его как int8). | `COLI_MAP_EXPERTS=1`, собственные эксперты FP8 или записи коляски int4-g64. |
| `qwen36` | Резидент. При использовании канала int8 по умолчанию внедрение не копируется: каждая строка токена считывается из контрольной точки при использовании (`COLI_EMBED_MMAP`; не с `COLI_VULKAN=1`). | Кэш хотя бы одного слота на слой. |
| `inkling`, `deepseek_v41`, `olmoe` | Резидент. | Кэш хотя бы одного слота на слой. |

Сопоставленный вес требует чтения диска всякий раз, когда операционная система его вытесняет, поэтому вв худшем случае каждый токен считывает каждый сопоставленный байт: так работает модель
все дело не в том, как быстро он работает. Сопоставленные байты также не считаются резидентными, и
движок передает освобожденную ими оперативную память в экспертный кеш; чтобы снизить общую сумму, понизить
`RAM_GB` (`coli --ram`) или `CAP` тоже. Для GLM-5.2 на машине где даже нет
в багажник помещается: `TRUNK_RESIDENT_LAYERS=0 COLI_MMAP=1 RAM_GB=2`.

<a id="the-coli_ssd-probe-cache"></a>
## Кэш зонда `.coli_ssd`

В Metal + macOS при первом запуске движка объем модели измеряется с помощью
честный тест произвольного чтения F_NOCACHE (#379) и кэширует результат в
`<model>/.coli_ssd`, поэтому при каждом последующем запуске читается файл вместо
повторное измерение. Детали, которые имеют значение, когда вы встречаете этот файл в дикой природе:

- **Управление холодным диапазоном.** `F_NOCACHE` обходит страничный кеш только для страниц.
  которые еще не являются резидентными, поэтому проверка только что прочитанного (теплого) фрагмента будет
  измеряйте ОЗУ, а не диск. Зонд делает снимки резидентности с `mincore` и
  читает только 4 Мб окна, которые совсем холодные.
- **Вето на загрязнение.** Если осколок предлагает менее 64 МБ такого холода.
  windows, измерение отклонено: ничего не кэшируется, одна строка stderr
  объясняет отсрочку, сохраняются консервативные (медленные) дефолты, и
  зонд просто повторяет попытку при следующем, более холодном запуске. То же вето (с
  свое честное сообщение) срабатывает для недостаточно выделенного шарда — редкого или
  все еще загружаемый файл, чьи «холодные» страницы представляют собой дыры, которые можно было бы измерить как
  Заполнение нулями на скорости оперативной памяти — и для сегмента, слишком маленького, чтобы когда-либо предложить 64 МБ
  щуповые окна. Зонд измеряет наибольшее значение `.safetensors` в реж.
- **Формат (v2).** Одна строка, `v2 <gbs> <st_dev>` — измеренное ГБ/с и
  `st_dev` объема модели во время измерения. Грамматика
  строгий (простые цифры, `0 < gbs < 1000`; без inf/nan/hex/экспонент) и оба
  читатели — движок C и `coli doctor`/`coli plan` — принимают именно
  те же байты; все остальное игнорируется и перепроверяется, ему никогда не доверяют.
- **Идентификатор тома (максимально возможное).** Кэш учитывается только до тех пор, пока он
  записанный `st_dev` соответствует текущей громкости каталога модели, поэтому копирование или
  синхронизация каталога модели (включая этот скрытый файл) с другим диском
  обычно запускает повторное зондирование вместо наследования старого диска.
  номер; врач/план также перестанет показывать устаревшее значение. Это
  максимальные усилия, а не гарантия идентичности: macOS перерабатывает значения `st_dev`, поэтому
  кеш перенесен на внешний том, которому назначен старый
  идентификатор устройства (например, диски, подключенные один за другим в один и тот же слот) будет
  ошибочно доверяли, пока не были удалены. Если у вас есть сомнения после перемещения каталога модели,
  удалить `.coli_ssd`. Истинная идентификация UUID тома является именованным продолжением.
- **Устаревшее обновление.** Кэш простых чисел до версии 2 (записанный до управления
  существует, поэтому, возможно, загрязнен теплом) измеряется повторно один раз на следующий
  запуска и переписан как v2.
- **Удаление файла всегда безопасно** — единственная стоимость — одно повторное сканирование ~0,35 с.
- **Раздельные/зеркальные макеты:** датчик измеряет только **основное** направление модели.
  (`COLI_MODEL`), и его вердикт устанавливает значения кэша по умолчанию для всего запуска.
  С помощью `COLI_MODEL_DIRS`/`COLI_MODEL_MIRROR` распределение осколков по дискам
  разные скорости, этот вердикт с одним приводом является приблизительным; пересмотреть, если
  Сплит-системы со смешанной скоростью становятся обычным явлением (стартап `COLI_DISK_WEIGHTS`датчик уже измеряет каждый привод, но подает коэффициент разделения, а не
  настройки кэша по умолчанию).

## Потоковая передача с двух SSD

| Переменная | По умолчанию | Эффект |
|---|---|---|
| `COLI_MODEL_DIRS` | не установлен | РАЗДЕЛИТЕ модель на 2+ диска: список дополнительных каталогов, разделенных `;`/`,`, каждый из которых содержит **отдельное** подмножество осколков `.safetensors` (без дублирования). Осколки действуют как путь поиска — каждый фрагмент считывается с того диска, на котором он находится, поэтому одновременные экспертные нагрузки распараллеливаются на разных дисках и используется объединенная емкость. Масштабируется до N дисков. Метаданные (config/tokenizer/`.coli_usage`) остаются в основном каталоге `COLI_MODEL`. Хорошо сочетается с `PIPE=1` (одновременные загрузчики) + `DIRECT=1`. В отличие от `COLI_MODEL_MIRROR` и компонуется с ним: зеркало сопоставляется для каждого сегмента по базовому имени с объединенным (разделенным) индексом, поэтому зеркальный каталог может содержать копию любого подмножества разделенных сегментов. |
| `COLI_MODEL_MIRROR` | не установлен | `;`/`,` список каталогов, каждый из которых представляет собой идентичную по байту (только для чтения) копию модели на другом диске; эксперт читает разделенное по основному и каждому зеркалу. Частичные зеркала работают (используются только имеющиеся осколки). |
| `COLI_DISK_WEIGHTS` | отключено (запуск проверки пропускной способности) | Коэффициент разделения `<primary>,<mirror>[,<mirror2>...]` — один положительный вес на диск (например, `1,1` для 50/50, `9,3` для пары быстрый+медленный, `1,1,1` для трехстороннего зеркала). Не установлено = проверять каждый диск с помощью собственного шаблона доступа движка при запуске. |
| `SNAP_MIRROR` | не установлен | Устаревший псевдоним `COLI_MODEL_MIRROR`, используется только в том случае, если он не установлен или пуст. |
| `COLI_MIR_STRIPE` | см. источник | Степень детализации полос для разделения одного экспертного чтения по зеркальным репликам. |

Количество байтов на каждый диск отображается в строке статистики `MIRROR:`. Объедините его с `DIRECT=1`, чтобы две копии никогда не конкурировали за кэш страниц.

### Уровень маршрутизированного эксперта (`vk_tier.c`, каждый движок МО)

При использовании `COLI_VULKAN=1` каждый движок MoE (qwen36, qwen38, inkling, olmoe, kimi_k3, mimo, deepseek_v41, deepseek_v4, colibri, glm53) хранит на устройстве кэш маршрутизированных экспертов, который адаптируется, пока вы общаетесь, и вычисляет резидентные эксперты для каждого шага уровня, пока CPU вычисляет все остальное. См. [vulkan.md](vulkan.md#the-routed-expert-tier-vk_tierc) (там экспертные форматы и история каждого движка), а также два движка GLM (форматы `COLI_VK_EXPERTS`, glm53 `swiglu_limit`) [vulkan.md](vulkan.md#glm-52-and-glm-53-flash-on-the-tier). Если включен экспертный уровень CUDA, CUDA побеждает, а этот уровень остается выключенным.

| Переменная | По умолчанию | Эффект |
|---|---|---|| `COLI_VK_TIER` | дальше с `COLI_VULKAN=1` | `0`: нет уровня; маршрутизированные эксперты остаются на CPU (плотная магистраль по-прежнему использует устройство). |
| `COLI_VK_TIER_GB` | измеренный | Бюджет уровня в ГиБ, в пределах, которые может хранить устройство. ### Второе устройство Vulkan (по подписке)

Каждый движок на уровне маршрутизированного эксперта. Второй графический процессор хранит эксперты после основного устройства: заполняется из истории при запуске (самые горячие на основном устройстве, следующие там), затем адаптируются, как на основном устройстве; каждый шаг отправляет каждому устройству свою собственную партию, оба в полете одновременно. Собственные конвейеры, царапины и очереди, поэтому горячий путь основного устройства не затрагивается.

## Устанавливается через CLI (обычно не устанавливается вручную)

`coli` / `openai_server.py` устанавливают их внутри, чтобы выбрать режим работы или передать флаг:

- `SNAP` — каталог снимков модели (требуется для `glm`; устанавливается с `--model`).
- `SERVE`, `SERVE_BATCH` — выбор режима подачи/пакетной подачи.- `PROMPT` — одноразовый текстовый режим (движок также учитывает `COLI_PROMPT`, предпочтителен кроссплатформенный режим; `PROMPT` игнорируется в Windows, если он содержит cmd.exe `$`-метасимволы).
- `COLI_OMP_TUNED` — внутренний дозорный, охраняющий переисполнение ОМП (см. `COLI_NO_OMP_TUNE`); не ориентированный на пользователя.

## Рабочий пример — быстрая и воспроизводимая конфигурация Apple-Silicon.

```bash
# fast (sampling, non-deterministic by design):
COLI_METAL=1 DIRECT=1 COLI_NO_OMP_TUNE=1 PIPE=1 PIPE_WORKERS=6 MTP=0 \
  ./coli run --model /path/to/model --ram 113 "your prompt"

# same, but reproducible (greedy):
COLI_TEMP=0 COLI_METAL=1 DIRECT=1 COLI_NO_OMP_TUNE=1 PIPE=1 PIPE_WORKERS=6 MTP=0 \
  ./coli run --model /path/to/model --ram 113 "your prompt"
```
