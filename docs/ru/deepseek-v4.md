# Целевой движок DeepSeek V4 (CPU + дополнительный уровень CUDA)

[简体中文](deepseek-v4.zh-CN.md) (старая версия; эта английская страница является ссылкой)

DeepSeek V4 Flash запускается с официальной контрольной точки сегментированных защитных тензоров с помощью
без конвертации: перенаправленные эксперты остаются в исходном формате fp4, плотный набор остается fp8-e4m3
с блочными весами UE8M0, разреженное внимание MLA + DSA, 43 слоя, 256 маршрутизируемых
эксперты + 1 общий, топ-6. Движок ориентирован на CPU и каноничен для CPU: каждый
часть состояния находится в памяти хоста, а дополнительный уровень CUDA ускоряет
предварительное заполнение и декодирование поэтапно, возвращаясь к ссылке на CPU для любого
стадия снижается. Каждый этап графического процессора принимался только тогда, когда он воспроизводил
ссылка на процессор движка в жадном тексте; что может означать «идентичный» и что не может означать
между ядрами и состояниями кэша указано в [Проверка](#validation).

<a id="windows-release-recommended"></a>
## Версия Windows (рекомендуется)

Пользователям Windows не нужно собирать или копировать движок вручную. Загрузите и
распакуйте [последнюю версию Windows](https://github.com/JustVugg/colibri/releases/latest),
затем запустите Colibri через программу запуска релизов:

```powershell
coli.cmd web --model F:\path\to\DeepSeek-V4-Flash
```

Программа запуска считывает `config.json` контрольной точки, выбирает `deepseek_v4` из
это `model_type`, и запускается соответствующий предварительно созданный движок. В архиве также
содержит бэкэнд CUDA; обнаружение оборудования и безопасная начальная настройка CPU/GPU
план автоматический. Используйте `coli.cmd doctor --model F:\path\to\DeepSeek-V4-Flash`
чтобы проверить этот план, прежде чем изменять какие-либо расширенные элементы управления CUDA, указанные ниже.

Инструкции по сборке в этом документе предназначены для участников и пользовательских
строит. Не смешивайте движок, созданный из текущего исходного кода, с более старой версией:
библиотеки запуска, семейного реестра, движка и серверной части имеют одну версию
единица.

## Область применения

- Производственный код `c/deepseek_v4.c` (объединённые единицы); общественность
  API движка/сессии — `c/deepseek_v4.h`. Уровень CUDA
  `c/backend_cuda_dsv4.cu` (+ `backend_loader_dsv4.c` в Windows).
- Официальные контрольно-пропускные пункты шардированных защитных устройств загружаются через общий `st.h`;
  стандартный matmul MXFP4 использует общий `quant.h`.
- унифицированные маршруты `c/coli` `run`, `chat`, `serve` и `web` до V4; `serve` это
  шлюз, совместимый с OpenAI/Anthropic (`c/openai_server.py`): он отображает
  Инструменты OpenAI и Anthropic в встроенный контракт подсказок V4 и анализируют DSML.
  блоки вызовов обратно в каждый протокол (см.
  [матрица API для каждого движка](api.md#tool-calling-support)); грамматика остается
  не поддерживается.
- Подача жадная, один слот КВ; спекулятивные разработки существуют и отключены
  по умолчанию (`V4_DRAFT`, `V4_MTP`).
- Цели сборки: x86-64/aarch64 Linux, Windows/MSYS2, Arm64 macOS (CPU);
  Уровень CUDA в Windows (DLL среды выполнения) и Linux (`CUDA=1`, прямая ссылка);
  проверено в соответствии с WSL2).

Уничтожьте каждый сеанс, прежде чем уничтожать его движок.

<a id="memory-policy"></a>
## Политика памяти

Контрольная точка имеет 43 слоя трансформаторов, скрытый размер 4096 и 256 маршрутизированных.
экспертов на разреженный слой с top-k 6. Плотные веса занимают около 6,27 ГиБ и
резидентная выходная головка BF16 около 1,06 ГиБ. Экспертные веса маршрутизации (~ 137 ГиБ)
на диске, ~12,6 МБ каждый) передаются в потоковом режиме и кэшируются в соответствии с бюджетом оперативной памяти:
планировщик резервирует рабочее пространство и минимальный экспертный рабочий набор, а затем включает
плотная/головная резидентность и увеличивает экспертный кэш, когда позволяет память.
`--ram GiB` — это плановый бюджет, а не ограничение, установленное ОС; без этого
бюджет определяется из доступной памяти ОС. `COLI_MODEL_MIRROR=<dir>` (а
вторая копия контрольной точки на другом SSD) разделяет экспертное чтение на два
накопители — измерена пропускная способность чтения в 2 раза; в этой рабочей нагрузке два NVMe являютсяограничение как для предварительного заполнения, так и для декодирования (см. «Производительность»).

<a id="build"></a>
## Сборка

Процессорный движок (все платформы):

```bash
cd c
make deepseek-v4            # ARCH=native for the local CPU (default x86-64-v3)
```

По умолчанию в сборке используется оптимизация времени компоновки. GCC, построенный без него (
портативный w64devkit в Windows говорит: «Поддержка LTO не включена в этом
Configuration`) builds with `make deepseek-v4 LTO=0`.

<a id="windows-cuda-tier"></a>
### Уровень Windows CUDA

Движок создан на базе MinGW (оболочка MSYS2 **UCRT64**: `MSYSTEM=UCRT64`; простой
Оболочка MSYS выбирает cygwin gcc и терпит неудачу на `getrusage`), в то время как CUDA
ядра должны быть собраны с помощью nvcc + MSVC в DLL, которую загружает движок.
время выполнения. Два варианта одного и того же источника отправляются рядом и загрузчик.
выбирает при запуске графическим процессором:

| DLL | построить цель | ядра | графические процессоры |
|---|---|---|---|
| `coli_cuda_dsv4_dg.dll` | `make cuda-dsv4-dg-dll` (из оболочки vcvars64; извлекает закрепленные заголовки DeepGEMM при первом использовании) | Пути предварительного заполнения тензорного ядра DeepGEMM + общие ядра | вычислительные возможности 12.x (серия RTX 50) |
| `coli_cuda_dsv4.dll` | `make cuda-dsv4-dll CUDA_ARCH=portable` | Только общие ядра CUDA (вычисление fp32 на основе декодирования fp8/fp4) | любой sm_80+ (RTX 30/40/50, серия A/H) |

Пакет Windows CUDA этой версии (`colibri-<tag>-windows-x86_64-cuda.zip`)
содержит оба варианта, созданные с помощью `DSV4_TC=0`: без учета подписки cuBLASLt
Путь MXFP8 (`DSV4_CUDA_TC=1`), поэтому для DLL нужен только путь `cudart64_12.dll`.
Вместе с ними поставляется и драйвер NVIDIA, а не сотни МБ cuBLASLt.
Распаковано рядом с `deepseek_v4.exe` основного архива, уровень находится на следующем уровне.
по умолчанию (`DSV4_CUDA=0` выключает). DLL, которой нет в папке движка
и тот, у которого отсутствует собственная зависимость, разделяются при запуске; Windows
сообщает об обоих как об ошибке 126.

Заголовки DeepGEMM sm120, необходимые DLL, отсутствуют в репозитории:
`c/tools/fetch_deepgemm.sh` проверяет порт DeepGEMM на sm120, созданный сообществом.
(MIT; исходная версия DeepGEMM не имеет ядер sm120) плюс его подмодуль CUTLASS/CuTe
(BSD-3) при закрепленном коммите в gitignored `c/third_party/deepgemm/`,
проверяет оба идентификатора фиксации и применяет `c/patches-deepgemm-sm120-msvc.patch`
(MSVC игнорирует `alignas(64)` в дескрипторах TMA по значению — патч-пады
их). `make cuda-dsv4-dg-dll` и `DEEPGEMM=1` запустите его при первой сборке
(`make deepgemm-fetch` запускает его отдельно; ~40 МБ, требуется git);
`DEEPGEMM_HOME=<dir>` вместо этого указывает на существующее дерево, а `DEEPGEMM_PIN`
нарушает коммит. Атрибуция: `THIRD_PARTY_NOTICES.md`. Правила загрузки:сначала попробуйте `_dg`, спросите, подходит ли устройство 0 (`dsv4_cuda_backend_arch_ok`),
в противном случае загрузите общую DLL; `COLI_DSV4_DLL=<file name>` заставляет один.
Баннер при запуске называет выбор: `[DSV4 CUDA] backend=coli_cuda_dsv4_dg.dll
(deepgemm-sm120)`. Deploy = `deepseek_v4.exe` + обе библиотеки DLL рядом с ним.

<a id="linux-cuda-tier"></a>
### Уровень Linux CUDA

```bash
cd c
make -f Makefile.deepseek-v4 deepseek-v4 CUDA=1 CUDA_ARCH=portable   # generic kernels, any sm_80+
make -f Makefile.deepseek-v4 deepseek-v4 CUDA=1 DEEPGEMM=1           # DeepGEMM flavour, sm_120a only (fetches the pinned headers)
make -f Makefile.deepseek-v4 deepseek-v4 CUDA=1 CUDA_ARCH=sm_86 NO_TC=1   # toolkit older than 12.8
```

`CUDA_HOME` по умолчанию равно `/usr/local/cuda` (`CUDA_HOME=/usr/local/cuda-13.3`
чтобы выбрать версию установки). `CUDA_ARCH` — это `native` (местная карта),
`portable` (sm_80/86/89/90/120 + PTX) или один `sm_XX`; `DEEPGEMM=1` игнорирует это
и собирает только sm_120a — ядра DeepGEMM используют блочный MMA PTX, который
не существует ни для какой другой цели. `NO_TC=1` (`-DCOLI_DSV4_NO_TC`) составляет
подписаться на путь cuBLASLt MXFP8 (`DSV4_CUDA_TC=1`), для которого требуется API блочного масштабирования
cuBLASLt ≥ 12,8; используйте его для наборов инструментов CUDA 12.6 (Jetson JetPack). `libcuda`
связан с `lib64/stubs` набора инструментов (драйвер устанавливается и WSL2 поставляется
только `libcuda.so.1`), а двоичный файл содержит rpath до `$(CUDA_HOME)/lib64`.

Проверено на Ubuntu 22.04 под WSL2 (gcc 11, CUDA 13.3.1 + 12.6.85, RTX
5080): сборка только для CPU (6 с), общий толстый двоичный файл, DeepGEMM
двоичный файл и объект 12.6 `NO_TC=1` компилируются; без ворот 12,6
компиляция завершается неудачно ровно на четырех символах cuBLASLt 12.8. Во время выполнения оба
Бинарные файлы CUDA повышают уровень (`[DSV4 CUDA] device 0: ... sm_120`,
`v4_gpu tier=dense-matvec`) и сгенерировать; см. [Проверка](#validation) для
номера WSL2.

В Linux нет загрузчика: один вариант связан напрямую. Глубокий ГЕММ
двоичный файл на карте, отличной от SM120, записывает `v4_gpu alert=backend... не поддерживает
устройство` и работает только на процессоре. Закрепление хост-панели для экспертных загрузок
Пока только для Windows (`VirtualQuery`); Linux использует постраничные копии (правильно,
более медленное пополнение).

<a id="run"></a>
## Беги

Каноническая строка обслуживания (Windows, PowerShell; среда, используемая для каждого
номер ниже):

```powershell
$env:COLI_MODEL_MIRROR = "D:\models\DeepSeek-V4-Flash"   # optional second copy
$env:COLI_CUDA = "1"; $env:COLI_GPU = "0"; $env:CUDA_DENSE = "1"; $env:COLI_CUDA_PIPE = "2"
$env:COLI_CUDA_ATTN_BATCH = "1"; $env:COLI_CUDA_MOE_BATCH = "1"
$env:V4_MOE_REFILL_GROUP = "12"; $env:DSV4_CUDA_EXPERT_MIRRORS = "688"
$env:V4_LOADER_LANES = "3"   # GPU tier: 9-lane default tuned for the CPU path, see the env table
python ./coli serve --model C:\models\DeepSeek-V4-Flash --ram 32 --ctx 20000
```

`coli run|chat|web` возьмем ту же среду. В Windows подсказка с текстом
вне ASCII (китайские буквы с акцентом) не сохраняется в командной строке
движок работает вручную: задайте его с помощью `--prompt-file <UTF-8 file>`. `--ngen` — это потолок, а не
цель (ответы заканчиваются на EOS; к контексту прижат огромный потолок
с примечанием stderr). `CTX`/`--ctx` устанавливает контекстное окно.

Что делают ручки (полная таблица в [Справочнике по среде](#environment-reference-v4-engine)):
`COLI_CUDA_ATTN_BATCH=1` помещает блок внимания пакетного предварительного заполнения на графический процессор.
(проекции компрессора/индексатора, мало внимания постоянному устройству KV
Ring, wo, mHC) и позволяет графическому процессору декодировать пути внимания/индексатора;
`COLI_CUDA_MOE_BATCH=1` запускает предварительное заполнение MoE для временного экспертного банка VRAM.
(пополнение с учетом маршрута, GEMM с группировкой экспертов); `DSV4_CUDA_EXPERT_MIRRORS` это
экспертный кэш VRAM на стороне декодирования; `V4_MOE_REFILL_GROUP` ширина поиска пополнения.
Все значения по умолчанию соответствуют значениям, безопасным для CPU, если они не установлены; сам уровень графического процессора включен, когда
DLL загружается (`DSV4_CUDA=0` отключает ее). GGUF на экспертном уровне CUDA
(`COLI_CUDA=1`) является исключением: его плотные матрицы уже есть на карте
(`COLI_CUDA_DENSE`), поэтому там включено групповое внимание, если только
`COLI_CUDA_ATTN_BATCH=0`; слой без зеркала FP8 `wq_a` занимает
устройство, движок открылся.

<a id="vram-budget-and-per-card-settings"></a>
## Бюджет VRAM и настройки для каждой карты

Что уровень сохраняет в видеопамяти (измерено на RTX 5080 емкостью 16 ГБ): плотность/внимание
зеркала **6,3 ГБ** (необходимы для внимания графического процессора и плотного матвека графического процессора в
декодирование), временный экспертный банк предварительного заполнения (`COLI_CUDA_MOE_BATCH`, освобождается при
начинается декодирование; 12,75 МБ на слот, 13,5 МБ в сборках DeepGEMM: **3,2 ГиБ**
для 256 экспертов, 3,4 ГиБ на DeepGEMM), буферы внимания/КВ/работы **~0,5 ГБ**,
а остальные — как экспертные зеркала декодирования по **12,75 МБ каждое** (ворота, вверх ивниз в fp4 с их весами).
`DSV4_CUDA_EXPERT_MIRRORS` — это только верхняя граница (по умолчанию 4096): кэш
растет, пока хотя бы `DSV4_CUDA_VRAM_RESERVE_MB` остается свободным, поэтому свободная VRAM
изменяет его размер во время выполнения — обычно вам не нужно его устанавливать. Бесплатная видеопамять — это
перечитывайте каждые 64 зеркальных промаха; между ними явный резерв и 600 МБ.
запас также учитывает количество зеркал, выращенных с момента последнего чтения, поэтому кэш
останавливается на резерве вместо до 64 зеркал (~800 МБ) мимо него, где
Буфер сжатого KV и буферы внимания предварительного заполнения больше не подходят и
внимание их слоев возвращается к процессору (`[DSV4 CUDA] kv comp
распределение: недостаточно памяти`). Дефолт размером с банк, описанный ниже, уже несет в себе
эти 64 зеркала являются запасом, поэтому его решения не меняются. Декодирование
привязка к диску, поэтому большее количество зеркал помогает пропорционально частоте попаданий, которые они добавляют
(всего ~11 000 экспертов; 600 зеркал ≈ 5 %); больше оперативной памяти (`--ram`) позволяет купить больше, чем
больше видеопамяти.

Резерв по умолчанию составляет 600 МБ без учета банка. С `COLI_CUDA_MOE_BATCH=1`
его размер соответствует банку модели при открытом движке, поэтому следующая большая предварительная заправка
все равно находит место после декодирования карты: 600 МБ + банк
(два банка с `COLI_CUDA_MOE_DOUBLE=1`, обратно в один после завершения предварительной выборки)
выключился; второй банк, который не подошел, повторяется следующим
предварительное заполнение, чтобы его место оставалось зарезервированным) + 64 зеркала, потому что есть бесплатная видеопамять
перечитываю только каждые 64 промаха. Это 4681 МБ для 256 экспертов по дженерикам.
сборки, 4873 на DeepGEMM и 3100 для контрольной точки из 132 экспертов (7945, 8329 и
4783 со вторым банком); движок регистрирует это как `v4_gpu mirror-reserve=`.
При наличии менее 32 живых зеркал по умолчанию остается свободным только 600 МБ, поэтому карта слишком мала.

### Аудит только CPU (16 августа 2026 г.)

Вопрос: путь CPU все еще вычисляет то, что восходящий `dev` вычисляет после
графический процессор работает? Метод: подсказка из 826 токенов, 48 жадных токенов, реальная контрольная точка,
восходящий движок `dev`, построенный из собственного дерева, и движок, построенный в этом дереве
без уровня графического процессора (форма сборки Linux/macOS) и с уровнем
отключен.

- Компилируется чисто без `COLI_V4_GPU_TIER`; крошечный справочный набор для факелов
  (`tests/test_deepseek_v4_tiny.py`) является точным для токена в сборке только для CPU для
  каждый целевой случай.
- На реальном контрольно-пропускном пункте жадный текст **не** является надежной проверкой личности.
  между конфигурациями, в самом восходящем потоке: запускаются горячие (резидентные в кеше) эксперты
  векторизованное ядро `rows16`, в то время как холодные запускают эталонный matvec,
  два накапливаются в разных порядках, и какие эксперты являются горячими, зависит от
  история автозакрепления (`.coli_usage`, перезаписывается при каждом запуске), ширина чанка и
  шаблон попадания. Upstream создал разные тексты из 48 токенов с и без
  его история; то же самое произошло и с этим деревом; каждый вариант представляет собой последовательный ответ, отличающийся
  путем округления подбрасываем несколько токенов.
- При удалении этой переменной с обеих сторон (`COLI_V4_ROWS16=0`
  `COLI_V4_AUTOPIN=0 COLI_V4_SAVE_USAGE=0`: только эталонные ядра, нет
  история) **восходящий поток и сборка этого дерева только для CPU дают идентичные
  Текст из 48 токенов** — математические вычисления CPU не изменились.
- Одно изменение в этой ветке изменило порядок накопления CPU и теперь отключено.
  по умолчанию: короткое замыкание идентификатора индексатора для `count <= index_topk`
  (возвращенные кандидаты в порядке индекса; восходящий поток возвращает их в порядке оценки,
  и разреженные эталонные суммы внимания в указанном порядке). `V4_IDX_IDENTITY=1`
  повторно включает его (предварительное заполнение на графическом процессоре происходит примерно на 8 % быстрее, например 96 с -> 88 с при 3,3 к).
- Скорость предварительного заполнения только для CPU: фрагменты 128 и 64 идентичны в пределах шума (788 и 788).
  797 с для 826 токенов); закрепленная плита, конвейерное пополнение и все ядро
  работают только с графическим процессором и не затрагивают путь процессора.
- Вырожденная конфигурация защищена: экспертный зеркальный кэш декодирования содержит менее 8 записей.
  (`DSV4_CUDA_EXPERT_MIRRORS<8`) переработан слот, на который все еще ссылаются в одном
  слой и образующийся мусор; такие кеши теперь остаются в CPU.

## Последующие действия

- Нежадная выборка и больше слотов для обслуживания.
- Уровень Linux CUDA: измерение на собственном компьютере Linux (проверено WSL2), закрепление хоста POSIX.
- Экспертно-параллельный уровень с несколькими графическими процессорами (проектный проект, не отслеживаемый до момента создания).
- Совместная замена двух временных частных путей квантования (кеш строк 16).
