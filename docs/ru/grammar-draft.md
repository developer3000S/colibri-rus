# спекулятивные черновики с грамматическим уклоном

*Каноническая ссылка на черновой вариант источника `GRAMMAR=` (метод F). История: идея в
[#48](https://github.com/Developer3000S/colibri-rus/issues/48), реализация в
[#70](https://github.com/Developer3000S/colibri-rus/pull/70), объединенная рецензия с A/B
измерения и исправления в [#146](https://github.com/Developer3000S/colibri-rus/issues/146).*

<a id="the-mechanism-in-one-paragraph"></a>
## Механизм в одном абзаце

При рабочих нагрузках с ограниченным выводом (JSON/NDJSON, вызов функций, структурированное извлечение)
сама грамматика является черновым источником. Подмножество GBNF на уровне байтов компилируется в
набор стеков КПК; везде, где грамматика допускает **ровно один** допустимый следующий байт
(скобки, кавычки, имена ключей, тела перечислений, фиксированные разделители), движок выполняет это
принудительный интервал, токенизирует его и вводит в качестве предварительно принятых токенов черновика в
**то же самое пакетное объединение проверки вперед**, используемое в черновиках MTP и n-gram. Это никогда
ограничивает выборку: принудительные интервалы *проверяются целевой моделью*, поэтому это неправильно,
устаревшая или рассинхронизированная грамматика не может изменить вывод — в худшем случае черновики отклоняются,
и адаптивная защита отключает источник ниже 50% приемлемости. Он составляет с
`DRAFT`/MTP, которые заполняют пробелы между произвольным текстом между обязательными интервалами.

<a id="why-it-pays-disproportionately-in-this-engine"></a>
## Почему в этом движке непропорционально платят

В MoE с потоковой передачей данных на диск предельные затраты на этап декодирования составляют **уникальные экспертные байты.
с диска**, а не с флопа. Пакетное объединение вперед загружает каждого уникального эксперта один раз за
*все* позиции в проверочном пакете и структурные токены в значительной степени передаются экспертам
соседние позиции с произвольным текстом уже втянуты. Таким образом, каждый принятый принудительный интервал
практически напрямую преобразуется в **предотвращенное чтение с диска на каждый выпущенный токен**. На плотном
Движок процессора тот же трюк экономит только вычисления; здесь он экономит самый дефицитный ресурс.
Меньшее количество пересылок также означает меньшее изменение LRU, что влияет на частоту попаданий в кэш.

<a id="usage"></a>
## Использование

```bash
GRAMMAR=fit.gbnf COLI_TEMP=0 PROMPT="..." ./colibri 64 4 8
```

- `GRAMMAR=<file.gbnf>` — снабдить исходный текст грамматикой. GBNF на уровне байта
  подмножество: литералы (экранирующие символы `\" \\ \n \r \t \xHH`), байтовые классы `[...]`/`[^...]`,
  ссылки на правила, группы, постфиксные `? * +`, `|`, `#` комментарии. Корневое правило должно быть `root`.
- `GRAMMAR_DRAFT=n` — ограничение принудительного диапазона на перенаправление (по умолчанию 24, максимум 48).
- Постановка на охрану ленивая (ходок запускается с первого байта, который допускает рут, пропуская
  преамбулы) и устойчивы к десинхронизации (несоответствующий байт убивает ходок для
  текущий диапазон; оно перевооружается при первой же возможности).
- Движок сообщает об окончании работы: `grammar: NN% acceptance (a/b forced drafts)`.

<a id="what-to-expect-measured-current-main-m3-max-details-in-146"></a>
## Чего ожидать (измерено, ток `main`, M3 Max — подробности в #146)

| форма рабочей нагрузки | ток/переслать | сквозной |
|---|---|---|
| соответствующий компактный NDJSON (эпоха PR № 70) | 1,60 | большой |
| current-main NDJSON с неаккуратными интервалами и длинными полями для свободного текста | 1,21–1,22, одобрение 87% | ~+5% |
| окна с преобладанием прозы (преамбулы, длинные строки `reason`) | ~1,0 | ~ноль |

**Выигрыш обусловлен структурной плотностью.** Свободный текстовый контент ни к чему не приводит;
ключи, разделители, кавычки и тела перечисления заставляют все. Два практических рычага:

1. **Запрос на компактный вывод** (короткие поля типа перечисления, без ограничений уценки).
2. **Грамматики, допускающие пробелы**: грамматика, состоящая только из компактных элементов, сначала рассинхронизируется.
   теряет пространство и теряет каждый промежуток после него. Выдача необязательного пробела
   правило для разделителей стоит этих одиночных байтов (два допустимых байта → не принудительно), но
   сохраняет ходок в живых, поэтому каждый многобайтовый диапазон после них по-прежнему является черновиком.Поскольку черновики проверяются, толерантность строго позитивна.

<a id="guarantees-and-limits"></a>
## Гарантии и лимиты

- **Без потерь по конструкции**: жадный вывод побайтно идентичен с и без
  грамматика (проверена в #70 A/B); при выборке шаг отбраковки сохраняется
  распределение выборки. Граница токенизации принудительного диапазона байтов равна
  не гарантированно совпадает с моделью — проверка поглощает
  разница (в худшем случае последний вариант пролета будет отклонен).
- Адаптивное отключение при принятии ниже 50%, поэтому несовпадающая грамматика деградирует до уровня
  базовая скорость, никогда не ниже ее надолго.
- Ограниченная работа: грамматика, которой ходок не может следовать, дешево отключает его.
  вместо того, чтобы задерживать движок. Прошлые 64 живых стека (`GR_MAX_STACKS`), стек
  глубже 64 кадров (`GR_MAX_DEPTH`, левая рекурсия) или 65 536 шагов на один
  байт (`GR_MAX_WORK`: альтернативы, которые располагаются в одних и тех же стеках, несколько сотен
  байты грамматики, которые будут проходить 2^N путей; Грамматика схемы JSON занимает не более
  35) запрос выполняется без черновиков грамматики, его вывод не изменяется.
- Примечание по сравнительному тестированию (выучено на собственном горьком опыте, см. № 146): удерживайте PIN-код в горячем хранилище и
  постоянная теплота кэша страниц на всех ступенях A/B и отчет об экспертной частоте попаданий
  столбец рядом с любым утверждением tok/s.

<a id="prior-art"></a>
## Уровень техники

Общая идея — это не colibri: **декодирование с переходом вперед** (SGLang;
[XGrammar](https://arxiv.org/abs/2411.15100)) пропускает грамматически детерминированные токены на
*ограничение выпуска*, а объединение Outlines приводит к аналогичному движению автомата. Что
эта реализация добавляет: принудительные интервалы как **черновой источник, проверенный в целевом
собственный вперед** (без потерь даже при неправильной грамматике, компонуется с MTP/n-граммой в одном
объединенный пакет), развернутый там, где выигрыш выражается в экспертном вводе-выводе, а не в
пасы вперед.

<a id="server-usage-response_format-openai-api"></a>
## Использование сервера: `response_format` (OpenAI API)

Шлюз (`openai_server.py`) превращает `response_format` в **запрос**
грамматика передается в движок по протоколу `SUBMIT` (необязательный 7-й заголовок
поле, `gbytes`; Заголовки из 6 полей от старых клиентов остаются действительными — поле
аддитивная и обратная совместимость в обоих направлениях):

```jsonc
{"response_format": {"type": "json_object"}}                       // generic JSON grammar
{"response_format": {"type": "json_schema",
                     "json_schema": {"schema": { ... }}}}          // compiled by schema_gbnf.h
{"response_format": {"type": "gbnf", "grammar": "root ::= ..."}}   // raw GBNF (extension)
```

Семантика идентична `GRAMMAR=`/`SCHEMA=`: **черновой источник, а не
ограничение выборки**. Схема вне поддерживаемого подмножества или неверный формат GBNF.
стоит ускорение — ни запрос, ни вывод. Разработка чертежей занимается
жадные запросы (`temperature: 0`); выборочные запросы выполняются без составления. Скомпилировать
накладные расходы незначительны: ~8 мкс/запрос для типовой схемы, ~18 мкс на
32-уровневая вложенная крышка (измеренная, M3 Max). Полезные данные грамматики ограничены 1 МБ.
Как и в случае с MTP (#100), составленный жадный забег может отличаться от незадрафтованного по
токены близкой связи (пересылка проверки имеет другую форму пакета); каждый выход
представляет собой действительный жадный поток собственных прямых форм.
