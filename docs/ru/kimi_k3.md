# Движок Kimi K3 (`c/kimi_k3.c`)

Родственный движок для [Kimi K3](https://huggingface.co/moonshotai/Kimi-K3)
(параметры 2,8T, активные 104B, 93 слоя), в соответствии с принципом «один движок на семейство».
шаблон (`colibri.c` = GLM-5.2, `olmoe.c`, `inkling.c`). Он разделяет `st.h`,
`json.h`, `tok.h`, `quant.h` и ничего не затрагивает в движке GLM.

```
make kimi_k3
./kimi_k3 <model_dir> "prompt" --ngen 64
```

`<model_dir>` — это либо простой снимок HF (config.json +
`model-*-of-000096.safetensors`) или переупакованный контейнер (ниже). Только текст:
башня видений (осколки 95–96) никогда не читается.

<a id="architecture-notes"></a>
## Примечания по архитектуре

K3 не является моделью в форме DeepSeek; четыре штуки относительно всего новые
еще в этом репо:

- **Гибридное внимание, NoPE.** 69 слоев KDA (Kimi Delta Attention) + 24 закрытых слоя.
  Слои MLA (каждый 4-й плюс последний слой). Нет никакого позиционного
  кодирование где угодно — позиция живет в свертке и распаде KDA. ОМС
  блок имеет диммы DeepSeek (q_lora 1536, kv_lora 512, нет 128 + 64 некэшированные
  дополнительные димы, v 128, 96 голов), и оба типа внимания умножают свою производительность.
  полноранговыми сигмовидными воротами `σ(W_g x)` до `o_proj`.
- **KDA** на голову (размер 128, 96 голов): `q,k,v = SiLU(causal-conv4(W x))`,
  q/k L2-нормализованный (ε=1e-6 внутри sqrt), q масштабированный на 128^-1/2; на канал
  распад `gk = -5·σ(exp(A_log[h])·(W_fb W_fa x + dt_bias))`; правило дельты
  обновление состояния `S = (I − βkkᵀ)·Diag(e^gk)·S + βkvᵀ`; вывод
  `W_o[σ(W_g x) ⊙ RMSNorm_head(Sᵀq)]`. Контрольно-пропускной пункт сохраняет `A_log` как
  `[128]`: это параметр `[96]` для каждой головки, дополненный нулями (проверено —
  записи 96..127 равны ровно 0). Состояние декодирования: 96×128×128 f32 на слой.
- **AttnRes заменяет остаточный поток.** Каждый уровень продолжает работать.
  `prefix_sum`; на слоях 0, 12, 24,…, 84 делается снимок в блок
  список. Дважды на слой (до внимания, перед МЛП) и один раз на
  В конце скрытое состояние ЗАМЕНЯЕТСЯ смесью softmax поверх
  `[snapshots…, prefix_sum]`, оценка `(v · (res_norm.w ⊙ res_proj.w)) /
  rms(v)` и смешивание необработанных (ненормализованных) записей в fp32.
- **Стабильный LatentMoE.** Сигмовидный маршрутизатор `[896, 7168]` + смещение коррекции оценки,
  топ-16 выбраны на основе смещенных оценок, веса представляют собой перенормированные исходные оценки.
  Токен проецируется 7168 → 3584, 16 экспертов работают в этом скрытом пространстве.
  (GLU, inter 3072), агрегат рассчитывается по RMSNorm и проецируется обратно.
  3584→7168; Добавлены два объединенных полноширинных общих эксперта (inter 6144).
  Активация **SiTU-GLU**: `4·tanh(g/4)·σ(g) · 25·tanh(u/25)`.

<a id="weights"></a>
### Вес

Только маршрутизированные эксперты (`experts.N.w{1,2,3}`) квантуются в
контрольная точка — **MXFP4** (сжатые тензоры `mxfp4-pack-quantized`,
обученный с учетом квантования): полубайты e2m1 упакованы по два на байт (низкий полубайт =
четный столбец, бит 3 = знак) со шкалой степени двойки ue8m0 на 32 столбца,
`w = v · 2^(scale-127)`. 17,55 МБ на эксперта, 82 432 эксперта ≈ 1,45 ТБ.
`quant.h` получило `matmul_mxfp4` (скаляр + AVX2), которое вычисляется в этом макете
напрямую — экспертные байты **никогда не конвертируются**; Веса QAT
обученные значения, и любое повторное кодирование только добавляет ошибку.

Все остальное — BF16 и квантуется в ОЗУ **во время загрузки** (int8
per-row/int4-g64), либо читать предварительно квантованные из переупакованного контейнера.

<a id="streaming-design"></a>
## Потоковый дизайн

Эксперты передаются прямо из фрагментов защитных тензоров через каждый уровень
ЛРУ (`K3_EXPERT_GB`). Измеренные факты компоновки, которые использует движок: шестерка
тензоры эксперта хранятся подряд (один эксперт = один `pread`), а
эксперты *не* упорядочены по идентификаторам внутри сегмента, поэтому нагрузки выдаются со смещением диска
заказ. Промахи токена считываются **параллельно** (OMP по слотам рабочего набора)и по умолчанию с **O_DIRECT** (`K3_DIRECT=0` для буферизованного): резидентный
веса оставляют мало места для кэша страниц, а плоская маршрутизация означает кэширование операций чтения.
большинство из них в любом случае не могут быть повторно использованы — при измерениях на 93-слойной модели это заняло
эксперт читает от ~1,8 до ~6,3 ГБ/с (потолок накопителя 7,1) и декодирует от ~21
до ~9,4 с/токен. Минимальное количество слотов LRU равно 1 (эксперты потребляются по одному),
так что `K3_EXPERT_GB` почитается даже при крошечном бюджете. Кроме того, `K3_PIPE`
(по умолчанию включено) запускает чтение в потоках загрузчика, поэтому матмулы эксперта j перекрываются
предварительное чтение эксперта j+1, `K3_IDOT` (по умолчанию включено) вычисляет экспертные матрицы с помощью
для каждой 32-группы int8-квантованные активации через целочисленные точки (e2m1 удвоил
значения точны int8 — тот же трюк, что и `dot_i4i8`), и `K3_TOPP` опционально
отбрасывает маловесный хвост топ-16 (перенормированный; качество-ворота любые
сначала установите настройку `K3_LOGITS` A/B). Обратите внимание, что маршрутизатор K3 был обучен с помощью квантильной балансировки (намеренно
фиксированное экспертное использование), поэтому показатели попаданий LRU структурно ниже, чем на моделях
с искаженной маршрутизацией — ожидайте, что экспертный уровень будет ограничен полосой пропускания.

<a id="tokenizer"></a>
## Токенизатор

В репозитории HF поставляется только необработанный словарь tiktoken (`tiktoken.model`).
`tools/k3_tokenizer.py` записывает для него `tokenizer.json`, а `tok.h` получает:

- **семейство претокенизаторов kimi** (обнаружено через `\p{Han}` в регулярном выражении Split):
  правила o200k с учетом регистра плюс ведущее правило Хана, Хан исключен из
  классы букв и отсутствие хвоста `/` в правиле пунктуации;
- **режим ранга-BPE**, используемый, когда `model.merges` пусто: объединить соседние
  пара, чья конкатенация имеет наименьший словарный идентификатор — собственный идентификатор tiktoken
  алгоритм, поэтому кодирование является точным по своей конструкции. (Восстановление списка слиянием из
  ранги, очевидно, имеют потери: стандартная реконструкция ошибочно объединяется, например.
  «новая строка»; вот почему генератор не генерирует слияний.)

`tools/k3_tokenizer.py --ctest tests/test_tok_kimi` перепроверяет C
токенизатор против тиктокена; он совпадает во всех 18 корпусах случаев (китайский,
кандзи-кана, корейский, CRLF, сокращения, эмодзи, границы смешанного письма).

## Проверка

`tools/k3_ref.py` — это независимая реализация полного слоя.
стек (повторение KDA, закрытое MLA, AttnRes, LatentMoE с деквантом MXFP4). С
вводимые входные данные (`K3_X0`, минуя встраивание) и веса f32
(`K3_BITS=32`), движок C сопоставляет его с реальными весами контрольных точек во всех
четыре типа слоев для **rel-L2 ≤ 2.2e-6** (шум float32).

Одно свойство, которое стоит знать: логиты микса AttnRes расположены близко друг к другу.
(поля ~0,02), поэтому микс сильно усиливает *вес* шум, даже если он
не усиливает *входные* возмущения (входное возмущение 1e-4 остается 1e-4
через стек). Время загрузки int8 создает дрейф скрытого состояния, увеличивающийся до
~14 % по четырем слоям на синтетических входах — SNR для каждого тензора квантования
равномерность ~1 %, так что это архитектурная чувствительность, а не проблема выброса.
Оценивайте выбор квантования по логитам реального текста, а не по нормам синтетических векторов.

<a id="chunked-prefill"></a>
## Частичное заполнение

Предварительное заполнение обрабатывает промпт частями по `K3_CHUNK` токенами, на уровне слоев:
каждый плотный матмул распределяет пакеты по куску (каждая весовая матрица передается из
RAM один раз на блок вместо одного раза на токен), МО загружает каждый уникальный
эксперт фрагмента один раз (измерено при C=32 для реального текста: дедупликация в 2,7 раза —
соседние токены разделяют экспертов гораздо больше, чем предполагает QB-плоская маршрутизация —
9,6 вместо 25,8 ГБ/токен), а lm_head запускается только на последнем фрагменте.
токен. Последовательное состояние (повторение KDA, кэш MLA, учет AttnRes)
авансы за токен внутри каждого слоя в исходном порядке, поэтому разбиты на части
результаты **бит-идентичны** результатам по токену (проверено: 125-позиционный
заданные учителем потоки логитов при C=32 и C=1 точно совпадают). Измеренное предварительное заполнение:
~5,3 -> **2,0 с/токен** при C=32. Обновления состояния KDA — AVX2.
(скалярный резерв для диммирования головки, не кратного 8).

<a id="chat-api-and-web"></a>
## Чат, API и Интернет

```sh
# standalone one-turn diagnostic
./kimi_k3 <model_dir> --chat "your question" [--system "..."] --ngen 300

# first-class multi-turn interfaces (config.json auto-detects Kimi K3)
COLI_MODEL=<model_dir> ./coli chat
COLI_MODEL=<model_dir> ./coli serve
COLI_MODEL=<model_dir> ./coli web
```

Формат чата К3 («XTML», из собственного контрольно-пропускного пункта `encoding_k3.py`) использует
всего четыре специальных токена — `<|open|>`, `<|close|>`, `<|sep|>`,
`<|end_of_msg|>` — вокруг имен и атрибутов обычных текстовых тегов:

```
<|open|>message role="user"<|sep|>TEXT<|close|>message<|sep|><|end_of_msg|>
<|open|>message role="assistant"<|sep|><|open|>think<|sep|>        <- generation prompt
```

Мышление ассистента является *структурным* каналом и сохраняется, когда
OpenAI-совместимый клиент отправляет до `reasoning_content`; `enable_thinking=false`
открывается `<response>` напрямую. Шлюз не преобразует XTML в строку:
он отправляет сообщения с длиной рамки в движок C, который строит каждую структурную структуру.
и сегмент обычного текста на границе токенизатора, требуемый рангом-BPE K3.
Мы сверили нашу обработку текста с собственной обработкой текста Moonshot: их `encoding_k3.py`
превращает разговор в цифры, которые на самом деле читает модель, а наша
выдал **одинаковые числа во всех 77 тестовых разговорах** — многоходовой
истории с сообщениями системы, пользователя и помощника, включая текст, отличный от ASCII.
Таким образом, движок ничего не искажает незаметно до того, как модель это увидит.

- Декодирование однотокенное (нет спекулятивного декодирования — у K3 нет головки MTP).
- Объявления/вызовы инструментов и содержимое изображений не отображаются через общий доступ.
  шлюз еще; неподдерживаемые запросы явно терпят неудачу.

- Пути протокола, токенизатора, шлюза, TUI и веб-клиента являются локальными.
  можно протестировать без контрольной точки 1,5 ТБ. Для заявления о выпуске по-прежнему требуется один
