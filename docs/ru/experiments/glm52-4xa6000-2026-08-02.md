Еще два правила были изучены на собственном горьком опыте, и оба из них привели к неправильному опубликованному утверждению:

<a id="only-two-levers-actually-moved-the-number"></a>
### Только два рычага действительно переместили число

**`CUDA_DENSE=1` — ×2,8 (1,53 → 4,26).** По умолчанию движок сообщает
`[CUDA] mode: routed experts only (resident dense on CPU)`. На хосте, привязанном к процессору, плотный
путь всех 78 слоев выполняется на процессоре, а 192 ГБ видеопамяти служат только экспертам. Этот флаг
**не упоминается в общедоступном README**; это был единственный найденный наиболее прибыльный вариант.

**Удаление `URING` + `PILOT` + `PILOT_REAL` + `PILOT_TWO` — +26 % (4,26 → 5,38).** Эти
скрыть задержку диска. Когда эксперты резидентны, скорость чтения диска во время декодирования **0 МБ/с**, поэтому
Механизм предварительной выборки/перекрытия потребляет только CPU — дефицитный ресурс. `DIRECT=1 PIPE=1` сохранено.

<a id="neutral-1-within-noise"></a>
### Нейтраль (±1 %, в пределах шума)

`COLI_CUDA_TC_INT4` (путь W4A4 требует ≥16 строк на эксперта; декодирование S=1 обеспечивает одну),
явный `OMP_PROC_BIND=close` (движок уже устанавливает его) и удаление `COLI_CUDA_PIPE`
(его шлюз декодирования уже учитывает количество устройств на 4 устройствах).

<a id="counter-intuitive-results"></a>
### Противоречивые результаты

1. **Максимальное использование RAM+VRAM *ухудшается*, когда плотный путь остается на CPU**: C1 (176 ГБ RSS,
   188 ГБ видеопамяти) → 1,41 tok/s по сравнению с C0 (99 ГБ RSS) → 1,53.
2. **Прибыль не суммируется.** `RAM_GB` 190→205 дает +4,5 % на базе C2, но только
   +1,5 % после удаления `URING`/`PILOT` — оба нацелены на одни и те же остаточные промахи по диску.
3. **Пропускная способность параллелизма не масштабируется**: 1,32 / 1,51 / 1,46 tok/s в сумме 1/2/4.

<a id="prefill-is-a-different-regime-but-not-for-the-reason-stated-in-the-first-draft"></a>
### Предварительное заполнение — это другой режим, но не по причине, указанной в первом проекте.

Декодирование активирует 8 из 256 экспертов на каждом уровне, и последовательные токены повторно используют их, поэтому изученные
закрепленный набор покрывает их. Предварительное заполнение не позволяет:

```
P(an expert is missed by N tokens) = (1 − 8/256)^N
P(512) ≈ 1e-7        P(8595) ≈ e^-273
```

Срез в 512 токенов затрагивает каждого эксперта каждого слоя. **Первая версия этого отчета
потом сделал вывод, что арифметика не поддерживает** — поэтому prefill
*перечитывает* нерезидентную модель один раз для каждого среза. Это не так: в кеше сохраняется какой-то кусочек
загружено, поэтому очистка оплачивается **один раз**, а не один раз за срез. Проблема № 153 измеряет это напрямую.
на хосте Zen 5 + 5090 — когда промпт удваивается, время диска остается ** неизменным ** (19,4 с → 21,2 с)
при этом внимание удваивается (49,2 с → 118,0 с). Предварительное заполнение привязано к вниманию, а не к вводу-выводу.

`COLI_PREFILL_CHUNK` по-прежнему имеет значение, но по другой причине: в фрагменте 512 фиксированный срез
затраты и реконструкция `kvb_all` доминируют. Поднять его до 2048 стоит брать.

Контролируемые измерения предварительного заполнения на этом хосте, `.coli_usage` сделанные снимки и восстановленные ранее
каждый уровень, промпт на ~ 1190 токенов:

<a id="6-the-finding-that-invalidates-naive-ab-benchmarking"></a>
## 6. **Открытие, которое делает недействительным наивный сравнительный анализ A/B**

Конфигурация, **идентичная по размещению памяти** наилучшему результату, указанному выше.
(VRAM 178 ГБ, RAM 190 ГБ) измерено **2,56 tok/s вместо 5,46**, без параметра памяти
изменился.

Скрытая переменная — это `.coli_usage`, постоянный изученный профиль маршрутизации, который
закрепленный горячий магазин при запуске:

| Момент | Записанные выборы |
|---|---|
| первый старт | 58 240 |
| конец матрицы из 9 конфигураций (~1 час спустя) | 238 840 |
| после дня реального разговорного общения | **17 697 640** |

Закрепленный набор перенастроился на реальную рабочую нагрузку, поэтому синтетический тест подсказал
стал нераспределенным для кеша.

**Последствия для всех, кто тестирует этот движок:**

- `.coli_usage` **сохраняется при перезапуске** и монотонно растет. Две конфигурации
  измеренные часы с разницей в часы несопоставимы даже при одинаковых флагах.
- `CONTRIBUTING.md` требует *политику разминки*, но одной разминки недостаточно:
  Профиль должен быть **сохранен и восстановлен** перед каждой тестируемой конфигурацией.
- Абсолютные цифры в этом отчете следует рассматривать как *рейтинги внутри сессии*, а не как
  портативные показатели пропускной способности. Матрица из 9 конфигураций выполнялась подряд за один час на одной
  подсказка, чтобы ее порядок был внутренне согласованным; межсессионные сравнения — нет.

Были сформированы и затем опровергнуты две гипотезы: «общая резидентность определяет пропускную способность».
(опровергнуто: резидентность 98 % измеряется *медленнее*, чем 91 %) и «резидентность VRAM определяет пропускную способность»

### Где потолок

При 3.64 tok/s время токена составляет 275 мс, из которых экспертное чтение на стороне CPU составляет ~200 мс:

## 14. Примечания по сборке (Linux, CUDA)

`nvcc` 12.6 + gcc 13 не работает с `identifier "_Float32" is undefined`;
`-allow-unsupported-compiler` выдает 100 ошибок. Рецепт `BUILD-cuda-glibc241.md` работает.
и не требует root, если префикс является каталогом пользователя:

```sh
micromamba create -y -p ~/cuda13 -c nvidia -c conda-forge cuda-nvcc=13 cuda-cudart-dev=13
ln -sfn ~/cuda13/lib ~/cuda13/lib64
make glm CUDA=1 CUDA_ARCH=sm_86 CUDA_HOME=~/cuda13
```

Для веб-панели требуется Node ≥ 20.12 (`styleText` от `node:util`); Ubuntu 24.04 поставляется
18.19, поэтому `npm run build` не работает при стандартной установке.

<a id="14-build-notes-linux-cuda"></a>
### `PIN_GB=all` не является безопасным устойчивым состоянием

Первоначально в отчете это рекомендовалось. После двух дней обычной эксплуатации движок **отказал
для начала**:

```
[USAGE] expert history: 26,437,320 selections
[PIN]   placement: 4661 VRAM + 5497 RAM expert (207.7 GB warm)
[RAM]   refusing to start: projected peak 315.0 GB exceeds the 258.2 GB available
```

Ничего не перенастраивалось. Семена `PIN=auto` от `.coli_usage`, который растет монотонно —
здесь 18,2 млн -> 26,4 млн выборок — так что с `PIN_GB=all` закрепленный набор растет вместе с ним:
184,8 ГБ, затем 207,7 ГБ. Рабочая конфигурация перестает работать сама по себе.

Это исправляют две вещи, и обе они относятся к рекомендуемой конфигурации: **bound `PIN_GB`** и set
**`COLI_USAGE_DECAY`**, который существует именно для этого и на который пользователю ничего не указываетк тому моменту, когда они ударились о стену.

Стоит отметить, что сам отказ является правильным и новым поведением: до #793
проекция недосчитала ширину слота, поэтому началась бы та же самая конфигурация и
были убиты ООМ среднего поколения (#305, #766).

`MemoryMax=238G` в модуле systemd: в `RAM_GB=235` собственный учет движка исключает
распределения, которые ядро по-прежнему взимает с cgroup, и убийца OOM прибывает до того, как
внутренняя крышка движка подходит.

Примечания по эксплуатации: движок не освобождает VRAM сразу при остановке — перезапуск через
~30 с происходит сбой с `Failed with result 'exit-code'` (`Restart=on-failure` восстанавливается). И
`coli plan` вычисляется с *текущей свободной* видеопамятью, поэтому его вывод не имеет смысла, пока
Экземпляр движка запущен.
