# Режим локального кластера

Координатор сохраняет генерацию токенов, маршрутизацию и состояние KV локальными, в то время как
Опытные работники с дисковым резервным копированием выполняют маршрутизируемые FFN на других компьютерах Mac. Слой маршрутизирован
пакетное объединение отправляется как один постоянный TCP-запрос, поэтому токен не требует одного
туда и обратно для каждого эксперта и каждого работника до того, как будет прочитан ответ, поэтому слой
ждет своего самого медленного работника, а не каждого из них по очереди.

Запустите дополнительную службу регистрации:

```bash
./coli cluster coordinator --host 0.0.0.0 --port 8765
```

Для каждого рабочего процесса с одной и той же преобразованной моделью, доступной локально:

```bash
./coli cluster worker --model /nvme/glm52_i4 --port 9100 \
  --coordinator http://COORDINATOR:8765 --advertise-host WORKER_IP
```

Запустите координатор с функцией обнаружения или укажите `--cluster-workers
HOST:PORT,...` для статической настройки:

```bash
./coli serve --model /nvme/glm52_i4 \
  --cluster-coordinator http://127.0.0.1:8765
```

GLM-5.3 (`glm53`, включая Flash) одинаково обслуживает своих потоковых экспертов int4.
путь. Рабочий GLM-5.3 загружает только экспертную таблицу и кэш, поэтому ОЗУ
плотные гири потребуют тепла, чтобы согреть своих специалистов. Эксперты принадлежат
детерминированный взвешенный хеш, поэтому каждый из них всегда относится к одному и тому же работнику.
Каждый работник при запуске измеряет свой диск и получает пропорциональную ему долю.
Чтобы установить доли самостоятельно, передайте по одному весу каждому указанному работнику с помощью
`COLI_CLUSTER_WEIGHTS=3,2,1` на координаторе или `COLI_WORKER_WEIGHT` на
рабочий. Запросы на слой передаются каждому работнику до того, как будет прочитан какой-либо ответ, поэтому
их диски считываются одновременно, и пока рабочий вычисляет один блок
экспертам слоя, он считывает следующий блок во вторую половину этого слоя.
слоты кэша, поэтому его диск и ядра тоже работают одновременно (слой с
один слот запускает свои блоки по очереди). Установите `CLUSTER_WORKER_BIND` в личный кабинет
адрес, чтобы не допускать работника к другим интерфейсам. `GLM53_VERBOSE=1` на
координатор печатает среднее время ответа каждого работника на выходе; `GLM53_VERBOSE=2`
печатает время ответа каждого работника каждого слоя и время ожидания самого медленного,
числа, по которым можно установить веса.

Чанк предварительного заполнения — это единица чтения с диска для каждого работника: каждый чанк создает
работник снова читает экспертов слоя, поэтому координатор предварительно заполняет рабочих
все промпт одним куском, до 1024 токенов. На двух рабочих SATA-SSD что
предзаполнение из 245 токенов увеличено с 618 до 454 с. Большие куски амортизируют чтения
дальше, но помещайте до 16 КиБ на строку токена в каждом направлении на каждом рабочем сервере,
поэтому значение по умолчанию на этом заканчивается; `GLM53_PREFILL_CHUNK` по-прежнему имеет приоритет, вплоть до
Ограничение одного рабочего запроса в 65536 строк (8192 токена в топ-8).

Ничто в кластере GLM-5.3 не ждет вечно. `GLM53_CLUSTER_TIMEOUT` (секунды,
по умолчанию 120) ограничивает подключение к работнику, каждому сообщению в полете и
ответ работника на запрос слоя: работник, который не отвечает вовремя
завершает координатор на `expert worker HOST:PORT did not answer in N s`, и
клиент, который подключается к работнику, не завершив вовремя рукопожатие
удаляется, поэтому он не может скрыть порт от реального координатора. А
координатор, завершивший рукопожатие, может делать паузу между запросами на
сколько угодно (подача ожидает следующей подсказки); тот, который исчезает
без закрытия обнаруживается службой поддержки активности TCP примерно через два срока. Поднимите
крайний срок для работника, диску которого требуется более двух минут на предзаливку
кусок.

<a id="protocol-v2"></a>
## Протокол v2

Проводной протокол (`COLIEX01` в `c/colibri.c`) имеет две версии. v1,
по умолчанию перемещает необработанные строки f32 и это то, что говорит каждый координатор, если его не об этом просят.
в противном случае кластер смешанных сборок движка продолжает работать. v2 добавляет `act`слово в заголовок и один раз отправляет пакетные строки слоя, при этом каждый эксперт называет свое имя.
строки по индексу, где v1 копирует строку в каждый эксперт, который ее маршрутизирует (по адресу
декодировать с помощью топ-8 одну и ту же строку восемь раз); работник принимает и то, и другое.
координатор использует версию 2 только тогда, когда ему необходимо одно из:

- **Активации q8**, `COLI_CLUSTER_ACT=q8`: каждая строка пересекает провод как int8
  блоки по 32 за одной шкалой f32, в обоих направлениях — примерно в 3,5 раза меньше байтов,
  и не точно по символу (ворота дают ему дрейф, а не сиденье).
- **Общий эксперт по работнику**, `CLUSTER_SHARED=1`: общий доступ к каждому слою.
  эксперт обрабатывает первый маршрутизированный запрос слоя как еще один элемент (каждая строка,
  невзвешенный, в запросе `act`) работнику `layer % n_workers`, который
  загружает три матрицы один раз и сохраняет их (GLM-5.2 при 8-битной плотности: 2,9 ГБ
  по всем слоям). Со строками f32 рабочий выполняет ту же последовательность процессоров FASE E
  выполняется, и координатор добавляет строки в одной и той же точке, поэтому ни токен
  ни один логит-байт не перемещается: `c/tests/test_cluster_sharding.py` содержит то, что выполняется до
  байты логитов локального запуска. По умолчанию выключено.

Что бы работник ни считал, координатор складывает ответы работников в
строку в том порядке, в котором локальный контур добавляет экспертов этой строки (порядок `uniq[]`), и
только после того, как ответил последний работник, так что бег на одного, двух или трех
работники дают байты логитов локального запуска; `c/tests/test_cluster_sharding.py`
придерживается всех троих. Вместо этого добавлялся работник за работником, токены были
то же самое, и последние биты логитов были отключены у двух включенных рабочих.

Всякий раз, когда координатор говорит v2, он сначала отправляет каждому работнику пустой v2.
просьба, здравствуйте. Рабочий, построенный на основе старого движка, замыкается на нем вместо
отвечать, а координатор отказывает этому работнику по имени («экспертный работник
HOST:PORT закрыт на COLIEX01 v2, здравствуйте... пересоберите работника`) перед
генерируя что-либо. Рабочий отказывается от версии или формата активации, которые он делает
не говорить одинаково, на своем собственном stderr. Координатор сообщает об отправленных байтах
и получен на выходе.

Транспорт отключен, если рабочие не настроены, поэтому существующие
путь одной машины остается неизменным. Осколки внимания и плотные
матрицы рабочих процессов и рабочих браузеров/WebGPU являются отдельным продолжением.
швы.

<a id="engines"></a>
## Движки

Протокол (`COLIEX01`) переносится двумя движками, а рабочий обслуживает
семейство, для которого оно было создано — движки никогда не смешиваются в одном координаторе:

- `colibri` (GLM): маршрутизированные эксперты каждого слоя, как указано выше.
- `deepseek_v41` (DeepSeek V4.1 Flash): эксперты по маршрутизации fp4 магистральной сети. А
  рабочий имеет один экспертный слот на каждый слой и работает одинаково `matmul_mxfp4`
  ядро, которое сделал бы координатор, поэтому строка возвращается в виде байтов локального пути
  производит. Маршрутизация, общий эксперт, внимание, индексатор DSA, инграмма.
  столы, обзорная башня и этапы драфта DSpark (собственные, меньшие по размеру).
  экспертный набор) оставайтесь на координаторе.

```bash
./coli cluster worker --model /nvme/dsv41 --port 9100 --advertise-host WORKER_IP
./coli serve --model /nvme/dsv41 --cluster-workers WORKER_IP:9100
```

`c/tests/test_cluster_sharding.py` и `c/tests/test_dsv41_cluster_sharding.py`
являются точными по токену воротами: локальный запуск и делегированный запуск одного и того же двоичного файла
должен декодировать одни и те же токены, а делегированный должен пройти процедуру
рабочий.
