# Собственная установка Windows 11 — полное пошаговое руководство (без WSL)

Полный, воспроизводимый путь от новой машины с Windows 11 до генерации токенов GLM-5.2 на уровне графического процессора. Каждый шаг и каждый приведенный ниже режим сбоя были проверены и проверены на реальном оборудовании: Core Ultra 9 285K (AVX-VNNI) / RTX 5080 (sm_120) / 128 ГБ ОЗУ / Windows 11 24H2 (проблема № 306). Шаги упорядочены, поэтому длительная загрузка выполняется во время сборки.

## 2. Сборка движка (CPU)

Из обычного PowerShell в каталоге репозитория `c\`:

```powershell
make colibri.exe ARCH=native      # ARCH=native unlocks AVX-VNNI on Alder Lake+/Arrow Lake
make iobench.exe              # disk benchmark, useful before committing to the download
```

Предупреждения о `#pragma comment` и неиспользуемых переменных являются нормальными (MSVC-измы gcc игнорирует). Баннер движка должен печатать `idot: avx-vnni` на процессорах с поддержкой VNNI — если там написано avx2, вы построили без `ARCH=native`.

<a id="2-build-the-engine-cpu"></a>
### ⚠️ Smart App Control заблокирует ваш новый двоичный файл

На компьютерах с Windows 11 с включенным **Smart App Control** (`VerifiedAndReputablePolicyState = 1`) запуск самоскомпилированного `colibri.exe` завершается с ошибкой:

```
Program 'colibri.exe' failed to run: An Application Control policy has blocked this file
```

Это не Defender и не Mark-of-the-Web — SAC блокирует *все* неподписанные неизвестные двоичные файлы, включая все, что вы скомпилируете самостоятельно. **Исправление:** Безопасность Windows → Управление приложениями и браузером → Настройки Smart App Control → **Выкл.**, затем **перезагрузка** (политика перезагружается только при перезапуске). Примечание. SAC является односторонним: для повторного включения позже потребуется перезагрузка Windows. Если страница настроек отсутствует, эквивалентом реестра является установка с `HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy\VerifiedAndReputablePolicyState` на `0` (администратор PowerShell), а затем перезагрузка. Прежде чем прикасаться к чему-либо, проверьте свое текущее состояние:

```powershell
(Get-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy").VerifiedAndReputablePolicyState
# 0 = off, 1 = enforced, 2 = evaluation
```

SAC также может заблокировать сам компилятор: сразу после того, как `pacman` установит gcc, свой собственный
`collect2.exe` неизвестен SAC до тех пор, пока не будет получен вердикт по облаку (два часа, #1900),
и gcc только говорит: «Невозможно выполнить «collect2.exe»: CreateProcess: Нет такого файла или
каталог`. Исправление то же (выключение SAC и перезагрузка), либо ожидание вердикта.

## 3. Сборка библиотеки CUDA DLL (уровень графического процессора)

nvcc нуждается в MSVC в качестве хост-компилятора, поэтому этот шаг необходимо выполнить из оболочки со средой MSVC: откройте **"x64 Native Tools Command Prompt for VS 2022"** из меню «Пуск» (обычная PowerShell не пройдет проверку `cl`). Не обычная «Командная строка разработчика»: это 32-битный компилятор, и nvcc затем дает сбой внутри `cuda_fp16.hpp` с `asm operand type size(8) does not match ... constraint 'r'` (#1405). Только `cl` печатает тот, который у вас есть: `for x64` — правильный баннер. Тогда:

> **В командной строке VS нет `sh.exe` (#478):** эта командная строка представляет собой оболочку `cmd.exe`, а в рецепте `cuda-dll` используются идиомы POSIX (`command -v`, `{ ...; }`), для которых требуется `/bin/sh`. Запустите это один раз в командной строке VS перед сборкой:
> ```cmd
> установите PATH=%PATH%;C:\msys64\usr\bin
> ```
> (измените путь, если вы установили MSYS2 в другом месте). Если вы пропустили MSYS2 в пользу w64devkit или выбрали MinGW, укажите это место, где находится `sh.exe`.

```cmd
make cuda-dll CUDA_ARCH=sm_120        # match your GPU: sm_120 Blackwell, sm_89 Ada, ...
make colibri.exe CUDA_DLL=1 ARCH=native   # relink host with the runtime loader
```

Две ловушки, обе исправлены в текущей версии `dev` (#314), но о них стоит знать при использовании старых касс:

- **Пробелы в `CUDA_HOME`** (`C:\Program Files\...`), используемые для нарушения рецепта → исправлено; nvcc теперь происходит из PATH и `"$(NVCC)"` заключен в кавычки.
- **`make colibri.exe CUDA_DLL=1` после сборки только для CPU** используется для сообщения о `up to date` и молчаливом сохранении двоичного файла только для CPU (уровень графического процессора никогда не задействуется, нет ошибок). Текущий `dev` имеет штамп конфигурации сборки, который вызывает перелинковку. На старых деревьях: сначала удалите двоичный файл (`colibri.exe`; `glm.exe` предварительное переименование).

Проверка работоспособности: первый запуск графического процессора должен вывести `[CUDA] device 0: <your GPU>, ... sm_XX` и `[CUDA] mode: routed experts + resident dense tensors`.

<a id="3-build-the-cuda-dll-gpu-tier"></a>
## 4. Первый запуск

```powershell
cd <repo>\c
$env:OMP_NUM_THREADS = "<physical cores>"
python coli run "Explain what a mixture-of-experts model is." --model D:\glm52_i4 --ngen 48
```

Первый запуск холодный — ожидайте, что в профиле будет доминировать `expert-disk`, пока кеш прогревается; процент попаданий возрастает. Уровень графического процессора сверху:

```powershell
$env:COLI_CUDA="1"; $env:COLI_GPU="0"; $env:CUDA_DENSE="1"; $env:CUDA_EXPERT_GB="4"
python coli run "..." --model D:\glm52_i4 --ngen 64
```Размер `CUDA_EXPERT_GB` настолько плотный (~10 ГБ) + эксперты + рабочий набор, что остается под вашей видеопамятью. Примечание. Спекуляция MTP по умолчанию отключена в CUDA (#293, расхождение с плавающей запятой между черновиком и проверкой) — `COLI_CUDA_MTP=1` снова включается.

#### Закрепите набор инструментов MSVC

clang hipcc выбирает **самый новый** установленный набор инструментов MSVC. На машине, которая
также имеется Visual Studio 2026 MSVC **14.51.36231**, `<cmath>`
объявляет встроенные функции сравнения, которые конфликтуют с перегрузками HIP `__device__`, и
бэкэнд не может скомпилироваться. Закрепите набор инструментов для оболочки сборки:

```powershell
$vs2022 = "C:\Program Files\Microsoft Visual Studio\2022\Community"

$env:VCToolsInstallDir  = "$vs2022\VC\Tools\MSVC\14.44.35207\"
```

VS2026 может остаться установленным; это просто не должен быть тот набор инструментов, который выбирает hipcc.

<a id="pin-the-msvc-toolset"></a>
#### Изолируйте устаревший компьютер на уровне `HIP_PATH`

Установщик HIP SDK устанавливает значение `HIP_PATH` для всего компьютера, а на компьютере с более
чем одна установка ROCm/HIP может указать куда-то, чего вы не планировали. Переопределить это
**только внутри оболочки сборки** — не редактируйте общемашинное значение:

```powershell
$env:HIP_PATH = $sdk          # the SDK you actually want, for this shell only
# ROCM_PATH / ROCM_HOME / HIP_DEVICE_LIB_PATH are read by the ROCm toolchain, not
# by Colibri; clear them so a second install cannot redirect headers or bitcode:
Remove-Item env:ROCM_PATH, env:ROCM_HOME, env:HIP_DEVICE_LIB_PATH -EA SilentlyContinue
```

Оболочке сборки также требуется `C:\Windows\System32` на `PATH` (собственные исполняемые файлы
без него вызывается цепочкой инструментов), и записываемый `TMP`/`TEMP`/`TMPDIR`
— clang записывает туда временные файлы и сообщает «невозможно создать временный файл»
когда они не установлены, оболочки MSYS2 обычно оставляют пустыми.

### Настройка среды выполнения

Для работы хоста HIP необходимы две вещи. Оба проверяются перед любым графическим процессором
работа начинается, и все, что невозможно доказать, скорее отключает уровень графического процессора.
чем гадать — движок продолжает идти по пути CPU.

**1. `coli_hip.dll` рядом с `colibri.exe`.** Хост HIP загружает *только*
точный абсолютный путь. Намеренно нет резервного варианта с открытым именем и нет
Поиск System32: запасной вариант может позволить другому `coli_hip.dll` удовлетворить
загрузите и спокойно отмените проверку времени выполнения ниже.

**2. `COLI_HIP_RUNTIME_DIR` имя среды выполнения HIP.** Абсолютный путь к
каталог, содержащий `amdhip64_7.dll`:

```powershell
$env:COLI_HIP_RUNTIME_DIR = "C:\path\to\hip\bin"
$env:COLI_CUDA = "1"
.\colibri.exe
```

Относительный, относительно диска (`C:runtime`) и корневой без диска (`\runtime`)
значения отклоняются, поскольку их разрешение относительно текущего каталога
именно для устранения этой двусмысленности и существует настройка. Пробелы, не ASCII
символы и конечный разделитель в порядке.

Почему это обязательно: Windows разрешает импорт DLL по **базовому имени**
все, что уже загружено, и машина может легко перевозить более одного
`amdhip64_7.dll` (общесистемная установка ROCm плюс все, что вы распаковали). Левый
по случайности бэкэнд привязывается к тому, который загрузился первым. Итак,
загрузчик отказывается запускать уровень графического процессора, когда обнаруживает:

- уже загружен **другой** `amdhip64_7.dll`, отличный от настроенного
- **загружено более одного** `amdhip64_7.dll`, даже если один из них правильный
  файл — к какому модулю привязывается импорт, определяется порядком загрузки
- список загруженных модулей, которые он не мог прочитать, или файл, личность которого он мог
  не устанавливать

Файлы сравниваются по **физическому идентификатору**, а не по тексту пути, поэтому
настроенная среда выполнения через жесткую ссылку или путь с другим написанием
принято.

Одно ограничение указано прямо: среда выполнения проверяется *после* ее сопоставления.
`LoadLibraryExW` принимает путь, а не открытый дескриптор, поэтому файл заменен
между проверкой и загрузкой **обнаруживается, но не предотвращается**. Длинные пути
за пределами `MAX_PATH` больше не попадают в фиксированный буфер в загрузчике, но будут ли они
работа по-прежнему зависит от вашего манифеста процесса и политики Windows, и это имеет
здесь не проверялось на аппаратном обеспечении.

**CUDA не затрагивается.** Хост `CUDA_DLL=1` игнорирует `COLI_HIP_RUNTIME_DIR`.
полностью и сохраняет существующее поведение поиска `coli_cuda.dll` без изменений.### Как `coli plan` и `coli doctor` видят графический процессор AMD здесь

<a id="runtime-setup"></a>
#### Сообщается, но не запланировано — и почему

`hipInfo` сообщает имя устройства, `gcnArchName`, `isIntegrated` и **оба**
`memInfo.total` и `memInfo.free`. Colibri записывает личность, маркирует
`isIntegrated: 1` как единая память и принимает общее количество.

Он намеренно **не** использует `memInfo.free` в качестве бюджета размещения, потому что
на этом оборудовании эта цифра не была квалифицирована как таковая.

Настройка прошивки Armory Crate на проверенном хосте предоставляет
*предел общей памяти*. Четыре контролируемых наблюдения, каждое по-своему
перезагрузил сеанс, все остальное осталось неизменным, выдал:

| Ограничение общей памяти Armoury Crate | `memInfo.total` | `memInfo.free` | Окна видны |
|---|---|---|---|
| ~6 ГБ (минимум пользовательского интерфейса) | 76,79 ГиБ | 76,63 ГиБ | 127,15 ГиБ |
| ~32 ГБ | 76,79 ГиБ | 76,63 ГиБ | 127,15 ГиБ |
| ~64 ГБ | 76,79 ГиБ | 76,63 ГиБ | 127,15 ГиБ |
| ~123 ГБ (максимум пользовательского интерфейса) | 93,00 ГиБ | 92,84 ГиБ | 127,15 ГиБ |

Три настройки, охватывающие двадцатикратный диапазон, дали одинаковые показания; только
максимум отличался. При минимуме ~6 ГБ заявленное общее количество составило примерно **12,8×.
настроенный лимит**. Видимая Windows физическая память не изменилась во всех
четыре прогона, как и выделенный буфер кадров емкостью 0,50 ГиБ, о котором сообщает драйвер.

Таким образом, сообщаемая цифра не является простой функцией настройки, и нет
Здесь предполагается сопоставление слайдера с памятью HIP. И это не выделенная видеопамять: на
интегрированная часть: графический процессор и хост используют один физический пул, и какая часть
то, что рекламирует HIP, на самом деле можно потратить (и сколько это будет стоить хосту)
не измерялось. Определение экспертного уровня на основе этого было бы предположением.

Таким образом, такое устройство рассматривается как **только удостоверение**: свободная память
*неизвестно для планирования*, что не то же самое, что «ноль байтов свободен».
`coli plan`
показывает его с пометкой `(identity only)`, с предупреждением о его названии и:

- уровень VRAM остается на уровне 0
- не рекомендуется использовать `CUDA_EXPERT_GB`, `PIN_GB`, `COLI_GPU` или `COLI_CUDA`
- `COLI_CUDA_PIPE` не включен- узкое место классифицируется точно так же, как и на хосте только с CPU.

Отсутствующее значение также не заменяется никаким значением системного ОЗУ; ничего нет
изготавливается вместо измерения.

Ничто из этого не мешает вам работать на графическом процессоре. Каждая переменная среды
в этом документе по-прежнему работает точно так, как описано — это регулирует только то, что
Colibri включится *самостоятельно*. Квалификация безопасного автоматического бюджета на общих
память нуждается в измерениях распределения на реальном оборудовании, и это намеренно
оставить на более позднее изменение, а не предполагать здесь.

Дискретная карта Windows AMD имеет маркировку `unified_memory: false` от
`isIntegrated: 0`, но на данный момент также используется только как идентификатор: нет
дискретный хост Windows AMD в этом наборе проверки, и то же предположение будет
там такой же неквалифицированный.

<a id="how-coli-plan-and-coli-doctor-see-an-amd-gpu-here"></a>
### Размещаем тензоры модели на GPU — и проверяем, что это произошло

`COLI_CUDA=1` инициализирует серверную часть. Он **не** сам по себе не помещает ни одного
модельный тензор на графическом процессоре. Добавьте `CUDA_DENSE=1`, чтобы плотные тензоры были приемлемыми:

```powershell
$env:COLI_CUDA  = "1"
$env:COLI_GPU   = "0"
$env:CUDA_DENSE = "1"
$env:COLI_HIP_RUNTIME_DIR = "$sdk\bin"
.\colibri.exe 64 16 16
```

В этой конфигурации перенаправленные эксперты остаются на **CPU**. Они становятся пригодными для использования с графическим процессором
только посредством существующих механизмов контроля за размещением экспертов (`CUDA_EXPERT_GB` вместе
с помощью PIN-кода или источника использования); эта комбинация не была проверена в Windows
ХИП.

**Проверьте резидентность — строка устройства не является доказательством.** Можно распечатать серию.

```
[CUDA] device 0: AMD Radeon(TM) 8060S Graphics, 84.0 GB VRAM, sm_115
```

и при этом выполнять каждый тензор на CPU. Строка, которая устанавливает это, печатается
в конце пробега:

```
[CUDA] resident set: 46 tensors, 0.00 GB VRAM
```

`N = 0` означает, что **ни один тензор модели не находился в графическом процессоре**, хотя
устройство было обнаружено — обычная причина — `CUDA_DENSE` не устанавливается. лечить
`resident set: N tensors` с `N > 0` в качестве доказательства и проверяйте его каждый раз.
(Цифра `GB` округляется до 1e9, поэтому на маленькой модели законно отображается `0.00 GB`.
наряду с ненулевым числом тензоров.)

**Откат CPU обеспечивает успешность выполнения команды.** Если тензор не удается загрузить,
Движок регистрирует это, перемещает этот тензор в CPU и продолжает работу; процесс все еще
выходит из 0, и числа остаются правильными. Вы получаете строку на тензор для первого
несколько, уведомление об эскалации, если несколько из них не удалось, и окончательный подсчет:

```
[CUDA] N tensors ran on CPU after failed uploads: this run did NOT use the GPU for them.
```

Прочтите их вместе с резидентным набором — запуск может *частично* выполняться на графическом процессоре.

**Жизненный цикл.** Обычные однократные выходы из модели основаны на **Разборке процесса Windows**
освободить серверную часть и среду выполнения HIP; `coli_cuda_shutdown` не вызывается
на обычных путях выхода из-под принуждения учителя или декодирования. Это соответствует существующему
Поведение хоста Windows CUDA безопасно для однократного использования CLI — это процесс
демонтаж, а не явное отключение серверной части.

### Генерация синтетической модели оракула GLM

Чтобы протестировать весь движок, вам нужна модель *a*, самая маленькая из них —
генерируется локально, а не загружается. `c/tools/make_glm_oracle.py` сборки
**`glm_tiny`** — GLM-5.2 (`glm_moe_dsa`) ~0,6 МБ (`glm_moe_dsa`) с реальной архитектурой
(MLA + индексатор DSA + сигмовидный маршрутизатор + общий эксперт, 5 уровней, 8 маршрутизируемых экспертов,
top-2), но случайные веса плюс `ref_glm.json`, оракул, заставляющий учителей
ожидаемые идентификаторы токенов.

> **Это инструмент тестирования, а не языковая модель.** Случайные веса дают
> бессмысленный текст. Его единственная цель состоит в том, что движок C должен воспроизводить
> точно ссылайтесь на идентификаторы токенов.

Приведенные ниже пакеты представляют собой **только инструменты разработки** — сам движок написан на языке C.
двоичный и не требует использования Python, если файлы модели существуют.

**1. Создайте изолированную среду.** В масштабе всей системы ничего не устанавливается:

```powershell
$tooling = "$env:USERPROFILE\colibri-oracle-tooling"   # anywhere outside the repo
uv venv --python "$env:LOCALAPPDATA\Programs\Python\Python314\python.exe" "$tooling\venv"

# CPU-only Torch from the official PyTorch CPU index; the rest from PyPI
uv pip install --python "$tooling\venv\Scripts\python.exe" `
    --index-url https://download.pytorch.org/whl/cpu `
    --extra-index-url https://pypi.org/simple `
    --index-strategy unsafe-best-match `
    torch "transformers==5.11.0" "safetensors>=0.4"
```

Проверено на **CPython 3.14.6 (Windows x64)** с **torch 2.13.0+процессор**,
**трансформаторы 5.11.0** и **безопасные тензоры 0.8.0**. `transformers>=5.11` — это
твердый пол — генератор выходит под ним, поскольку применяются более старые версии
разделить пополам Llama RoPE и тихо издать оракул, с которым движок не может сравниться
(выпуск №281). Пин 5.11.0 именно так, чтобы избежать дрейфа оракула.

**2. Проверьте среду** (только импорт — ничего не строит, ничего не загружает):

```powershell
& "$tooling\venv\Scripts\python.exe" -c "import torch, transformers; from transformers import GlmMoeDsaConfig, GlmMoeDsaForCausalLM; print(torch.__version__, torch.version.cuda, transformers.__version__)"
```

Ожидайте сборку `+cpu` Torch и `None` для версии CUDA.

**3. Сгенерировать модель — из внешнего рабочего каталога.** Генератор
не принимает `--outdir`: пишет `glm_tiny/` **и** `ref_glm.json` относительно
текущий каталог. `c/ref_glm.json` — это отслеживаемый файл, поэтому он генерируется внутри `c/`
перезаписал бы его. Вместо этого запустите его извне репозитория:

```powershell
$repo = "<your colibri checkout>"       # e.g. "$env:USERPROFILE\src\colibri"
$out  = "$tooling\model"
New-Item -ItemType Directory -Force -Path $out | Out-Null
Push-Location $out
& "$tooling\venv\Scripts\python.exe" "$repo\c\tools\make_glm_oracle.py"
Pop-Location
# -> $out\glm_tiny\{config.json,model.safetensors} and $out\ref_glm.json
```

Генерация полностью автономна после установки пакетов: модель построена.
из буквальной конфигурации с фиксированным начальным значением, и из сети ничего не извлекается.

**4. Запустите движок против него.** `SNAP` и `REF` оба принимают внешние пути,
поэтому сгенерированные файлы никогда не должны попадать в репозиторий:

```powershell
$env:SNAP = "$out\glm_tiny"
$env:REF  = "$out\ref_glm.json"
$env:TF   = "1"
.\colibri.exe 64 16 16
```

`TF=1` — это самопроверка, требующая учителя: она печатает
`PREFILL (teacher-forcing) C vs oracle: N/32 positions` и один
`[ORACLE] mismatch pos=… expected=… got=…` строка за несогласие. Добавить
`DEBUG_LOGITS=1`, чтобы сбросить первые 5 логитов при несоответствии. Плавающая точка
близкие связи зависят от инструментальной цепочки, поэтому ожидается небольшой дефицит; сравнить
Графический процессор работает с процессором, работающим на той же машине, а не с фиксированным
номер.

Чтобы вместо этого использовать серверную часть HIP, добавьте настройки времени выполнения из
[Настройка времени выполнения](#runtime-setup-experimental-developer-facing) то же самое
команда.

**Очистка** удаляет инструмент и созданную модель за один шаг; тот
репозиторий нетронут:

```powershell
Remove-Item -Recurse -Force $tooling
```

## Экспертное упреждающее чтение

Экспертное упреждающее чтение использует ограниченную очередь пула потоков Windows. Подсказка `WILLNEED`
возвращается без чтения эксперта в потоке вывода, даже если файл
был открыт синхронно. Рабочий процесс предварительно выбирает сопоставление файлов только для чтения;
второй, временной копии эксперта нет. Не более четырех подсказок на движок
единица перевода находится на рассмотрении, каждое окно ограничено 64 МБ. Лишние подсказки,
недоступные API и неудачные сопоставления безопасно пропускаются; обычная модель читает
еще поставлю гири. Это относится к общему пути к файлам, используемому
процессоров и графических процессоров и не меняет их весовые форматы или арифметику.

<a id="amd-failure-index"></a>
## Эксперт читает

Осколок открывается один раз, и каждый поток читает этот дескриптор. Дескриптор
из среды выполнения C `open()` является синхронным дескриптором, и Windows обслуживает один
читать через него за раз, независимо от количества потоков, поэтому каждый осколок также получает
второй дескриптор открывается с помощью `FILE_FLAG_OVERLAPPED`. Читатель, который находит
Shard free считывает первый дескриптор, как и раньше; читатель, который находит
было выполнено чтение до второго, где любое количество чтений находится в процессе
вместе. `pread` по-прежнему является блокирующим вызовом; он ждет своего чтения. Если
второй дескриптор не может быть открыт, осколок сохраняет тот, который у него есть, и его
операции чтения сериализуются, а не отклоняются. Это меняется, когда байты
читать, никогда не какие байты.
