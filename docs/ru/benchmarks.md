оборудование здесь не указано, **пожалуйста, откройте проблему, указав свои номера** — реально

<a id="reference-numbers-the-original-dev-box-wsl2-12-cores-25-gb-ram-nvme-via-vhdx"></a>
## Справочные номера (исходная коробка разработчика: WSL2, 12 ядер, 25 ГБ ОЗУ, NVMe через VHDX)

Подробный эксперимент с графическим процессором: [GLM-5.2 на 6× RTX 5090](experiments/glm52-6x5090-2026-07-12.md) —
полная экспертная резидентность VRAM+RAM достигает **6,84tok/s** декодирования с одним запросом.

| метрика | ценность |
|---|---|
| модель на диске (контейнер int4) | ~370 ГБ |
| резидентное ОЗУ (плотное, int4) | 9,9 ГБ |
| время загрузки | ~30 с |
| пик RSS во время чата | ~20 ГБ (ограничено автоматически) |
| стоимость холодного декодирования | ~11 ГБ операций чтения с диска/токенов (75 слоев × 8 экспертов) |
| потолок диска (дисковод этого разработчика) | ~1 ГБ/с → ~0,05–0,1 tok/s холодный |
| Спекуляция MTP (головка int8) | 2,2–2,8 ток/вперед измерено ([#8](https://github.com/Developer3000S/colibri-rus/issues/8)) |

Это не быстро. Это модель 744B пограничного класса, **правильно отвечающая на
машина, которая стоит меньше одного вентилятора H100**. Теплый кэш, закрепленные горячие эксперты и
MTP значительно снижает задержку полезного ответа; физика диска
делает все остальное.

<a id="ssd-note"></a>
### Примечание о SSD

Холодный запуск требует большого количества случайных операций чтения (~ 11 ГБ/токен), но операций чтения нет.
разумно носить SSD — потоковая передача colibrì доступна только для чтения. Реальные проблемы
при интенсивном использовании: (1) **трафик подкачки**, если в системе заканчивается оперативная память (записывает
носите диск — сохраняйте вменяемый бюджет `--ram`; Автобюджет colibrì рассчитан
чтобы избежать подмены) и (2) **устойчивые температурные условия**: часы при полном чтении
цикл будет нагревать более дешевые диски. Следите за температурой и состоянием накопителя.

<a id="test-your-machine-in-order"></a>
## Проверьте свою машину по порядку

```bash
cd c && ./setup.sh                 # build + architecture self-test (expects ~30-32/32)

# 1) measure YOUR disk the way the engine uses it (parallel 19 MB random reads):
gcc -O2 -fopenmp iobench.c -o iobench
./iobench /path/to/glm52_i4/out-00069.safetensors 19 64 8 0   # buffered, 8 threads
./iobench /path/to/glm52_i4/out-00069.safetensors 19 64 8 1   # O_DIRECT (bypass cache)
# Caveat (#86): iobench reads a bounded ~1 GB shard, so buffered reads on a big-RAM box
# report the PAGE CACHE, not the disk. Use the O_DIRECT run (arg 1) for a true number, and
# run it on a shard you haven't touched this session (a prior buffered run caches its pages).
# On macOS there is no O_DIRECT — iobench uses F_NOCACHE, which stops *new* caching but can't
# evict pages a prior buffered run already resident-mapped, so a macOS "O_DIRECT" figure right
# after a buffered run still reads cache. Reboot or use a fresh shard for a real cold read.

# 2) chat; watch the per-turn stats line (tok/s, expert hit-rate, RSS):
COLI_MODEL=/path/to/glm52_i4 ./coli chat

# 3) full automated datapoint — machine info + cold/warm decode + disk, one command:
python tools/datapoint.py --snap /path/to/model --shard /path/to/container/model-00000.safetensors
# (stdlib-only; auto-selects GLM, Inkling, Kimi K3, OLMoE, Qwen3.8, Qwen3.6, or DeepSeek V4
#  from config.json; evicts the page cache before engine load; then keeps one
#  SERVE=1 engine alive for cold, warm-identical, and rotating-prompt measurements)

# 4) record expert usage, then pin the hottest experts in your spare RAM:
STATS=stats.txt ./coli chat
PIN=stats.txt PIN_GB=20 ./coli chat        # scale PIN_GB to your free RAM

# 5) quality benchmarks (MMLU/HellaSwag/ARC):
./coli bench
```

**Точка данных серверной части графического процессора нуждается в строке корректности рядом с ее пропускной способностью.**
Пропускная способность не может отличить неправильный сервер от быстрого: ядро, которое вычисляет
мусор работает на полной скорости и не сообщает об ошибках. Измерено в #1502 на gfx1151,
HIP сборка выдала недоумение 727 против 7.0 для той же модели на том же
машина, идентичная tok/s, и только проверка качества выявила это. Итак, для любой строки
снято с включенными CUDA, HIP, Metal или Vulkan, запишите одно из: a `./coli bench`
оценка в шуме работы процессора, недоумение по фиксированному тексту рядом с процессором
цифру или жадный выходной байт, идентичный пути CPU в том же промпте.
последний справедлив только в том случае, если устройство и процессор выполняют одну и ту же арифметику: графический процессор
пути умножают активации f32, а несколько значений по умолчанию CPU округляют активации до int8
первый (плотное и экспертное ядра Qwen3.6, ствол int8 Qwen3.8, эксперты Kimi K3;
docs/vulkan.md, «Арифметика»). В них жадные токены могут отделиться от процессора.
после нескольких шагов, а на экспертном уровне Vulkan они также могут различаться от запуска к
беги (docs/vulkan.md, "Беги, чтобы бежать"), так что счет или недоумение - это проверка
там (#2081). Строка без нее — это заявление о скорости, а не точка данных.

Точка данных по умолчанию измеряет поведение обслуживания, а не повторный запуск: то же самое
Процесс механизма и слот кэша используются для одного холодного запроса, одного повторного запроса
теплый запрос и четыре запроса, полученные в фиксированном порядке из различных встроенных
подскажите люкс. **Медиана подсказки о вращении является основным результатом**, поскольку
Экспертный кэш должен постоянно адаптироваться по мере изменения запросов. Теплые идентичности остаются вотчет только как полезная верхняя граница кэша/KV; это не представитель
смешанная нагрузка в чате. Сообщенное количество завершенных операций, декодирование tok/s, попадание эксперта
скорость, а RSS исходят из `DONE` кадра каждого механизма.

Используйте повторяющиеся аргументы `--rotate-prompt '...'` для замены встроенного пакета.
(минимум два разных запроса) или `--rotating-runs N` для запуска более фиксированного порядка
образцы. Используйте `--mode fresh-process` только при измерении кэша страниц запуска или ОС.
эффекты; этот режим совместимости запускает новый механизм для каждой строки и
поэтому не сохраняет внутрипроцессные кэши.

<a id="back-of-envelope-predictions"></a>
## Прогнозы на обратной стороне конверта

Декодирование привязано к диску: холодный токен стоит ~11,4 ГБ экспертного чтения; MTP
спекуляции примерно вдвое уменьшают эффективную стоимость *после того, как кэш прогреется*; ОЗУ
превращает холодное чтение в бесплатные обращения к кэшу.

| машина | ожидается |
|---|---|
| блок разработчика (WSL2 VHDX, ~1 ГБ/с, 25 ГБ ОЗУ) | ~0,05–0,1 tok/s холод — проверенный базовый уровень |
| собственный Linux, PCIe4 NVMe (~3–5 ГБ/с в произвольном порядке), 32 ГБ | ~0,5–1 tok/s |
| PCIe5 NVMe или 2×NVMe RAID0 (~8–12 ГБ/с), 64 ГБ (PIN-код ~40 ГБ горячих экспертов) | ~2–4 tok/s |
| 128–256 ГБ ОЗУ, 12 ядер (горячие эксперты кэшируются) | ~2–4 tok/s — привязка к matmul: ~80 GFLOP/токен против ~250 GFLOP/с наших ядер AVX2 |
| та же оперативная память + 24–32 ядра или ядра AVX-512/VNNI | ~5–15 tok/s — интерактивный; работа ядра является множителем |

Это оценки, а не измерения.

### GLM-5.3-Flash Metal экспертная очистка кэша — Apple M4 Max

Декодирование 512 токенов на Apple Mac Studio с M4 Max и унифицированным хранилищем 128 ГБ.
память измеряла эффект экспертного кэша GLM-5.3-Flash `--cap`, в то время как
сохраняя остальную часть рабочей нагрузки фиксированной. Модель была GLM-5.3-Flash Colibri.
int4-g64 с включенным путем Metal Routed-MoE, `--ram 96`, `--ctx 8192`,
и зеркало модели с двумя твердотельными накопителями, маршрутизация 60/40 (`COLI_DISK_WEIGHTS=3,2`).
Сохранение истории использования было отключено для изолированных запусков тестов.

| `--cap` | резидентный экспертный кэш | декодировать | Металлические попытки МО | Резервный процессор |
|---:|---:|---:|---:|---:|
| 4 | 2,4 ГБ | 1.850 tok/s | 24 533 | 0 |
| **8** | **4,8 ГБ** | **1,895 tok/s** | **24 533** | **0** |
| 12 | 7,1 ГБ | 1,887 tok/s | 24 533 | 0 |

примерно на 2,4% быстрее, чем вариант 4, при этом используется значительно меньше экспертов-резидентов
кэша, чем cap 12. Cap 12 был примерно на 0,4% медленнее, чем cap 8, несмотря на то, что он использовал примерно
Еще 2,3 ГБ резидентного кэша. Все три рейса завершены
выполнения с нулевым откатом CPU.

Это результат, зависящий от рабочей нагрузки, а не универсальная рекомендация по ограничению. короче

### Две точки данных, которые не являются строками

**16 ГБ — это меньше минимального значения для больших моделей** ([#923](https://github.com/Developer3000S/colibri-rus/issues/923)):
i5-12450H с 16 ГБ DDR5 и диском QLC без DRAM собирает и проходит
самопроверка в родной Windows, но номер декодирования для отчета отсутствует, поскольку
холодному токену требуется около 11 ГБ экспертного чтения, а ограничение оперативной памяти почти ничего не оставляет
житель. На машинах такого размера запускайте OLMoE или Qwen3.6 вместо GLM-5.2:
Строка M3 выше имеет унифицированный размер 16 ГБ и достигает 3,69–4,18 tok/s на OLMoE.

**Больше экспертного кэша не всегда быстрее, если модель является резидентной, но у вас есть
измерять попарно.** На полностью резидентном OLMoE весь контейнер емкостью 7 ГБ находится в
кэш страниц, поэтому промах — это memcpy, а не чтение устройства, и дополнительное
вид на жительство, который покупает более крупный капитал, должен окупать себя ни за что. Это не так:
кэп 32 превосходит кэп 64 в **7 из 8 чередующихся пар**, медиана 19,1 против 16,3 tok/s,
занимает половину резидентной площади (3,1 ГБ экспертных плит против 6,1 ГБ на 24 ГБ
машина).

Спаривание не является формальностью, и первая версия этой заметки была ошибочной.
без этого. Непарные развертки на этом узле разошлись между собой по поводу знака:
одна зачистка с пятью ранами вывела кепку на 64 вперед по медиане (14,96 против 14,32), а более поздняя - с десятью ранами.
блок поставил кэп 32 вперед на 35% (18,21 против 13,45), а только кэп 32 колебался в пределах 13,97.

сеансов, чем измеряемый эффект, поэтому решается только чередование одного и того же сеанса.
это — дисциплина [журнал ошибок декодирования](experiments/glm52-decode-failure-ledger-2026-07-31.md)

с одного заказанного прохода получается то, что машина чувствовала в тот час.

Относится к [#1050](https://github.com/Developer3000S/colibri-rus/issues/1050), но не кта же форма: срок бухгалтерского учета в этом отчете `miss_rate × cap` *самый низкий* и составляет 64
и поэтому предсказывает 64-й результат, что в данном случае противоположно парному результату.
Сканирование O(cap) предположительно реально на этом хосте; на этом что-то масштабируется
с видом на жительство доминирует над этим.

**Разделение осколков на уровне файла не заменяет зеркальный путь.** +5,5 %
в разделенной строке 12900K и **+37,5%** в
[#1249](https://github.com/Developer3000S/colibri-rus/issues/1249) — оба NVMe
приводы на независимых контроллерах, а разрыв между ними и есть механизм,
не аппаратное обеспечение. Разделение *целых осколков* на два монтирования только с помощью символических ссылок
распараллеливает чтения, которые уже выполняются одновременно, и декодирует в этом блоке, находящемся в
глубина очереди ~1 при загрузке диска 24-28% - перекрываться было нечему.
Распределение на уровне блоков и собственное взвешенное зеркало движка параллельны *внутри*
каждые 19 МБ чтения, и именно в этом заключается реальный фактор. Записано, потому что
отрицательный — это полезная половина: он оценивает разницу между разделением файлов
и чередование блоков примерно на уровне 5% против 37%.

<a id="takeaways"></a>
### Еда на вынос

При наличии 24 ГБ ОЗУ движок автоматически ограничивает экспертный кэш до 2 слотов на слой, поэтому
декодирование остается холодным даже на быстром диске — **на машинах с малым объемом оперативной памяти ограничение ОЗУ, а не
диск — ограничение привязки**; Только `--topp 0.7` купил чистый 1.6×
сквозное ускорение. Пара 9950X — самый чистый эксперимент с узким местом: то же самое
машина, та же история, только диск поменян — ×5,8, пропускная способность диска куплена ×2,9
токенов, а профиль **перевернулся с 66% диска на 57% матмула**. Но
кроссовер зависит от ядра CPU: при включенной настройке OMP hot-team CPU AVX-512
может соответствовать RTX 5090 на экспертном матмуле ([#101](https://github.com/Developer3000S/colibri-rus/issues/101)),
поэтому **уровень графического процессора получает свою видеопамять только тогда, когда процессор является слабым звеном**.
Пара M1 Ultra ↔ M5 Max Metal — тот же урок, что и Apple Silicon: почти равные
Количество ядер графического процессора (48 против 40), но −33% tok/s (1,50 против 2,24), поскольку 57%
Стена декодирования M1 Ultra — это ожидание последовательного SSD при ~ 93% измеренного значения накопителя.
потолок — ** когда эксперты выполняют потоковую передачу с диска, диск, а не графический процессор, устанавливает
ставка**. На хостах с несколькими сокетами размещение NUMA является дополнительным рычагом:
чередование резидентных весов между измеренными узлами **+13 % (2-процессорный процессор) и +40 % (4-процессорный процессор только)**
([#82](https://github.com/Developer3000S/colibri-rus/issues/82)). На двухпроцессорном процессоре Xeon Silver
Хост 4510 с 6 × RTX 5090, выборочный `COLI_NUMA=1` повышенный эффективный процессор
пропускная способность от **42,42 до 58,26/65,89 ГБ/с** и жадное декодирование от **7,66 до
9.02/9.17 tok/s** (64 токена, `TEMP=0 DRAFT=0`, байтовый вывод). Не
полное чередование хоста графического процессора: он также распределяет промежуточные страницы DMA и измеряет

Три урока из данных 2026–2008 годов. **Вторая поездка на независимом
контроллер — это реальная пропускная способность**: пара Threadripper показала +37,5 % от
добавление одного, и прирост более чем удваивается при `DIRECT=1`, потому что буферизованный
операции чтения тратят полосу пропускания второго контроллера на пополнение страничного кэша движкане требуется ([#1249](https://github.com/Developer3000S/colibri-rus/issues/1249)). Это

Процессоры, которые ядра связывают раньше, чем диск**: запуск Zen 3 DeepSeek V4 Flash

([#1119](https://github.com/Developer3000S/colibri-rus/issues/1119)), что является
противоположность машинам с маленькой оперативной памятью, указанным выше, и говорит, что ядра AVX-512 находятся там, где
скорость этой коробки. И **настройки в Apple важнее, чем оборудование.
Кремний**: M5 Max увеличился 0,4 → 2,0, а M1 Max 0,13 → 0,61 при идентичных
выходной сигнал, при *большем* `--ram` измерении постоянно медленнее на M1
([#387](https://github.com/Developer3000S/colibri-rus/issues/387),
[#1030](https://github.com/Developer3000S/colibri-rus/issues/1030)).
