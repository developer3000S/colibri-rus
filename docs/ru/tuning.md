## Самые важные ручки

| ручка | что он делает |
|---|---|

| `RAM_GB=<n>` | требуют больше оперативной памяти для экспертного кэша, чем для консервативного автоматического обнаружения |
| `PIN=stats PIN_GB=g` | определите самых популярных экспертов по измеренному профилю использования |
| `DRAFT=n` | Глубина проекта MTP (0 отключает спекуляции) |
| `GRAMMAR=g.gbnf` | грамматические черновики для ограниченного вывода JSON/NDJSON ([docs](grammar-draft.md)) |
| `THINK=1` | включить блок рассуждений GLM-5.2 |
| `PILOT=1` | предварительная выборка диска с предварительным просмотром маршрутизатора (см. ниже) |
| `URING=1` | Пакетный экспертный ввод-вывод только для Linux (подразумевается `PIPE=1`) |
| `PIPE=0` | отключить асинхронный пул экспертной нагрузки (по умолчанию включено — перекрывается `pread` с matmul, дисковым сервисом −18%) |
| `DIRECT=1` | Экспертные показания O_DIRECT (измерение **+65%** только на Strix Halo, [#200](https://github.com/JustVugg/colibri/issues/200)) |
| `COLI_NUMA=1` | чередование резидентных весов между узлами NUMA на хостах с несколькими сокетами ([#82](https://github.com/JustVugg/colibri/issues/82)) |
| `CACHE_ROUTE=1` | маршрутизация максимального ранга с учетом кэша (согласие, [#199](https://github.com/JustVugg/colibri/issues/199)) |
| `AUTOPIN=0` | отключить автозакрепление кэша обучения |
| `CAP_RAISE=0` | не увеличивайте автоматически экспертный кэш |
| `KVSAVE=0` | отключить сохранение KV-кэша |
| `TF=1` | проверка, принуждающая учителя |

Автоматическое закрепление истории и адаптивный LRU используют одну и ту же экспертную оперативную память.
бюджет. Colibri автоматическое закрепление колпачков для сохранения емкости LRU без выводов;
явные настройки `PIN` и `PIN_GB` остаются авторитетными.

<a id="hybrid-cudacpu-openmp-override"></a>
### Гибридное переопределение OpenMP CUDA/CPU

Основной движок GLM намеренно пропускает настройку OpenMP с активным ожиданием, когда
`COLI_CUDA` установлено. Активные рабочие команды измеряли серьезные регрессии по
борьба с диспетчеризацией и синхронизацией CUDA, поэтому модель CUDA, которая все еще
маршрутизация некоторых экспертов через ОЗУ сама по себе не является причиной менять это
по умолчанию.

На конкретном гибридном хосте, где профилирование показывает окно эксперта по CPU на
критический путь, поддерживаемый эксперимент — это OpenMP, явно принадлежащий пользователю.
политика:

```bash
OMP_WAIT_POLICY=active GOMP_SPINCOUNT=200000 KMP_BLOCKTIME=200 \
OMP_PROC_BIND=close OMP_DYNAMIC=FALSE \
COLI_CUDA=1 ./coli run --model /models/glm52_i4 "Benchmark prompt"
```

Среда выполнения OpenMP считывает эти переменные до `main()`, поэтому их необходимо установить.
при вызове механизма, а не экспортируется после запуска. В движке используется
`overwrite=0`; явные ценности остаются авторитетными. `GOMP_SPINCOUNT` применяется
в libgomp и `KMP_BLOCKTIME` в среду выполнения Intel/LLVM OpenMP, поэтому переносите оба
сохраняет команду переносимой в распространенных сборках.

Считайте это измеренным переопределением для каждого хоста, а не рекомендуемым значением по умолчанию CUDA.
Сравните ее с неизмененной командой со стабильным состоянием страничного кэша ичередующийся порядок выполнения; сообщать экспертное время процессора, критическое время графического процессора, ожидание диска,
и сквозная пропускная способность. Отклоните его, если время графического процессора увеличивается или окно процессора было
уже скрыт за графическим процессором. Не используйте активное ожидание на Apple Silicon: CPU
В этом случае спин работал медленнее из-за кражи общего бюджета мощности CPU/ГП.
`COLI_NO_OMP_TUNE=1` остается явным выключателем пассивной политики.


<a id="measured-machine-profiles"></a>
## Измеренные профили машины

`coli plan` выбирает безопасную отправную точку с учетом мощности и топологии.
`coli tune` измеряет оставшиеся варианты планирования для фактической модели и
машина, затем сохраняет профиль оборудования/модели/движка:

```bash
coli tune --model /models/glm52_i4
coli run --model /models/glm52_i4 --auto-tier "Explain MoE offloading"
```

GLM генерирует одно продолжение калибровки и принудительно выполняет его для каждого
кандидат. Вместо этого родственные механизмы используют свой общий протокол обслуживания: один
движок остается активным для всех запросов кандидата и детерминированных подсказок
вращаться в фиксированном порядке. Это сохраняет экспертный кэш и измеряет реальную
смешанный чат вместо многократной загрузки одного процесса или обучения кэша
точная подсказка. Жадные результаты сравниваются по каждому запросу для каждого кандидата; любой
дрейф байтов дисквалифицирует изменение планирования.

Ограниченная развертка включает в себя такие регуляторы выполнения, как количество потоков OpenMP, NUMA
размещение, перекрытие ввода-вывода, прямой ввод-вывод, конвейеризация CUDA и эксперт DeepSeek V4
дорожки для погрузчиков. Когда холодные эксперты остаются на диске, он также проверяет 75% и 50%
пособие планировщика на экспертный кэш. Плотные веса, резервирование КВ/рабочего пространства,
и резерв ОС никогда не уменьшаются, и ни один кандидат не может превышать лимит планировщика.
безопасный базовый уровень. GLM/Inkling/OLMoE/Qwen получают измеренное ограничение количества слотов на слой;
V4 получает цельнотехнологический потолок `RAM_GB`; Kimi получает `K3_EXPERT_GB` под
неизменный потолок всего процесса. Развертка никогда не меняет веса,
квантование, решения маршрутизатора, `TOPK`, `TOPP` или выборка. Добавить повторяющиеся
`--rotate-prompt` варианты замены вторичного встроенного запроса рабочей нагрузки.

Кандидат сохраняется только тогда, когда медианная пропускная способность увеличивается как минимум на 3%, в то время как
Показатель попаданий экспертов остается в пределах 0,5 процентных пункта, как сообщает TTFT/p99.
задержка остается в пределах 20% от базового уровня. Затем победитель повторно запускается перед финалом.
базовый уровень; этот вентиль обратного порядка дает базовый уровень оставшегося теплого кэша
преимущество и отвергает дрейф при запуске. В противном случае базовый уровень записывается и нет
применяется переопределение. Сохраненные профили загружаются нажатием `--auto-tier`; `--ram`,
`--cap`, `RAM_GB`, `K3_EXPERT_GB` и другие явные настройки всегда выигрывают. А
победитель ресурса перепроверяется по текущему плану при каждом запуске, поэтому
профиль, измеренный с большим количеством свободной оперативной памяти, позже игнорируется, а не перераспределяется.
Используйте `--no-tune-profile`, чтобы обойти сохраненный профиль.

Профили живут под `$XDG_CONFIG_HOME/colibri/tuning` (обычно
`~/.config/colibri/tuning`) или `%LOCALAPPDATA%\colibri\tuning` в Windows. А
изменение двоичного файла движка, метаданных модели, топологии CPU или инвентаризации графического процессора.
создает новый отпечаток вместо повторного использования устаревших измерений.

Диск — это неизменяемый источник восстановления, а не обычная цель декодирования. Если план
оставляет на диске холодные экспертные байты, скорость зависит от скорости попадания в кэш; качество вывода
нет.

Холодное экспертное чтение может использовать отложенный конвейер: выполняются резидентные эксперты RAM/VRAM.
пока отсутствующие эксперты загружаются в ограниченный фоновый пул ввода-вывода, затем холодный
результаты объединяются до завершения слоя. В пуле задействовано только до `PIPE=1`;`PIPE_WORKERS=n` устанавливает количество рабочих (по умолчанию 8). Профилирование сообщает об обоих дисках
время обслуживания и меньшее время ожидания, видимое на переднем плане, поэтому перекрытие явно.

`--policy balanced` включает размещение в реальном времени без потерь (`REPIN=64`). По безопасному запросу
границ, показатель LFRU для каждого уровня сочетает в себе снижающуюся частоту сеансов с недавними
доступ и заменяет не более четырех достаточно холодно закрепленных экспертов. `--политика
качество` leaves live replacement off by default; `REPIN=0` всегда отключает его.

<a id="the-learning-cache"></a>
## Кэш обучения

Движок записывает, к каким экспертам на самом деле направляется ваше использование (`.coli_usage`
рядом с моделью, обновляется каждый ход) и при запуске автоматически закрепляет
самые горячие в свободной оперативной памяти — colibrì буквально становится быстрее, чем больше вы его используете.
`PIN=auto` выбирает пин-код непосредственно из истории использования в реальном времени.
([#301](https://github.com/JustVugg/colibri/pull/301)).

**Экспертный кэш автоматически подстраивается под размер вашей оперативной памяти** (с 10 июля 2026 г.): движок
*повышает* ограничение LRU, чтобы заполнить ваш бюджет в `--ram`, а не просто снизить его.
Если вы протестировали colibrì до этой даты, повторите тест — ваши цифры были ограничены.

**Адаптация живого уровня** (`--repin N`, подписка): на границах безопасного поворота
затухающая тепловая карта сеанса заменяет холодно закрепленных экспертов на более горячие потоковые передачи
эксперты. Гистерезис 25% и ограничение в четыре свопа предотвращают перегрузку уровня.
Постоянный `.coli_usage` остается долгосрочным сигналом и не затухает.

Формат истории на диске: что происходит, когда один движок передается другому
история движка и чем `PIN=<file>` отличается от `PIN=auto` тем, насколько он
доверяет файлу, документированы в
[routing-telemetry.md](routing-telemetry.md).

<a id="what-a-pin-budget-buys-toolsusage_coveragepy"></a>
### Что можно купить за скромный бюджет (`tools/usage_coverage.py`)

AUTOPIN и уровень CUDA определяют размер вывода в соответствии с объемом свободной памяти. Чтобы увидеть, что
что покупает память, почитайте кривую покрытия истории: доля прошлого эксперта
выборки, которые можно было бы использовать в лучшем закрепленном наборе данного размера.

```bash
cd c
python3 tools/usage_coverage.py <model>/.coli_usage --expert-mb 1.7 --vram-gb 6 --ram-gb 8
```

Он показывает, насколько сконцентрирована маршрутизация (верхние 1/10/30% экспертов, Джини,
эффективное число экспертов), охват списком бюджетов, наименьший бюджет
для 70/80/90%, колено, где лишний ГБ начинают покупать дешевле среднего,
и план VRAM-the-RAM в порядке `pin_load` заполняет их (VRAM меньше
`--reserve-gb`, по умолчанию 2, например `CUDA_RESERVE_GB`). `--min-gain G` отмечает, где
еще один ГБ добавляет меньше, чем G баллов. `--expert-mb` — размер одного маршрутизируемого
эксперт; без этого бюджеты приводятся в процентах от экспертов.

В поставляемом профиле Qwen3.6 (`profiles/qwen36-35b.coli_usage`, 1,7 МБ на
эксперт int4):

| закреплен | эксперты | покрытие |
|---:|---:|---:|
| 1 ГБ | 5,7% | 23,4% |
| 2 ГБ | 11,5% | 37,4% |
| 4 ГБ | 23,0% | 56,6% |
| 6 ГБ | 34,5% | 70,2% |
| 8 ГБ | 45,9% | 80,5% |

Охват измеряется историей, на основе которой он был построен, поэтому он завышает то, что
тот же контакт служит для новых подсказок. `--holdout <files>` оценивает рейтинг
другие истории: поставляемый профиль Qwen3.8 покрывает 70% собственных выборов
с 26% экспертов, но те же эксперты охватывают 57,7% отдельного Qwen3.8
сеанс (`docs/experiments/vulkan-qwen38-mtp-2026-10-05/history.usage.gz`).
Охват также является нижней границей показателя попадания, поскольку LRU обслуживает часть
остальное. Модели без горячих экспертов (OLMoE,
[#864](https://github.com/JustVugg/colibri/issues/864)) появляются как почти
прямая кривая.

<a id="router-lookahead-prefetch-pilot1-experimental"></a>
## Предварительная выборка с предварительным просмотром маршрутизатора (`PILOT=1`, экспериментальная)

Экспертная маршрутизация GLM-5.2 в значительной степени предсказуема *заранее* — при применении
Маршрутизатор уровня L+1 в состояние пост-внимания уровня L вызывает **71,6%**
настоящий топ-8 (против 41,3% у «тех же экспертов, что и последний токен»). `PILOT=1` вопросовУпреждающее считывание экспертом следующего уровня из выделенного потока ввода-вывода, в то время как текущий уровень
вычисляет. `PILOT_REAL=1` убирает предварительно выбранные нагрузки с критического пути.
(измеренная частота попаданий +11pp на хосте с большим кэшем) и `PILOT_TWO=1` сворачивает
вычисленный общий эксперт в прогнозе (+3% отзыва,
[#200](https://github.com/JustVugg/colibri/issues/200)). На диске, насыщенном
ПИЛОТ только для подсказок хостов может быть чистым отрицательным — измеряйте по своему.

<a id="speculation-and-reproducibility"></a>
## Спекуляции и воспроизводимость

Спекулятивное декодирование требует, чтобы пути черновика и проверки вычислялись одинаково.
функция — `SPEC_PIN=1` (по умолчанию, начиная с [#294](https://github.com/JustVugg/colibri/pull/294))
закрепляет все выданные форварды, пока черновики активны, в ядре платформы S=1
семья. Для воспроизводимости с точностью до байта между запусками: `DRAFT=0` плюс `IDOT=0
COLI_CUDA=0`, если вы также хотите независимости от ядра/GPU. Принятие
проценты не сопоставимы для разных версий движков ниже `--topp`
([#163](https://github.com/JustVugg/colibri/issues/163) содержит полную историю).

Встроенная головка MTP GLM-5.2 создает токены, которые основная модель проверяет в одном
пакетно вперед: 2,2–2,8 токена/форвард при выплате. Руководитель МТР должен быть
**int8**: головки int4 схлопываются до приемлемости 0–4%.
([#8](https://github.com/JustVugg/colibri/issues/8)). Черновики с грамматикой
([`GRAMMAR=file.gbnf`](grammar-draft.md)) добавьте почти бесплатное принятие на
ограниченный вывод JSON. Является ли спекуляция чистым выигрышем, зависит от вашего кеша
температура: измерьте и используйте `DRAFT=0`, когда это не помогает.

Пакеты Verify также могут использовать **ядро точного внимания** с помощью
`COLI_EXACT_VERIFY=1` ([#689](https://github.com/JustVugg/colibri/issues/689)):
Оценка CPU MLA-absorb и контекстные точки накапливают целочисленные произведения и округляют
один раз, поэтому близкая связь в строке проверки разрешается одинаково на каждом хосте, в
примерно 0,6x tok/s на крошечном оракуле (сама точка примерно в 5–7 раз превышает цикл с плавающей запятой).
Два ограничения, которые следует знать: при использовании квантованного KV-кэша (`tq1`, TQ или int8 KV)
Контекстная точка сохраняет путь с плавающей запятой, поэтому точность там не обеспечивается; и
настоящий флип при ничьей только обсуждался, но еще не был обнаружен на GLM-5.2 при n = 64.

<a id="approximate-mode-degrade_zero-opt-in-olmoe-calibrated"></a>
## Примерный режим: `DEGRADE_ZERO` (по желанию, калибровка OLMoE)

`DEGRADE_ZERO=1` включает добровольную политику ухудшенного вывода: при предварительной выборке
срок пропущен, эксперты, чей вес ворот на позицию падает ниже
`DEGRADE_TAU` (по умолчанию 0,03) **заполняются нулями, а не загружаются с диска**.
Слот не вносит никакого вклада в выходные данные слоя; приближение - это
выброшенная масса, а не перемасштабированная ее версия (ренорм катастрофически хуже —
см. выпуск № 865 для измерения A/B).

Это уменьшает блокировку чтения диска при рабочих нагрузках, связанных с NVMe, за счет небольшого
качественный хит. Измерено на OLMoE-1Б-7Б:

| `DEGRADE_TAU` | слоты обнулены | дельта человек |
|---|---|---|
| 0,03 | ~22% | +2,9% |
| 0,05 | ~60% | +41% |

**Эти цифры относятся к OLMoE.** GLM-5.2 (`norm_topk=1`) и Kimi K3 имеют
разные контракты маршрутизаторов и количество экспертов — их рабочие точки не имеют
было измерено. Пока они не появятся, рассматривайте `tau=0.03` как отправную точку и проверяйте
качество вашей модели, прежде чем полагаться на нее.

**Эти цифры предполагают наличие «теплого» экспертного кэша.** Сеансы с холодным стартом — когда кэш
начинается пусто, и все эксперты изначально промахиваются — скорость выпадения будет выше, пока не будет LRU
наполняет. Измерялась устойчивая дельта недоумения, указанная выше; переходный процесс при холодном запуске
поведение отдельно не охарактеризовано.

Эта функция предназначена только для декодирования (`S≤4` защита, такая же, как `EXPERT_BUDGET`): удалениеэксперты во время предварительной заливки повреждают кэш KV. Правило спасения гарантирует отсутствие токена
позиция остается с нулевым разгромленным экспертом. Резидентный (закрепленный или кэшированный в LRU)
эксперты никогда не падают независимо от веса.

В нижнем колонтитуле `[PROF]` указано общее количество обнуленных слотов и три верхних слоя.
отбрасывайте долю, когда флаг активен, поэтому неправильно откалиброванный тау скорее виден
чем молчать.

```bash
DEGRADE_ZERO=1 DEGRADE_TAU=0.03 COLI_MODEL=/nvme/glm52_i4 ./coli chat
```

См. [ENVIRONMENT.md](ENVIRONMENT.md) для получения полной ссылки на переменную и
[выпуск № 865](https://github.com/JustVugg/colibri/issues/865) для
методология измерения.

<a id="conversations-reopen-warm"></a>
## Разговоры возобновляются тепло

`coli chat` сохраняет сжатый MLA KV-кэш на диск после каждого хода.
(`.coli_kv`, ~182 КБ/токен, добавляется постепенно, защищен от сбоев). Закрой чат,
откройте его завтра — модель все еще помнит весь разговор и **ноль
происходит повторное предварительное заполнение**: проверенный байт, идентичный непрерывному сеансу.
`:reset` очищает, `KVSAVE=0` отключает.
