# GLM-5.3-Флеш-движок (`c/glm53.c`)

Родственный движок для [GLM-5.3-Flash](https://huggingface.co/zai-org/GLM-5.3-Flash).
(параметры 321B, 45 слоев + MTP, с обзорной башней), следуя
схема «один движок на семейство» (`colibri.c` = GLM-5.2, `kimi_k3.c`, `inkling.c`).
Он разделяет `st.h`, `json.h`, `tok.h`, `quant.h` и `hyper_connections.h`, и
в других движках ничего не трогает.

```
make glm53
./glm53 --model <dir> --prompt "Ciao, come stai?" --greedy 32
```

Или через лаунчер, где живут изображения и шаблоны чатов:

```
coli chat  --model <dir> --no-think
coli serve --model <dir>
coli web   --model <dir>
```

<a id="getting-the-model"></a>
## Получение модели

Движок считывает преобразованный контейнер, а не снимок HF. Один проход делает оба
загрузка и преобразование по одному осколку за раз:

```
python3 tools/convert_glm53.py --outdir /path/glm53_i4 --min-free-gb 30
```

Пиковый диск — это выходные данные плюс один исходный фрагмент размером 5 ГБ, а не репозиторий.
328 ГБ. На эталонной машине: 62 шарда, **194,7 ГБ свободного места, 25 часов**.

Перенаправленные эксперты становятся масштабируемыми в группе int4 на уровне 64 (`name` полубайты U8 + `name.qs`
Весы F32, тот же контейнер, что и GLM-5.2). Все остальное остается BF16 — 9,7B.
параметры 321, около 18 ГБ — поэтому точность плотного набора — это время загрузки
выбор и его повторная настройка никогда не означают повторную загрузку репозитория. Каждый из
92 вида тензоров классифицируются явно, и неизвестное имя останавливает
преобразование, потому что преобразователь, который пропускает то, чего он не знает, создает
контрольная точка, которая загружается и незаметно пропускает тензор.

<a id="architecture-notes"></a>
## Примечания по архитектуре

Четыре штуки отличаются от всего остального в этом репозитории:

**KDA (Внимание Дельты Kimi)** на 34 из 45 слоев: `q,k,v = SiLU(ShortConv4(Wx))`,
q и k L2-нормализованы с эпсилоном **внутри** квадратного корня (FLA
соглашение, намеренно отличающееся от `F.normalize`), то правило закрытой дельты.
выходные ворота здесь имеют низкий ранг, а у Kimi K3 - единственная проекция.

**DSA с объединением k-групп** на остальных 11. Ключи группируются в пулы
`index_kpool`; объединенный ключ представляет собой смесь softmax для каждого канала, а не
среднее значение, поэтому пул не обязан описывать себя средним значением. Бассейн
можно выбрать только в том случае, если он полный и причинно видимый, неполный хвост
добавляется по запросу (следовательно, строка шириной `topk + pool - 1`, а не `topk`), и
связи идут к нижнему индексу, поэтому выбор является детерминированным.

**Гиперподключения mHC**, доступные для DeepSeek V4 через
`hyper_connections.h` — измеренная битовая совместимость, не предполагается.

**Зажат SwiGLU в тексте MLP**, не только в обзорной башне: `gate` имеет
потолок, `up` зажимается с обеих сторон. Plain SiLU дает говорящую модель
ну и это неправильно.

<a id="mla-is-absorbed"></a>
### MLA поглощено

Кэширование расширенных ключей стоит 1,39 МБ на каждый токен на всех уровнях DSA — 11,9 ГБ на каждом уровне.
8192 позиции на движке, который умещается в небольшой памяти. `kv_b_proj` это
вместо этого сложен на два конца, поэтому в кеше хранится скрытая ширина 512:

```
score_j = q · (W_k c_j) = (W_kᵀ q) · c_j
out     = Σ_j a_j (W_v c_j) = W_v (Σ_j a_j c_j)
```

Тождество, а не приближение: меняется только порядок продуктов.
**33 КБ на токен**, что составляет 1,1 ГБ при 32 тысячах позиций и 4,4 ГБ при полной
128 тыс. Веса тоже не растут, потому что транспонирование W_k сохраняет свой элемент
считать.

<a id="memory-and-speed"></a>
## Память и скорость

Замерено на реальной GGUF, 6 физических ядер, 25 ГБ ОЗУ, модель на
обычный диск:

| | |
|---|---|
| вес резидента составляет `GLM53_BITS=4` | ~12 ГБ |
| КВ состояние | 33 КБ на токен (1,1 ГБ при 32 КБ) |
| предварительное заполнение рабочей области | плоский, ~60 МБ в любом контексте |
| декодировать | ~44 с/токен в холодном состоянии, ~20 с/токен с теплым экспертным кэшем |

**Диск — это стена, и стоит знать, где он находится.** Один токенкасается 42 разреженных слоев × 8 экспертов × 14,2 МБ = 4,8 ГБ. Измерено с
`O_DIRECT`, эталонный диск дает 72 МБ/с при глубине очереди 1, 185 при QD4 и
207 на QD16 — скорость насыщения около 200 МБ/с. Таким образом, **минимальная продолжительность составляет 24 секунды на
токен** на этом оборудовании: что требуется диску для доставки байтов с любым процессором.
и любой графический процессор. Более быстрый кремний его не перемещает; меньше байтов.

Именно поэтому путь Vulkan предлагается для машин с достаточным количеством видеопамяти для
держать здесь экспертов, а не акселератора.

**Vulkan.** В сборке `make VK=1 glm53` `COLI_VULKAN=1` дает разгромленных экспертов.
общий экспертный уровень (`c/vk_tier.c`, тот, который использует каждый механизм MoE): a
бюджет экспертов, сохраненный на устройстве, теплый от истории (`.coli_usage`) на
запуск и адаптация во время чата, поэтому горячего эксперта нельзя ни прочитать с диска, ни
вычисляется процессором. Каждый шаг МО отправляет строки резидентных экспертов на устройство в виде
один пакет, пока CPU читает и вычисляет остальные; то каждый эксперт присоединяется к своему
токен в порядке маршрутизации после общего эксперта. Зажим SwiGLU от экспертов – тот самый
условие: `swiglu_clamped` фиксируется на любом `swiglu_limit`, включая 0, пока устройство
фиксирует только выше 0, поэтому при пределе 0 эксперты остаются на CPU и в строке написано
так. Резидентные матрицы следуют за `COLI_VK_DENSE` (на устройстве, которое совместно использует ОЗУ CPU).
они остаются в CPU, пока уровень включен). Каждый забег заканчивается
`[VK] tier glm53 run: device N of M routed experts ...`; ручки - это
`COLI_VK_TIER*` ряды по `docs/ENVIRONMENT.md`, детали в
[vulkan.md](vulkan.md#glm-52-and-glm-53-flash-on-the-tier). Измерено на Lavapipe для
Единственная корректность: ни один графический процессор еще не выполнил на нем реальные веса.

<a id="vision"></a>
## Видение

Доступен с любой поверхности: путь, вставленный в `coli chat` (читается клиентом,
отправляется как URI данных), файл, прикрепленный или переброшенный в `coli web`, или OpenAI
`image_url` часть с URI данных в формате Base64. Читается локальный путь в запросе
только под `COLI_IMAGE_ROOT` (см. `docs/ENVIRONMENT.md`): файл, прочитанный
сервер происходит со своими правами, и клиент вывода не является
оператор. Удаленные URL-адреса скорее отклоняются, чем загружаются — запрос не должен
заставить сервер открыть сетевое соединение по выбору отправителя.

`tools/glm53_image.py` выполняет предварительную обработку и привязан к официальному
`Glm5NextImageProcessor`: идентичная геометрия всех опробованных форм, побитовая идентичность.
пикселей там, где не происходит передискретизации, и 0,03 в худшем случае, когда она происходит, что
это бикубика Pillow против torchvision. Изображение масштабируется с учетом его аспекта.
сохраняется и дополняется, никогда не растягивается и дополняется нулями *до* нормализации.

Изображения перемещаются в своем собственном кадре `IMAGE`, объявленном непосредственно перед
`SUBMIT`, которому они принадлежат (см. `docs/serve_protocol.md`). Движок держит один
ожидающее изображение и удаляет более старое, вместо того, чтобы отвечать о предыдущем
фото, не говоря об этом.

`GLM53_MAX_IMAGE_TOKENS` имеет большее значение, чем кажется. GGUF собственный
потолок — 8000 токенов за изображение, что составляет 2691 за обычное фото 1080р — на
движок, который передает экспертов с диска, предзаполнение, которое никто не выдержит.
Каждый токен изображения занимает размер 28×28 пикселей, поэтому 256 сохраняет обычный текст разборчивым, а 64
сохраняет только формы и цвета. Изображение сжимается, а не обрезается: теряется то, что
детали, а не кусочки.

## Тесты

```

python3 tools/make_glm53_streaming_pair.py --fixture ~/glm53_mm_tiny --output ~/glm53_stream

        --quantized ~/glm53_stream-i4 --dequantized ~/glm53_stream-deq

bash tests/vulkan_engines.sh glm     # the expert tier against the CPU, on Lavapipe (glm-sanitize: ASan, UBSan)
```

Генераторам нужны трансформаторы 5.16.1, закрепленные, потому что оракул, написанный
другая версия - это другой оракул. Каждый жгут пропускает команду, которая
создает то, чего ему не хватает, а не выбрасывает, и завершает 2, когда это происходит: пропуск
ничего не проверено и не должно считаться пропуском.

Ремни имеют название `glm53_*_harness.py`, поэтому `make test-python` не имеет названия.
соберите их как пустые модули unittest. `tests/test_glm53_oracles.py` оборачивает
два оракула только для stdlib для unittest; он запускает их, когда `GLM53_TINY`
(`tools/make_glm53_tiny.py`) и `GLM53_MM_TINY` (мультимодальный прибор выше)
указывают на их приспособления, как это делает задание GLM-5.3 CI, и по этой причине пропускается
иначе.

Два генератора отказываются писать прибор, который не может выйти из строя: один отвергает
вырожденная модель, которая везде отвечает одному и тому же токену, а другой — приспособлению
ответ которого не меняется при переворачивании изображения. Проверка зрения делает
не проверять, что модель отвечает — она все равно ответит, игнорируя пиксели —
но что **два разных изображения дают два разных ответа**.

`tools/check_glm53_container.c` сравнивает настоящего конвертированного эксперта с пустышкой
деквантование одних и тех же байтов. Ему нужна преобразованная контрольная точка, поэтому он не
запустить в CI, и это первое, к чему нужно стремиться, когда реальная модель отвечает
странно.
