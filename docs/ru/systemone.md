# Режим System One: типизированные решения с калиброванными вероятностями

Режим System One отвечает на закрытые вопросы с вероятностью на разрешенное
вариант. Для этого есть один API, `POST /v1/systemone`, с запросом и
ответ Джева из TypeSafe: состояние, набранные вопросы (`noul`, `choice`,
`score`), а также для каждого вопроса вероятность каждого варианта. Языковая модель
ответы путем **оценки** вместо написания; модель принятия решения, такая как
[Laya](laya.md), [GLiNER2.5-Decide](gliner_decide.md) или [Ключ](clef.md)
отвечает родно. Тот же сервер и та же модель, что и у чата:
mode — это конечная точка, а не флаг сборки или отдельный процесс.

<a id="why-you-would-want-it"></a>
## Зачем вам это нужно

Сгенерированный ответ представляет собой строку. Вы анализируете его и надеетесь, что это одно из значений, которые вы
просил, а про уверенность ничего не получаешь: модель пишет `high`
точно так же, знает ли он или догадывается.

Режим System One отвечает на три вопроса, которые на самом деле имеет решение с закрытым набором:

| | поколение | Система Один |
|---|---|---|
| какой вариант | строка для анализа | вариант, по конструкции |
| насколько вероятно, что каждый | недоступно | вероятность каждого варианта, включая те, которые модель никогда не запишет |
| знает ли он | недоступно | a `confidence` за ответ, 1, когда одна опция содержит массу, и 0, когда она плоская (терминал и страница также показывают энтропию) |

Третий ряд — это тот, который вы не можете получить другим способом, и обычно именно он
который решает, может ли решение быть автоматизировано.

<a id="it-needs-a-running-server"></a>
## Требуется работающий сервер

Существует три способа использования режима System One, и все они являются клиентами одного и того же режима.
сервер: **конечная точка HTTP**, **терминал** (`coli chat --attach`) и
**Страница System One** в веб-интерфейсе. Чего не существует, так это одноразовой формы:
нет `coli decide <model> ...`, который загружается, отвечает и завершает работу.

Это не упущение. Вся суть в снимке: общий префикс

Итак, запустите сервер один раз и сохраните его:

| из | как |

<a id="the-http-endpoint"></a>
## Конечная точка HTTP

```
POST /v1/systemone
```

| поле | требуется | смысл |
|---|---|---|
| `state` | да | о чем вопросы: текст, объект или массив (JSON читается как текст) |
| `questions` | да | объект от 1 до 64 вопросов, `id: question`; в ответе используются те же идентификаторы |
| `model` | нет | любое имя: отвечает обслуживаемая модель (клиент Jev отправляет `jev-latest`) |
| `normalize`, `pin_state`, `prefix`, `cache_slot` | нет | Варианты colibri ниже |

Каждый вопрос имеет `type`, необязательный `instructions` (текст, объект или массив).
и это `criteria`:

| тип | критерии | ответ |
|---|---|---|
| `noul` | дополнительные `{"true": ..., "false": ...}` описания | `noul`: вероятность «да» |
| `choice` | `{label: description or null}`, от 1 до 255 ярлыков | `choice`, `probabilities` по метке, `confidence` |
| `score` | `[level 0, level 1, ...]`, уровни с 1 по 255 | `score` (ожидаемый уровень), `legend` и `probabilities` с ключами `"0".."n-1"`, `confidence` |

<a id="from-your-own-code"></a>
### Из вашего собственного кода

Никакого SDK не требуется: это один JSON-запрос на одном сервере с одинаковым

```python
r = requests.post("http://127.0.0.1:8000/v1/systemone", json={
    "state": open("ticket.txt").read(),
    "questions": {
        "queue":  {"type": "choice", "instructions": "Which queue?",
                   "criteria": {"billing": None, "bugs": None, "sales": None}},
        "urgent": {"type": "noul", "instructions": "Is it urgent?"},
    }})
answers = r.json()["answers"]
print(answers["queue"]["choice"], answers["queue"]["confidence"], answers["urgent"]["noul"])
```

```js
const r = await fetch("http://127.0.0.1:8000/v1/systemone", {
```

<a id="what-a-language-model-is-asked"></a>
### Какая языковая модель задается

Как три примитива отображаются на языковой модели, чтобы вы знали, что это такое
вообще-то спросил:

| Джев примитивный | что набрано | что входит в текст вопроса | ответить |
|---|---|---|---|
| `noul` | `yes` / `no` | `instructions`, затем `yes: <criteria.true>` и `no: <criteria.false>`, если они заданы, то «Ответить да или нет». | `noul` = вероятность «да» |
| `choice` | этикетки `criteria` (до 255) | `instructions`, затем по одной строке на метку с ее описанием | `choice`, `probabilities` по этикетке, `confidence` |
| `score` | номера уровней `"1".."n"` (от 1 до 255 уровней) | `instructions`, затем `k: <description>` за уровень, затем «Ответить цифрой». | `score` = ожидаемый уровень при распределении, `legend` и `probabilities` с кодом `"0".."n-1"`, как их нумерует Джев, `confidence` |

`state`, `instructions` и каждый критерий может быть строкой, объектом или
массив; JSON сериализуется как текст. `confidence` — это формула их
документация дает, `(n * peak - 1) / (n - 1)`: 1, когда вся масса находится на
одна метка, 0 в плоском состоянии; `noul` не содержит ничего, как и у них. Вопрос с
на одну метку или уровень отвечают, не спрашивая модель.

Что отличается от Джева, скорее заявлено, чем скрыто:

- `model` — обслуживаемая модель, `provider` — `"colibri"`, `usage.cost` — 0,
  и `id` — идентификатор запроса (также заголовок `x-typesafe-request-id`).
- `usage.output_tokens` подсчитывает маркеры опций для языковой модели **чтение**;
  ничего не генерируется. `input_tokens` — самая длинная подсказка запроса.
  Механизм принятия решений сообщает о прочитанных токенах как `input_tokens` и 0 на выходе.- Ошибки проверки: `422`, как и у них, с конвертом ошибок этого сервера.
  (`error.message`, `error.param`) и список Джева `detail` рядом с ним.
- `GET /v1/models` перечисляет карту Джева (`models`: имя, описание,
  Release_date) рядом с `data` OpenAI.
- Вероятности указаны для этой модели, нормированные по вариантам с
  Правило `sum` ниже. Числа не будут совпадать с числами Джева на том же входе; тот
  Контракт тот же, модель ваша.

<a id="colibris-options"></a>
### colibri варианты

Ничто из этого не отправляется клиентом Jev; каждый не является обязательным.

| поле | смысл |
|---|---|
| `normalize` | `"sum"` (по умолчанию) или `"mean"`: как логарифмические вероятности вариантов языковой модели становятся одним баллом для каждого варианта, см. ниже |
| `pin_state` | `true` / `false`: сфотографируйте состояние для следующего запроса. Если оставить это без внимания, сервер фотографирует его, когда его читают два или более вопросов или когда то же состояние возвращается из более раннего запроса. Состояние, которое меняется при каждом вызове (игра, сигнал датчика), считывается напрямую, на один запрос меньше |
| `prefix` | фиксированный текст, который читается перед состоянием, фотографируется один раз для каждого слота КВ и снимается повторно, если движок его вытесняет. Для правил или инструкций, которые остаются при изменении состояния: на крошечном приспособлении MiMo правила из 690 позиций плюс фрейм стоят 143 позиции за запрос вместо 690 |
| `cache_slot` | слот KV, как на конечных точках чата; по умолчанию он извлекается из состояния (из префикса, если он есть) |

Механизм принятия решений не имеет логарифмов вероятностей и фотографий: он игнорирует
`normalize` и `pin_state` и отказывается от `prefix` (вставьте этот текст в `state` или
`instructions`); `cache_slot` достигает его как слота РЕШЕНИЯ.

<a id="do-not-put-the-options-in-the-state"></a>
### Не помещайте параметры в состояние

Напишите состояние и инструкции; оставьте варианты `criteria`.
Сервер перечисляет метки вариантов выбора один раз в вопросе и читает каждую из них как
продолжение ответа. Повторение их в штате или инструкции
делает подсказку длиннее для каждого прочитанного варианта и называет их в предложении
смещает оценку в сторону того, что в предложении упоминается последним.

<a id="sum-or-mean"></a>
### `sum` или `mean`

`logprob` — логарифмическая вероятность всей строки опциона; `mean_logprob`
делит его на токены опциона. `sum` — значение по умолчанию. Измерено на
Тест проверки кода из 30 случаев (ALLOW / REVIEW / DENY), `mean` ответил DENY на
все 30, включено однословное исправление README, поскольку DENY — это два токена, а ALLOW
один: среднее значение на один токен отдает предпочтение тому варианту, в котором больше токенов. С `sum`
тот же пакет получил оценку ALLOW 10/10 и DENY 9/10. `mean` остается доступным, и
сервер предупреждает, когда его запрашивают параметры, количество токенов которых отличается. Вкл.
qwen36 один случай пошел другим путем (`sum` выбрал `merge`, где модель
мой жадный ответ был `request changes`), поэтому, когда у вас очень много вариантов
разная длина, посмотрите оба.

<a id="reading-the-answer"></a>
## Читаю ответ

`confidence` равно `(n * peak - 1) / (n - 1)` по сравнению с вариантами `n`: 1, когда все
масса находится на единице, 0, когда она плоская. Терминал и страница показывают
энтропия тех же вероятностей, нормированная на 0..1 по числу
варианты:

| энтропия | чтение |
|---|---|
| ниже 0,4 | модель уверена |
| от 0,4 до 0,8 | неуверенный |
| выше 0,8 | он не знает: рассматривайте верхний вариант как подбрасывание монеты |

Энтропия около 1 — полезный ответ, а не провал. Это модель говорит вамдля этого решения нужен человек, чего никогда не делает сгенерированное предложение.

<a id="in-the-terminal"></a>
## В терминале

Разговор на данный момент становится контекстом, поэтому вы можете общаться, а затем переключиться на
забить, ничего не переформулировав.

```
coli chat --attach http://127.0.0.1:8000

› /decide merge | request changes | close
  ✦ System One · 3 options · the model no longer generates, it assigns probabilities

› The PR touches the engine and carries no tests. What should we do?
  ◆ System One
     request changes  ███████████████████████░░░  93.6%
     merge            ██░░░░░░░░░░░░░░░░░░░░░░░░   6.4%
     close            ░░░░░░░░░░░░░░░░░░░░░░░░░░   0.0%
     → request changes  entropy 0.218  (sure)

› /decide

```

`/decide` с опциями переходит в режим разговора с учетом контекста;
Один `/decide` возвращается в чат. `:decide` тоже работает. TAB завершает команды.
Каждый вопрос передается `POST /v1/systemone` как один `choice`, метки которого являются
варианты, с разговором по состоянию.

<a id="in-the-browser"></a>
## В браузере

Запись **System One** в навигационной панели открывает страницу, созданную на основе той же
Форма: документ сверху, прочитанный один раз, а под ним накапливаются вопросы, каждый
со своим набором разрешенных вариантов и собственным ответом. Столбцы показывают
вероятность каждого варианта, а энтропия находится рядом с победителем. Каждый
вопрос идет к `POST /v1/systemone` как один `choice`, о языковой модели и
на модели принятия решений одинаково.

Варианты указаны для каждого вопроса и не публикуются на странице: «Насколько это рискованно» хочет
низкий/средний/высокий, где «мы подпишем» требует «да/нет», и один список для всех
изменил бы вопросы, чтобы они соответствовали списку.

Вы можете загрузить документ из файла (обычный текст: `.txt`, `.md`, `.json`, `.csv`).

читать как шум). Страница и чат остаются живы вместе: начните подсчет очков,

<a id="under-the-protocol"></a>
## По протоколу

Если вы говорите по [протоколу обслуживания](serve_protocol) напрямую, режим System One равен двум.
дополнительные клавиши на `SUBMIT`. Оба являются добровольными: запрос, который их не отправляет
создает кадры, идентичные кадрам, отправленным до того, как эта функция существовала.

```
SUBMIT <id> <slot> <bytes> <max_tokens> <temp> <top_p> [gbytes] [key=value ...]
```

| ключ | эффект |
|---|---|
| `logprobs=k` | прочитайте предварительное заполнение: один кадр `ECHO` на новую позицию и числовой хвост на `DATA` |
| `pin=1` | сфотографируйте состояние движка в конце этой подсказки |

`max_tokens=0` допустимо **только** вместе с `logprobs>0` и означает «прочитайте
подскажи и остановись». Без него каждый вариант требует полного шага декодирования, который затем
Отброшено: при варианте с одним токеном удвойте работу.

Кадр `ECHO`:

```
ECHO <id> <nbytes> <position> <logprob> <k> [<token_id> <logprob>]*k
<nbytes bytes of the token's text>
```

`<logprob>` — это log-softmax токена, который фактически находился в этой позиции, более
весь словарный запас. Первая позиция свежего промпта не имеет никаких условий
дальше и несет `nan 0`; когда снимок восстанавливается, его сохраненные журналы предоставляют это
вместо этого первый предиктор.

<a id="scoring-by-hand"></a>
### Подсчет очков вручную

1. Отправьте общий префикс с помощью `pin=1 logprobs=1 max_tokens=0`.
2. Для каждого варианта отправьте `prefix + " " + option` и `logprobs=1 max_tokens=0`.
3. Просуммируйте логарифмические вероятности `ECHO` в позициях после префикса, разделите на
   количество этих позиций и возьмите softmax для всех вариантов.

Это то, что `/v1/systemone` делает в языковой модели (с `sum` по
по умолчанию вместо среднего значения для каждого токена на шаге 3). Делать это в клиенте
возможно, и именно так была смоделирована конечная точка, но три вещи легко сделать
ошиблись: закрепление, список опций просачивается в подсказку, и
нормализация.

<a id="nested-snapshots"></a>
## Вложенные снимки

Полезные префиксы вложены: общие инструкции и инструкции плюс.
этот вопрос. Движок сохраняет несколько снимков (`COLI_PIN_SLOTS`, по умолчанию 4) и
всегда восстанавливает самый глубокий, который является строгим префиксом нового промпта.С одним снимком вам придется выбирать, какой уровень оставить, а другой платный.
еще раз при каждом запросе: измерено на qwen36, 496 токенов на предмет вместо 176.

Отправьте `pin=1` туда, куда вам нужна точка возврата. Движок соответствует идентификаторам токенов, поэтому
ничего не нужно объявлять заранее, и он отказывается от снимка, внимание которого
строки, которые состояние больше не содержит.

<a id="what-a-snapshot-holds"></a>
## Что содержит снимок

Снимок — это не всегда просто идентификаторы токенов. Он должен содержать все, что слой переносит из одного
токен к следующему, или опция, которая возобновляется с него, начинается из состояния, которое никогда не
существовали, и цифры остаются правдоподобными. Что это такое, зависит от модели:

- **Строки внимания, проиндексированные по положению** (каждый уровень полного внимания), остаются на своих местах.
  есть. Ничего не написано после того, как снимок окажется под ним, поэтому снимок сохраняется только
  идентификаторы, и движок проверяет, что состояние все еще хранит эти идентификаторы, прежде чем доверять
  строки. Несвязанное промпт между ними перезаписывает их; снимок будет тогда
  отпускается, и опция вычисляется с самого начала.
- **Повторяющееся состояние** (уровни DeltaNet Qwen3.6 и Qwen3.8) копируются в
  снимок, поскольку повторение невозможно перемотать.
- **Кольца с раздвижным окном** (MiMo-V2.6: 39 из 48 слоев присутствуют на последних 128
  позиции) тоже копируются. Оконный слой сохраняет позицию p в слоте p по модулю 128, поэтому
  первый вариант записывает свои токены в слоты последнего снимка
  позиции. Без копии второй вариант будет читать ключи первого.
  На MiMo-V2.6 Flash это около 50 МБ на снимок.

Промпт с **изображением** никогда не делает снимок и никогда не возобновляет работу с него. Его идентификаторы
описывайте, куда идет картинка, а не что на ней изображено.

**Чтение начинается там, где заканчивается снимок**, а не там, где заканчивается общий текст. Два
варианты разделяют текст перед ними, и остановка на этом месте оставит первый вариант
токен без логитов, которые его предсказывают. На MiMo и GLM быстрое считывание без
снимок для возобновления считывается с позиции 0, а не с живого префикса. Это
это то, что нужно `echo` на `/v1/completions`.

Во время испытаний на подачу движок удерживается за обе половины на крошечном приспособлении.
(`tests/test_brio_serve.py` и `tests/test_mimo_prefix_serve.py` для колец MiMo и
картинки). Опция, прочитанная через снимок, должна давать цифры, которые дает холодный движок,
до последней напечатанной цифры. Он также должен **обрабатывать только свои токены**: проверяя
одни только цифры передавались бы в механизм, который спокойно все пересчитывал.

<a id="limits"></a>
## Ограничения

- **Опции оцениваются, но не проверяются.** Два варианта, которые токенизируются одинаково:
  неотличим.- **Снимок находится в процессе движка.** Перезапустите сервер и сначала
  запрос снова оплачивает полное предварительное заполнение.
- **Снимки занимают память, в которой они хранят состояние.** `COLI_PIN_SLOTS` (по умолчанию 4) границы
  сколько держит движок: около 50 МБ на MiMo-V2.6 Flash, десятки МБ на Qwen3.6,
  только идентификаторы и окончательные логиты на движках, хранить больше нечего.
- **Один слот КВ означает один разговор за раз.** При нескольких слотах запросы
  совместно используемые `state` направляются в один и тот же слот, поэтому они используют общий снимок; с одним,
  чередующиеся клиенты вытесняют друг друга.
- **`normalize` — это политика, а не факт.** Ни среднее, ни сумма не подходят для всех.
  набор опций; если ваши варианты имеют очень разную длину, обратите внимание на оба.

<a id="decision-engines"></a>
## Механизмы принятия решений

Языковая модель отвечает на вопрос `/v1/systemone`, оценивая каждый вариант по своему значению.
Канал logprob: подсказка для каждого вопроса, считывание для каждого варианта. **решение
engine** — это модель, созданная для самого вопроса. Он считывает состояние и
вводит вопросы и возвращает вероятность каждого варианта за один проход вперед,
с калибровкой, установленной его авторами. colibri обслуживает его на том же
конечная точка и с тем же ответом, поэтому клиент Jev, SDK и панель мониторинга
не могу сказать, какой тип ответил.

| движок | модель | док |
|---|---|---|
| `c/laya` | Laya (Convai Innovations): кодер ModernBERT + руководитель принятия решений | [laya.md](laya.md) |
| `c/gliner_decide` | GLiNER2.5-Decide (быстро): кодер DeBERTa-v3 + классификационная головка GLiNER2 | [gliner_decide.md](gliner_decide.md) |
| `c/qwen36` | Ключ (Cloudflare): Qwen3.8-27B, прошедший обучение, + глава совместной схемы; он также общается | [clef.md](clef.md) |

Механизм только принятия решений (Laya, GLiNER2.5-Decide) обслуживает только `POST /v1/systemone`. Чат,
завершения и сообщения отвечают на 400 с указателем на `/v1/systemone`, и
`/v1/models` перечисляет модель с `capabilities: ["systemone", "decision"]`.
(языковая модель говорит `["chat", "systemone"]`). Модель чата с
руководитель принятия решений (Клеф) сохраняет каждую конечную точку и говорит `["chat", "systemone"]`;
только его `/v1/systemone` использует собственный путь. Путь представляет собой один рейс туда и обратно:
шлюз проверяет запрос, отправляет его в механизм как одну запись и
формирует ответ. Ничего не отображается в подсказке, и ни одна опция не учитывается.
самостоятельно. На Laya доля шлюза составляет около 2 мс на запрос: 8,1 мс на
клиенту за три вопроса по крошечному приспособлению, из них 6,1 в
движок; На реальной GGUF 882 мс, в движке 879,5. Движок собственный
время указано в заголовке `x-colibri-engine-ms`.

<a id="the-contract-for-an-engine-author"></a>
### Контракт для автора движка

Все нижеприведенное является общим; `c/decide_serve.h` реализует сторону движка,
поэтому новый движок пишет только свою модель и одну функцию.

**Рукопожатие.** Движок объявляет о себе на строке `CAPS` подачи.
протокол: `decide=1` (требуется `DECIDE`) и `chat=0` (ничего не генерирует).
Движок, который также поддерживает чат, исключает `chat`; затем шлюз отправляет
с `/v1/systemone` на `DECIDE` и конечные точки чата на `SUBMIT`, как и раньше.
`decide_record=raw` запрашивает необработанную форму записи ниже.

**Запрос.** `DECIDE <id> <slot> <bytes>`, за которым следует одна запись JSON:

```json
{"state": "{\"subject\": \"Duplicate charge\", \"body\": \"...\"}",
 "state_type": "object",
 "questions": [
   {"id": "department", "type": "choice", "instructions": "Which department?",
    "options": [{"label": "billing", "text": "invoices, payments, refunds"},
                {"label": "other", "text": null}]},
   {"id": "urgency", "type": "score", "instructions": "How urgent is this?",
    "options": [{"label": "0", "text": "not urgent"}, {"label": "1", "text": "blocking"}]},
   {"id": "churn", "type": "noul", "instructions": "Does the user threaten to leave?",
    "options": [{"label": "false", "text": null}, {"label": "true", "text": null}]}]}
```

- Каждый текст уже является текстом. Строка сохраняется в том виде, в каком она была отправлена; объект или
  массив (состояние, инструкции, критерий) записывается как
  `json.dumps(value, ensure_ascii=False)`, ссылка на сериализацию
  пакеты применяются, поэтому движок считывает байты, на которых обучалась его модель.
  `state_type` говорит, что отправил звонящий (`string`, `object`, `array`, ...),потому что модель может по-разному относиться к списку (разговору).
- Опции идут в порядке вызывающего абонента: метки выбора с их
  описания (`null` при отсутствии), уровни баллов от 0, ноль `false`
  затем `true` с дополнительными критериями. Отсутствующие инструкции получают то же самое
  текст по умолчанию, который запрашивает путь к языковой модели.
- `slot` — это слот KV для механизма, который сохраняет состояние между запросами.

**Необработанная форма.** Модель, ссылка на которую преобразует запрос в подсказку.
самому (Clef) нужно то, что отправил вызывающий абонент, а не чтение этого шлюзом. Ан
движок, на котором написано `decide_record=raw`, получает запись с `"record": "raw"`
и той же формы, с тремя отличиями: инструкции `null`, когда
вызывающий абонент ничего не отправил (нет текста по умолчанию); описание сохраняется в том виде, в котором оно было отправлено, `""`
включен, а на стороне, которую звонивший не описал, нет клавиши `"text"` на
все (`null`, когда оно было описано как `null`); и значение JSON (состояние,
инструкции, описание) написана рассортированными ключами и компактно.
разделители, `json.dumps(value, обеспечения_ascii=False, separators=(",", ":"),
sort_keys=True)`, with `"json": true` для опции, текст которой один.
Laya и GLiNER2.5-Decide получают форму по умолчанию, байт за байтом, как и раньше.

**Ответ.** Один кадр `DECISION <id> <bytes>`, затем `DONE`:

```json
{"answers": [{"id": "department", "logits": [4.68, -2.78], "probs": [0.9804, 0.0196],
              "temperature": 1.906, "actions": {"act": 1.0, "escalate": 0.0},
              "tokens": 96, "state_tokens": 50, "state_dropped": 0}],
 "input_tokens": 348, "engine_ms": 879.5}
```

`probs` — окончательные вероятности движка, по одной на каждый вариант в записи.
порядок; шлюз строит ответ Jev только из них (argmax для
`choice`, ожидаемый уровень для `score`, `probs[1]` для `noul`). `logits`,
`temperature` и `actions` (глава политики, например, действие/эскалация Лайи) являются
собственные записи движка о том, как он туда попал. Запись, от которой отказывается движок,
`ERROR <id> DECIDE_INVALID <field>: <reason>`, которые клиент получает в качестве
422 имя этого поля; `DECIDE_FAILED` — отказ самого движка (500).

**Реестр.** Семья с `modality="decision"` и
`FamilyCapabilities(decision=True)` в `c/family_registry.py` и способ
`resolve_model`, чтобы распознать свой контрольно-пропускной пункт (Laya: `rl_agent_config.json`
плюс `encoder/config.json`, с ключом `laya_<encoder model_type>`;
GLiNER2.5-Decide: `config.json`, `model_type` которого равно `extractor` плюс
`encoder_config/config.json`, с ключом
`gliner2_<architecture>_<encoder model_type>`). `checkpoint_files` называет
файлы `coli doctor` чеков. `coli serve`
и `coli web` затем подайте его, `coli info` и `coli plan` опишите его, и
`coli chat`/`coli run` отказываются от него с указателем на конечную точку. Решение
вместо головы в семейном чате — `DecisionHead` (Клеф: контрольная точка qwen36
с `joint_head_config.json` и `joint_head.safetensors`): семья остаётся
чат, `resolve_model` устанавливает `decision_head`, и ни в чем не отказывается.

**Тесты.** Крошечное приспособление, справочные ответы которого взяты из собственной модели.
пакет (`tools/make_laya_tiny.py`, `tools/make_laya_ref.py`,
`tests/test_laya_tiny.py`; `tools/make_gliner_decide_tiny.py`,
`tools/make_gliner_decide_ref.py`, `tests/test_gliner_decide_tiny.py`;
`tools/make_clef_tiny.py`, `tools/make_clef_ref.py`, `tests/test_clef_tiny.py`),
и приспособление за настоящими воротами (`tests/test_decision_serve.py`,
`tests/test_jev_sdk.py`).
