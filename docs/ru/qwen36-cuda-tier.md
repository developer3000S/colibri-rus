# qwen36: Экспертный уровень CUDA VRAM

Применяет концепцию размещения colibri («маршрут -> место -> перекрытие -> изучение») к
Qwen3.6-35B-A3B на уровень выше уровня диска GLM: все 10 240 экспертов живут
в оперативной памяти, **горячие** перемещаются в DEVICE_LOCAL VRAM в одном или
больше графических процессоров и вычисляются там через существующий общий бэкэнд CUDA
(`backend_cuda.cu` API экспертной группы — без нового бэкэнда).

> **Два движка.** Этот уровень также обслуживает Qwen3.8-Flash-Next (`c/qwen38.c`,
> [qwen38.md](qwen38.md#gpu-cuda-vram-expert-tier)) в потоковой передаче *fp8
> режим* (`qt_init_fp8`): не все эксперты живут в оперативной памяти, может быть `cap`
> меньше, чем количество экспертов, уровень копирует плиту e4m3 каждого эксперта и
> блок масштабируется, когда движок сообщает об этом и не сохраняет указателя на
> слот движка, и повышение происходит во время отчета, а не при теплом запуске.
> Все нижеописанное описывает режимы Qwen3.6, если не указано иное.


<a id="how-it-works"></a>
## Как это работает

- **Домашнее устройство:** эксперт `eid` живет на графическом процессоре `eid % n_gpus`; никаких дубликатов.
– **Размещение:** распределение тепла определяет, кто получит VRAM (семантика LFRU из
  `tier.h`, 25%+4 гистерезиса). Нагрев во время выполнения уменьшается вдвое каждые 1024 такта декодирования.
  поэтому долгоживущий процесс может заменить экспертов из старой рабочей нагрузки вместо
  навсегда заморозить свой первоначальный горячий набор. Параллельный **теплый старт** заполняет каждое устройство
  бюджет перед первым токеном — упорядочен по постоянной таблице нагрева
  (`HEAT_FILE`), если он присутствует, поэтому второй проход начинается с полной установки. Без одного
  требуется эксперт 0 каждого слоя, затем эксперт 1 и так далее, поэтому каждый слой
  имеет свою долю: в индексном порядке карта содержала целые слои (на Colab T4,
  слои 0–24 и часть 25), а фрагмент подсказки скопировал остальные слои.
  эксперты над шиной слой за слоем, через 25 слоев с шиной
  в режиме ожидания (подсказка Colab T4 из 512 токенов, после промпта из 64 токенов и его декодирования,
  читается на 14 % быстрее: `docs/experiments/qwen36-tier-spread-2026-10-27`).
- **Декодирование:** для каждого (токена, слоя) резидентные эксперты выдаются как асинхронные.
  группы на всех устройствах (`coli_cuda_expert_group_issue/take`); Видеопамять отсутствует
  вернуться к процессору и перекрыться с группами в полете, как и
  поделился эксперт. Размещение никогда не меняет маршрутизацию. С планарным int4 в оперативной памяти это
  решает, какое ядро вычисляет эксперта, и поэтому его последние цифры (см.
  жители следят за разговором»).
- **Память:** в контейнере **int4 gs64** эксперты остаются плоскими в int4.
  ОЗУ (`expert_ffn.h`, ядро CPU для промахов), одна копия размером
  на диске; уровень преобразует планарные байты в их пары, когда он организует
  загрузить. До #2090 сборка CUDA распаковывала каждый эксперт в int8 и сохраняла
  упакованный int4 рядом с ним для загрузки, в три раза больше байтов на диске,
  в то время как планировщик (`--auto-tier`) оценивал байты на диске.
  `QWEN_EXPERT_KERNEL=0` сохраняет эту историческую структуру (int8 для CPU,
  int8 копия резидентов VRAM упала при теплом старте). На **int8
  контейнер** каждый эксперт хранит свои веса int8 в оперативной памяти (#1341).
- **Любой размер ОЗУ:** с каждым экспертом слоя в ОЗУ (`cap` >= `n_experts`)
  уровень сохраняет указатели на слоты и самостоятельно меняет жителей
  (тикает LFRU, `QT_PREFILL_REPLAN`). При меньшем количестве он копирует эксперта, в то время как
  движок хранит его для CPU и затем решает, заслуживает ли он места в
  VRAM (самый холодный житель своего устройства уступает дорогу новичкужарче); Резиденты VRAM никогда не считываются в ОЗУ, поэтому два кэша суммируются.
  Затем теплый старт загружает только тех экспертов, которые он помещает в VRAM, а ОЗУ
  кэш заполняется по мере маршрутизации экспертов CPU. До #2090 `cap` ниже
  `n_experts` отключил ярус, багажник включил.
- **Жара:** каждый разгромленный эксперт засчитывается один раз за токен, попадание в `qt_issue`,
  промах, когда движок передает свои байты (`qt_note`). Хиты используются для подсчета
  только через ту заметку, которая в режиме копирования (и на Qwen3.8) никогда не приходит
  житель: жители остались в той жаре, с которой приехали, и любой
  новичок потеплее, чем тот, который их выселил.
- **Нет экспертов, все равно ствол:** смешанная раскладка (int4gate/up, int8
  вниз), эксперты int8 с сгруппированными шкалами и `COLI_PLACE` `experts=cpu` сохраняют
  Эксперты по процессорам и устройствам занимают плотный ствол внизу.

<a id="usage"></a>
## Использование

```bash
make -C c qwen36 CUDA=1 CUDA_ARCH=native   # NVCC=/usr/bin/nvcc on distro CUDA
COLI_CUDA=1 COLI_GPUS=0,1 HEAT_FILE=heat.bin CUDA_EXPERT_GB=auto \
OMP_NUM_THREADS=<physical cores> OMP_WAIT_POLICY=ACTIVE OMP_PROC_BIND=close \
SNAP=<container> N_NEW=200 ./c/qwen36 256 4 prompt.txt
```

<a id="windows-cuda_dll1"></a>
### Windows (CUDA_DLL=1)

MinGW не может напрямую связать CUDA, поэтому бэкэнд встроен в `coli_cuda.dll`.
с nvcc + MSVC и `qwen36.exe` достигает его через `backend_loader.c`.
`CUDA=1` изначально отклонен в Windows. Из промпта *x64 Native Tools*
с MSYS2 `mingw64\bin` и `usr\bin` на `PATH`:

```cmd
cd c
make cuda-dll CUDA_ARCH=sm_89
make qwen36.exe CUDA_DLL=1 ARCH=native
set COLI_CUDA=1
set COLI_GPUS=0
set CUDA_EXPERT_GB=auto
qwen36.exe <same arguments as the CPU build>
```

Оставьте `coli_cuda.dll` рядом с `qwen36.exe`, созданным на основе той же кассы, и
каталог `bin` набора инструментов CUDA на `PATH` для `cudart`. Линия запуска
`[gpu] MoE experts -> CUDA VRAM tier` подтверждает, что уровень активен; без этого
запуск осуществляется только с использованием процессора.

`cap` (argv[1]) — кэш ОЗУ на каждый уровень для сборки CPU, любой размер.
(см. «Любой размер ОЗУ» выше; до #2090 любой `cap`, но `n_experts` переключал
ярус, включая более крупный); `--auto-tier` размер его из оперативной памяти. `COLI_TIMERS=1`
печатает пофазные тайминги и уровневую телеметрию.

<a id="placement-where-the-dense-trunk-goes-coli_place"></a>
## Размещение: туда, где идет плотный ствол (`COLI_PLACE`)

Уровень перемещает разгромленных экспертов. В этой гибридной модели это *маленький*
часть токена: 40 слоев × топ-8 экспертов, ~190 МБ int8 на токен
81 % попаданий в плотный ствол -- внимание, прогнозы DeltaNet,
общий эксперт, lm_head – **1,8 ГБ данных int8, прочитанных на каждом токене**. Уходя
магистральный канал CPU — вот почему для карты емкостью 6 ГБ частота попаданий перестает иметь значение
(#1040): графический процессор выполняет дешевую работу.

По умолчанию движок теперь сам размещает багажник. Прежде чем уровень примет решение
бюджет, движок предлагает каждый компонент багажника со своим размером и уровнем
оценивает их по сравнению с экспертами, которых они могли бы заменить, в **байтах, сэкономленных на
шины памяти на токен, на байт VRAM**. Компоненты с их размером int8
на Qwen3.6-35B-A3B (скрытые 2048, 30 уровней DeltaNet и 10 уровней внимания):

| компонент | что | за слой | всего |
|---|---|---|---|
| `lmhead` | выходная головка, один раз | | 508 МБ |
| `dnproj` | DeltaNet in_proj qkv++ z, слитый | 25,2 МБ | 755 МБ |
| `dnout` | DeltaNet out_proj | 8,4 МБ | 252 МБ |
| `attnproj` | внимание q, k, v, o (один элемент, четыре матрицы) | 27,3 МБ | 273 МБ |
| `shexp` | ворота общего эксперта, вверх, вниз (предлагается только с `Q36_OFFER_SHEXP=1`, см. ниже) | 3,1 МБ | 126 МБ |

Заказ на предложение является приоритетом размещения, если бюджет исчерпан: `lmhead`,
затем `dnproj`, `dnout`, `attnproj`, `shexp`, каждый в порядке слоев, поэтому частичный
размещение - целые слои. `dnout`, `attnproj` и `shexp` были добавлены после
точка данных M10 в # 1652 показала неразгруженный плотный путь в качестве потолка
на процессоре без AVX2; измерено на 16-ядерном процессоре, из 37,5 мс на декодирование
расходы токенов в стеке DeltaNet 23,4 — это входные прогнозы, 8,3 —out_proj и норма, 3.3 свертка и 2.4 повторение - матмулы,
не повторение, а стоимость багажника. Они обслуживаются из VRAM на
декодирование (по одному GEMV); пакетная обработка сохраняет пакетный пакет CPU.

Размещенные входные проекции DeltaNet (`dnproj`, qkv++z) также работают как CUDA
пакеты во время предварительного заполнения: не более 256 строк на вызов, с поэтапным вводом/выводом
ограничен 32 МБ (или одной строкой, если она больше). Свертка и
рекуррентное состояние по-прежнему продвигает один токен за раз. Недоступно или не удалось
проекция использует существующий путь CPU для каждого токена. Это меняет количество отправлений,
не порядок повторного обновления; это не полная реализация DeltaNet на графическом процессоре.

**Измерено, а не предполагается.** В приведенном ниже правиле ценообразования предполагается, что графический процессор отвечает
GEMV быстрее, чем процессор. Четыре Tesla M10 (sm_50, без тензорных ядер, четыре
графических процессоров на одной плате PCIe) в #1652 сказано иначе: каждый эксперт
Резидент VRAM, размещение магистрали замедляло работу каждого компонента (lm_head 68,8 мс
против 41,7 на CPU, 30 проекций DeltaNet 106 против 66) и
декодирование упало с 3,56 до 2,68tok/s. Таким образом, движок измеряет перед загрузкой
байт магистрали: одна входная проекция DeltaNet синхронизируется в обоих направлениях на
устройство, на котором он будет проводиться (десять GEMV, лучший результат из трех раундов, после разминки),
одна строка `[place] probe:` сообщает оба раза, а если графический процессор теряет всю
автоматическое размещение отменяется (`[place] trunk stays on the CPU`) и его
байты возвращаются в экспертный бюджет перед теплым стартом. На процессоре десятка
GEMV считывают проекции десяти слоев, а декодирование считывает каждый один раз:
одна проекция размером 16 МБ, прочитанная десять раз, остается в большом L3 и рядом с RTX PRO
6000 и EPYC 9B45 (три L3 по 32 МБ) таким образом оказались в пределах 10% от карты.
и привязал его под nsys. Эксперты следят за
(`[qtier] the experts stay on the CPU too`), когда их пособие является автоматическим:
уровень вычисляет постоянного эксперта с тем же GEMV int8 и циклическим обходом
через PCIe, и уровень ожидает своей доли. На GTX 1650 Max-Q (#2211; 0,900
мс на карте против 0,306 на CPU) тир с десятой частью экспертов
резидентное потерянное декодирование (9,2 против 10,9 tok/s) и предварительное заполнение (14 против 46).
`CUDA_EXPERT_GB=<GB>` сохраняет их на устройстве. Только автомат
размещение подвергается сомнению: стоит рукописное `COLI_PLACE`, и
`COLI_TRUNK_PROBE=0` пропускает зонд. Правило ценообразования:

- плотный компонент читается каждый токен: 1,0 на байт;
- перенаправленный эксперт считывается с вероятностью, что к нему маршрутизируется токен - его тепло
  поделиться, когда существует `HEAT_FILE`, `topk / n_experts` в противном случае — и процессор
  Резервный вариант считывает слот int8, что в два раза превышает объем видеопамяти эксперта int4: 2·p на каждый
  байт.

Компонент попадает в устройство с наибольшим пространством, если его значение превосходит значение
самых холодных экспертов он выталкивает. Без нагрева этот хвост стоит 0,06 за байт.
на 35Б и багажник всегда выигрывает; с жарой, карта, предельный эксперт которой равен
маршрутизация более чем на каждый второй токен содержит своих экспертов. Размещенные байты выходят
экспертного бюджета этого устройства, и каждое решение печатается в виде строки `[place]`.

| `COLI_PLACE` | поведение |
|---|---|
| не установлено или `auto` | автоматический, как указано выше |
| `off` | ничего не размещено: только эксперты (поведение до этого) |
| `lmhead=0,dnproj=0:20+1:20,experts=0` | рукописный список (инструмент измерения); выполнил как написано, транковые байты все равно списаны в бюджет || `dnout=0,attnproj=0,shexp=0` | та же форма списка для новых компонентов; любое из пяти имен, на каждый слой или разделенное с помощью `+` |

Первая калибровка, один Quadro RTX 4000 (8 ГБ), контейнер int4 на строку, 200 токенов
декодирование, одно и то же промпт, выходные данные идентичны во всех четырех прогонах:

| | `off` | `auto` |
|---|---|---|
| багажник в VRAM | -- | lm_head 0,47 ГБ + 30 dnproj 0,70 ГБ |
| эксперты-резиденты | 4,391 | 3,595 |
| холод: процент попаданий / tok/s | 44 % / 8,64 | 36 % / **9,62** |
| теплый: процент попаданий / tok/s | 95 % / 9,63 | 90,6 % / **12,92** |

| RTX 3070 (8 ГБ) одна, теплая | 93,6 % / 11.09 | 88,4 % / **16,55** |
| обе карты, эксперты по обеим, теплые | 100 % / 10,79 | 100 % / **14,80** |
| ссылка: Ollama 0.32.5, та же модель Q4_K_M, та же подсказка, обе карты (57 % CPU / 43 % ГП, 11,8 ГБ видеопамяти) | 20,3 тепло (21,3 холодно) | |

Теплый спор имеет значение: при 95 % вероятности успеха маргинальный эксперт
настолько ценен, насколько это возможно на этой карте, и сундук все равно выигрывает с преимуществом на треть.
Показатель результативности падает всего на 4,4 балла для на 796 жителей меньше, потому что
уволенные эксперты — самые холодные представители теплого порядка — именно те,
россыпь оценена как дешевая. Относительный выигрыш растет с увеличением доли ствола в
токена: +34 % на Quadro, +38 % при бюджете 5 ГБ, +49 % на 3070. (Ан
в более ранней версии этой таблицы имена двух карт были заменены местами: заказы CUDA
устройства быстрее всего, `nvidia-smi` на автобусе, и я прочитал не тот.)
Все шестнадцать прогонов этой калибровки давали побитово-идентичный текст. Против
Олламе на том же боксе разрыв сокращается с 1,5× (14,97 против 22,4 в августе, два
карты, установленные вручную) до **1,23× на одной карте емкостью 8 ГБ** (16,55 против 20,3) --
с Олламой, удерживающей плотные веса на уровне ~ 0,56 байта на вес (Q4_K_M)
против этого движка 1.0 (int8) и с использованием обеих карт.

шагает по каждому слою (более медленный `take()` закрывает цепочку), поэтому `off` на двух картах

в этой версии багажник распределяется по свободному пространству и оставляется экспертам по обоим --
достигает 14,80, где записанное вручную разделение R4 (`experts=0,lmhead=0,
dnproj=0:20+1:20`: эксперты на ОДНОЙ карте, транк через обе) достигает 17.11. Вкл.
две неравные карты — список все равно выиграет; следующая версия россыпи должна
выучить этот урок (эксперты на одной карте, багажник на другой), а не
напишите для этого.

Пиковый RSS примерно на 2 ГБ выше при `auto`: копии int8 на стороне хоста остаются
Резервный процессор процессора. Известно, еще не рассмотрено.

**Любая плотная матрица по названию.** Таблица предложений не ограничивается `lmhead` и
`dnproj`: движок предлагает всё, что хочет, с помощью `qt_trunk_offer(name,
слой, байты)` before `qt_init`, asks `qt_place_of(имя, слой)` после этого,
и передает размещенные матрицы как строки int8 с помощью
`qt_dense_init(q, scales, I, O, device)`, который возвращает дескриптор;
`qt_dense_matmul(handle, y, x, I, O)` отвечает на один GEMV из VRAM и возвращает 0
(CPU с этого момента), если серверная часть выходит из строя. Вызовы qwen36 остаются тонкими
обертки над тем же механизмом. Qwen3.8 использует его для всего своего ствола -- 553
матрицы, 4,0 ГиБ int8 на одной карте ([qwen38.md](qwen38.md), «GPU») — иименно здесь резидентный плотный matvec бэкэнда получил собственную промежуточную обработку.
буферы: `coli_cuda_matmul` используется для совместного использования буферов устройства `x`/`y` с
экспертная группа, которая работает асинхронно в собственном потоке между `qt_issue`
и `qt_take`. В этом окне выдается плотный GEMV (общий эксперт Qwen3.8)
перезаписал входные и выходные данные группы в процессе выполнения — никакой ошибки CUDA, только
неправильные цифры. qwen36 никогда не вызывал плотный путь внутри этого окна, поэтому его
результаты не пострадали.

<a id="the-deltanet-layer-on-the-card-q36_dn_gpu1"></a>
## Слой DeltaNet на карте (`Q36_DN_GPU=1`)

Когда транк находится в VRAM, CPU по-прежнему тратит около 8 из 39 мс на каждый токен на
свертка тридцати слоев DeltaNet, нормы L2, повторяемость и закрытая норма
(`dn-sub: proj 7.9 | conv 3.0 | l2n+rec 2.4 | norm+out 2.8`). Ничего из этого не
арифметика - свертка токена составляет 33 тыс. умножений-сложений, повторение 32
внешние продукты 128 x 128 – это путь туда и обратно: результат in_proj
спустился на хост, там запустилось повторение, его вывод снова увеличился на
out_proj, четыре копии и их синхронизация на слой, тридцать слоев
за токен.

`Q36_DN_GPU=1` сохраняет слой на карте. Для каждого уровня DeltaNet, чей
in_proj (`dnproj`) и out_proj (`dnout`) россыпь, поставленная на одно и то же устройство,
кольцо конв, рекуррентное состояние (32 x 128 x 128 f32, 2 МБ на слой, 63 МБ
для 35B), и туда же идут веса конв/норм, и запускается токен декодирования.
слой до конца в одной цепочке устройств (`coli_cuda_dn_step`): x up, in_proj
GEMV, причинно-следственная связь + SiLU, по значению, возглавляющему нормы L2 (двойной, eps внутри
квадратный корень как на CPU), распад, дельта относительно распавшегося состояния,
обратная запись, `out = q^T S` по обновленному состоянию, закрытый RMSNorm с
`silu(z)`, out_proj GEMV, выход вниз. Двое ворот (проекции `a`, `b`, 32
выходные данные каждый) остаются в CPU и передаются как параметры ядра. Одна загрузка и
одна загрузка по 8 КБ на слой, состояние никогда не пересекает шину.

Хост-массивы остаются владельцем государства. Копия карты представляет собой кэш, который
либо свежий (содержит то, что есть на хосте), либо впереди него; шаг процессора -- a
подсказка (`S > 1` сохраняет пакетный путь CPU), уровень, проекции которого
не на одной карте, шаг после неудачного шага графического процессора — сбрасывает состояние вниз
сначала снимок для `--pin` извлекает все слои, `reset_recurrent` и булавку
восстановить сделать копию карты недействительной. Итак, `--pin`, повторное использование префиксов и
Диагностика в стиле `QT_UPLOAD_SYNC` продолжает работать без изменений. Автоматический
Placer теперь помещает `dnout` слоя на устройство, на которое он перешел `dnproj`, когда это
у устройства есть место, поэтому под `auto` подходит каждый уровень DeltaNet; а
рукописный список должен содержать два документа на одной карточке (обратите внимание, что разделенный список
например, `dnproj=0:20+1:20` учитывает слои *модели* 0..39, а не слои DeltaNet).

зеркало на слой внимания с водяным знаком (`kv_valid`), шаг от `pos_base`

на устройстве во время работы цепочки: копия хоста возвращается до того, как что-либо будет прочитано

записывает его туда (сброс: на устройстве заполняются нули; восстановленный снимок: загрузка). А
спекулятивная проверка копирует состояние после каждой строки, кроме последней, в устройство
слот, свертка и повторение разделяются на одну отправку на копию (те же биты),

рекуррентное состояние, перестраивает его на CPU из записи префикса (значение CPU, необходимое для предварительного заполнения
работа; строки KV уже принадлежат хосту) и оттуда запускаются на CPU, как Vulkan
цепь делает. `COLI_CUDA_CHAIN_FAULT=n` имитирует потерю в n-м кадре.

### Разгромленные эксперты в кадре (`COLI_CUDA_CHAIN_MOE`, по умолчанию включено)

Цепочка выше по-прежнему завершала свой кадр на каждом уровне MoE: логиты маршрутизатора отключены,
маршрутизация хоста, группы уровней и доля CPU, резервная копия суммы. На шаг вверх
до 8 строк (декодирование, проверка) кадр теперь сам маршрутизирует и вычисляет экспертов, как
цепочка Vulkan делает (docs/vulkan.md, «Перенаправленные эксперты в кадре»):

- `cc_route` (`cuda_chain.cu`, порт `chain_route.comp`): softmax, с ограничением группы
  top-k, перенормировка, нижний эксперт при ничьей, по одному блоку в строке.
- `cc_moe` (`backend_cuda.cu`: `moe_gu_k`, `moe_dn_k`, `moe_sum_k`): каждый (строка, слот)
  пара, чей эксперт содержится в таблице, ворота и вверх, затем вниз, деформация на каждую выходную строку, в
  форматы яруса (1 ряд int8, 2 ряда int4, 4 int4 с масштабом 64, 8 fp8 с
  его блочные масштабы 128 x 128); затем сумма каждой строки в порядке уровня (хост
  промахи, затем слоты устройства в порядке ранга).- Таблица: по одному `CcExpert` на эксперт каждого слоя, адреса устройств
  резидентские гири и весы (`qt_chain_resident`, стол `tensor_dev`), построенные
  снова, когда изменилась резиденция уровня (`qt_chain_epoch`). Уровень сохраняется за
  вперед (`qt_chain_hold`): выселение сразу очищает флаг и перемещает эпоху, но
  никакой обмен не записывает в резидентные буферы до тех пор, пока не будет завершена пересылка.
- Слой, все эксперты которого находятся в таблице, не имеет шага хоста, а его идентификаторы маршрутов и
  веса остаются на устройстве во время кадра: идентификаторы каждого слоя сводятся в один
  копия в конце для книг ниже. Слой с некоторыми
  в другом месте (VRAM было мало) сигнализирует хосту, когда его маршруты и строки не работают
  (`cc_signal`: однопоточное ядро записывает слово памяти хоста после ограничения системы).
  Хост вычисляет слоты, которых не хватает таблице, поскольку промахи уровня всегда были
  (`qt_cpu_misses`: кэш ОЗУ, диск), пока устройство вычисляет свои собственные, записывает
  его строки в буфер UP и его слово; устройство ожидает слова (`cc_wait_host`)
  перед суммой. Хост обслуживает слой после записи следующего, поэтому устройство
  ставит этот слой в очередь, когда приходит ответ. Поездка туда и обратно стоит около 8 долларов за человека.
- Книги, которые сохранил шаг хоста (нагрев уровня, попадания и тик LFRU: `qt_chain_count`;
  резидентская коллекция; количество горячих выводов) следует из идентификаторов после кадра, с
  строки K/V в кэш хоста.

Блок запроса (более 8 строк) также запускает маршрутизируемые эксперты в кадре, слой за слоем.
слой, где в таблице хранятся все эксперты этого слоя: `cc_moe` сортирует чанк
слоты по эксперту (счет, смещения и плитки из 64 рядов, место каждого слота) и запускает каждый
строки эксперта через ядра тензора (`tcg_moe_k`: ворота и вверх в silu(g) * u, затем
вниз), затем сумму каждой строки в порядке ранга. Слой с экспертами в другом месте или подсказка
который перепланирует жителей (`QT_PREFILL_REPLAN=1`), сохраняет шаг хоста в этом куске.

Плотные матрицы быстрого фрагмента проходят через один и тот же GEMM с тензорным ядром.
(`tcg_dense_k`, от `coli_cuda_tensor_gemm_async` для более чем 8 строк), где блок
ядро тратило 256 потоков на каждый выход: фрагменты TF32 на sm_80 и выше, входы
округляется до TF32 (10-битная мантисса, диапазон fp32), коды int8 и int4 располагаются точно
с масштабом строки после суммы, int4 на 64-кратный масштаб ее группы в соответствии с постановкой, суммы
в фп32. По сравнению с эталоном fp64 выходные данные находятся в пределах от 2e-4 до 4e-4 (относительно
самый крупный); собственные эксперты CPU квантуют свои входные данные в int8. `COLI_CUDA_TC_GEMM=0`

### Жители следят за разговором (`COLI_CUDA_CHAIN_PROMOTE`, включено по умолчанию)

Теплый старт заполняет карту из теплового файла: маршруты истории. Разговор о
другая тема упускает это из виду - о RTX 3070 (2748 из 10240 экспертов Qwen3.6-35B)
подсказка истории обнаружила 44,5 % маршрутов декодирования в наборе, обученном на вопросе о МО
маршрутизация, против 82% для самого этого вопроса - и каждый промах - это строка, которую вычисляет CPU
пока устройство ждет (`qt_cpu_misses`, около 0,1 мс каждый).

После шага размером с декодирование цепочка запрашивает повышение на уровне (`qt_chain_promote`): до
`COLI_CUDA_CHAIN_PROMOTE` (4) промахов шага устранено не менее `COLI_CUDA_CHAIN_PROMOTE_MIN`
(2) раза в этом разговоре стоит самый первый. Ценность эксперта – его пыл.
маршруты истории, обветшавшие, плюс этот разговор (`qt_chain_count` для жителей,
`qt_note` за промахи) -- плюс еще раз маршруты этого разговора, чтобы разговор
от истории обгоняет на десятки токенов. Каждый использует буферы устройства
самый холодный из 64 жителей, выбранных случайным образом на его устройстве, где он очищает доступ на уровень
маржа (`tier_should_promote`: четверть и четыре над жертвой; то же правило, что и LFRU
тик, который продолжает работать один раз из 16 токенов). Цепочка выстраивает байты оперативной памяти новичка
в слот с блокировкой страниц (`qt_chain_promote_stage`: поскольку ОЗУ удерживает их для int8 и
упорядоченные попарно строки int4 или преобразованные из плоских блоков int4 в подписанные пары устройства)
и оттуда в буферы жертвы в потоке копирования (`cc_host_up`, шесть копий за одну копию).
эксперт), пока выполняются следующие шаги. Ветка загрузки уровня не принимает участия:
его синхронные копии берут блокировку драйвера из другого потока, в то время как кадр цепочки
ждет хоста (`cc_wait_host`), и это зашло в тупик внутри драйвера на 3070.
Как только копии доставлены (`cc_host_up_done`, проверяется после следующих шагов), уровень передает
буферы для нового пользователя (`qt_chain_promote_done`), и он является резидентным; жертва рассчитывает на
процессор с шага после его вытеснения (его копия int8 перестроена `tier_rebuild_evicted`
до этого вперед, параллельно, где `QWEN_EXPERT_KERNEL=0` нужен; плоский int4 сохраняет
его блоки оперативной памяти). Таблица цепочки принимает изменения запись за записью.
(`qt_chain_changes`: уровень фиксирует каждое изменение резидентности; считывается вся таблица
снова только там, где уровень потерял счетчик), и подготовленная таблица фрагмента запроса следует, когда
кусок нуждается в этом.

## Жители следуют подсказке (`QT_PREFILL_REPLAN=1`)

Теплый старт заполняет VRAM из теплового файла, т.е. из того, что подсказывало ранее
перенаправляется, и галочка LFRU затем корректирует одного эксперта на шестнадцать токенов и
устройство. Для подсказки по новой теме, которая требует тысяч токенов наверстать упущенное:
измерено на 35B с помощью теплового файла, накопленного по шести другим подсказкам,
декодирование свежего промпта достигает VRAM в 56-63 % случаев при резидентности 37 %, холод
старт 38%, и файл жары из *того же* промпта 89-91% -- жара
теплый старт — это оракул для повторного запроса и догадка незнакомца для нового
один.

Предварительное заполнение знает лучше. Его маршрутизация аналогична маршрутизации этого промпта: офлайн,
статический набор экспертов B для каждого уровня, выбранный из собственного количества предварительно заполненных подсказок
покрывает маршрутизацию декодирования гораздо лучше, чем тепловой файл при том же бюджете
(протянутые подсказки, четыре темы):

| B на слой (всего 256) | тепло из других подсказок | собственный счетчик предзаполнений | оракул (собственный декод) |
|---|---|---|---|
| 32 | 0,217 | **0,421** | 0,566 |
| 64 | 0,423 | **0,613** | 0,777 |
| 96 (~доля карты 8 ГБ) | 0,593 | **0,741** | 0,890 |
| 128 | 0,725 | **0,825** | 0,952 |
