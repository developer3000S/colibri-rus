### Этап 3. Ограничения и подход к разработке металла [2026-07-31] ✅ ЗАВЕРШЕНО

Ключевые ограничения Metal, которые следует применять при написании ядер:

- Единая память, нулевое копирование — без загрузки хоста/устройства, постоянные буферы, вычисления на месте.
- Размеры групп потоков: 32/64/128/256 (никогда 1024) — всегда проверяйте maxTotalThreadsPerThreadgroup.
- Группы SIMD ≠ деформации — используйте simdgroup, simd_sum(), simd_broadcast(), simd_prefix_exclusive_sum(), никогда не принимайте ширину 32
- Память группы потоков ограничена — ядра, требующие большого внимания, требуют перепроектирования, а не прямого перевода.
- **Выравнивание буфера: alignas(16) в структурах параметров — смещение дает неверные значения, а не приводит к сбою.
— Адресные пространства строгие — нельзя смешивать устройство, константу, поток и группу потоков; нет арифметики указателей через пробелы
— константа для параметров, доступных только для чтения — компилятор генерирует гораздо лучший код
- Никаких глобальных барьеров — вместо этого используйте последовательные отправки в одном и том же командном буфере.
- Индексы буфера должны точно совпадать — [[buffer(N)]] ↔ setBuffer(..., index: N), в противном случае мусор- Конвейеры: компилируйте один раз, используйте повторно навсегда.
- Одно устройство, одна очередь команд на всю жизнь
- Один командный буфер, много ядер — минимизируйте количество CB
- Режимы хранения: общий (простой, унифицированный), частный (более быстрый, только для графического процессора, требует явной передачи)
- Компилятор агрессивен — отключите -fast-math для числовой корректности.
- Хранение FP16, накопление FP32 — осторожно перемешивайте, чтобы избежать давления приводки и числового отклонения.
- Непрерывный доступ = быстрый, пошаговый = медленный — сохранение объединенных тензорных макетов из Vulkan.
- Профиль в Инструментах, не гадайте

### Этап 7b — Индексатор DSA порта (Ic + k_idx) [2026-07-31] ✅ ЗАВЕРШЕНО

DSA (Dictionary Sparse Attention) выбирает подмножество Top-K строк кэша на шаг декодирования,
чтобы в оценке внимания участвовали только наиболее релевантные контекстные позиции.
Этап 8. Он работает с отдельным кэшем «индексатора» размером `index_hd` (обычно 64–256),
что намного дешевле полного К/В.

**Зависимость от фазы 8:** Оценка внимания фазы 8 потребляет `k_idx` (выбранный DSA
должности). Без DSA внимание охватывает весь контекст — правильно, но медленнее.Без k_idx Фаза 8 по-прежнему работает в режиме обхода (полный контекст).

**Новые поля конфигурации:**
| Поле | Ключ JSON | Тип | Цель |
|---|---|---|---|
| `index_hd` | `index_hd` | интервал | Скрытый индексатор (ширина кэша на каждую позицию) |
| `index_nh` | `index_nh` | интервал | Количество головок запросов индексатора |
| `index_topk` | `index_topk` | интервал | Максимальное количество позиций для выбора в строке декодирования |
| `theta` | `rope_parameters.rope_theta` | плавать | Базовая тета RoPE (по умолчанию 10000) |
| `idx_type[128]` | `index_layers` (массив 1-индексированных идентификаторов слоев) | int8_t | Режим DSA на уровне: 1 = полный, 0 = общий |

`idx_type` по умолчанию имеет значение «полный» (1) для всех слоев MLA, если `index_hd > 0` — явное переопределение `index_layers`.

**Поля «Новый слой (объединение Mla)» — выделены только для полных слоев:**
| Поле | Тип | Цель |
|---|---|---|
| `wk` | `W` | Ключевая проекция `[index_hd x hidden]` — осколок `self_attn.w_k.weight` |
| `wq` | `W` | Проекция запроса `[index_hd x q_lora]` — осколок `self_attn.w_q.weight` |
| `wp` | `W` | Проекция веса `[index_hd x hidden]` — осколок `self_attn.w_p.weight` |
| `knw` | `float*` | Нормальные веса ключевого слоя `[index_hd]` — шард `self_attn.kn_w` |
| `knb` | `float*` | Ключевые отклонения от нормы слоя `[index_hd]` — осколок `self_attn.kn_b` |
| `Ic` | `float*` | Кэш индексатора `[max_t * index_hd]` — расположен в `kv_alloc()` |

**Новые поля модели:**
| Поле | Тип | Цель |
|---|---|---|
| `dsa_nsel` | `int*` | Выбор k_idx для каждого слота имеет значение `[S]` |
| `dsa_sel` | `int*` | Выбранные индексы k_idx для каждого слота `[S * index_topk]` |
| `dsa_scap` | `int64_t` | Выделенная мощность для `dsa_sel` |

**Путь предварительного заполнения (CPU, подключенный к `mla_forward()`):**
1. Для каждого токена `t` в `[pos0, pos0+C)` проецируйте от `x[t]` до `a->wk` через `w_matmul()` → `ikd [index_hd]`.
2. `rmsnorm_(ikd, ikd, a->knw, index_hd, eps)` — по месту RMSNorm по индексатору K
3. `dsa_rope(ikd, pos0+t, qk_rope, theta)` — верёвка_interleave на первом `qk_rope` затемняется
4. Напишите в `a->Ic + (pos0+t)*index_hd`

**Путь декодирования (CPU, помощник `dsa_score_single()` готов — ожидается подключение):**
1. Проект с `QR[s]` по `ix_wq[layer]` для производства `qi [nh*index_hd]` (через `w_matmul`)
2. RoPE на `qi` головках (RoPE с чередованием на каждую головку в позиции декодирования)
3. Проект с `x[s]` по `ix_wp[layer]` для создания скаляров веса `w32 [nh]`.
4. `dsa_score_single()` — косинусное расстояние по нескольким головкам: для каждой строки кэша `t`,
   вычислить `Σ_h w32[h] * ReLU(qi·Ic[t] / √hd)`, масштабировать на `1/√nh`
5. Выбор Top-K: `qsort` на `DsaEntry[]` (оценка+индекс), извлечение индексов Top-K.
6. Вывод: `k_idx[]` — массив выбранных позиций.

**Подключение к кимик3 (ЗАВЕРШЕНО):**
- `load_cfg()`: поля DSA, загруженные из JSON (`index_hd`, `index_nh`, `index_topk`, необязательные `index_layers`, `rope_theta`)
- `model_init()`: веса DSA загружаются из осколков только для полных слоев (`wk`, `wq`, `wp`, `knw`, `knb`)
- `kv_alloc()`: буфер `Ic`, выделенный на полный слой при `[max_t * index_hd]`
- `model_state_reset()`: `Ic` очищено — Металлический путь: `coli_metal_kv_clear(Ic)`, путь CPU: `free(Ic)`
- `mla_forward()` предварительное заполнение: запись Ic проводная после записи в кэш L/R KV; охраняется `index_hd > 0 && idx_type[li]`
- Помощник CPU `dsa_rope()`: веревка_interleave в первых измерениях `qk_rope`, встроенный кэш, на месте в `[index_hd]`
- Помощник CPU `DsaEntry` + `dsa_entry_cmp_desc()`: структура оценка+индекс, используемая для выбора `qsort` top-K
- Помощник CPU `dsa_score_single()`: многоголовочное ядро косинусного расстояния — для каждой строки кэша `t`,

**Ожидается подключение проводки (остается этап 7b):**

  передает `dsel/dnsel` для отфильтрованного подмножества сигналов (зеркала colibri.c:2826 шаблон)
- Оценка DSA для листовой балки. Металлическое ядро (в будущем: распараллеливание `dsa_score_single` по позициям кэша)

## Этап 8 — Внимание KDA порта

Вероятно, это самая крупная оставшаяся задача. Разбейте на независимые подфазы, каждый из которых сравнивает производительность Metal с процессором.

KDA (Kimi Delta Attention) — это вариант внимания модели в пространстве состояний, используемый в 69 из 93 слоев Kimi K3.
Каждый слой KDA имеет: квантованные проекции (q, k, v, g, o), f32 проекции затухания низкого ранга (fa, fb, bp),
conv1d по глубине (conv_q, conv_k, conv_v), нормализация L2 для каждой головы и последовательная обработка каждого токена.
цикл повторения состояния (распад, обновление, слияние для состояния [heads × hd × hd]).

**Поля конфигурации (из `Cfg`):**
| Поле | Значение для Kimi K3 | Цель |
|---|---|---|
| `kda_proj` | 2048 | Проекция dim на q/k/v |
| `kda_heads` | 96 | Количество руководителей КДА |
| `kda_hd` | 128 | Голова тусклая (2048/96*6,4/128? Нет — hd=proj/голов*фактор) |
| `conv_k` | 4 | Ширина ядра Conv1d |
| `gate_lb` | 0,068 | Нижняя граница основания ворот |

**Структура `Kda` (для каждого слоя):**
| Поле | Тип | Цель |
|---|---|---|
| `q`, `k`, `v`, `g`, `o` | `W` | Квантованные проекции (fmt=0/1/4) |
| `fa`, `fb` | `float*` | Распад низкорангового f32: `[kda_hd × hidden]`, `[kda_proj × kda_hd]` |
| `bp` | `float*` | Бета-проекция f32: `[kda_heads × hidden]` |
| `dt`, `A`, `onw` | `float*` | dt_bias `[kda_heads × kda_hd]`, exp(A_log) `[kda_heads]`, o_norm `[kda_hd]` |
| `conv_q`, `conv_k`, `conv_v` | `float*` | Отводы глубинные `[kda_proj × conv_k]` |
| `metal_fa`, `metal_fb`, `metal_bp` | `void*` | Металлические тензорные обертки для f32 GEMM (Фаза 8.1) |

**Порядок выполнения в течение `kda_forward()`:**
1. **Пакетные прогнозы** (токены C): `w_matmul` для q, k, v, g; `k3_matmul_f32` для fa, fb, bp — ограничено t=0
2. **Период для каждого токена** (t=0..C-1; последовательный из-за повторения состояний):
   а. Conv1d по глубине + ворота SiLU (q, k, v каждый: сдвиг окна `[K]`, точечные касания, умножение SiLU)
   б. Нормализация L2 для каждой головы (q, k каждый: вычислить норму по `[hd]`, разделить; q добавляет `qscale = 1/√hd`)
   в. Проверка состояния каждой головки (96 головок параллельно через OMP, каждая выполняет `[hd × hd]` матрично-векторную операцию):
      - Применить ворота через SiLU: `qg[i] = qn[i] * silu(rgt[h*hd + i])`
      - Вычислить альфу: `alpha[i] = exp(gate_lb * sigmoid(A[h] * (graw[h*hd+i] + dt[h*hd+i])))`
      - Состояние распада: `s[h][i][j] *= alpha[i]` для каждого `[hd × hd]` ряда.
      - Накопить k: `kS[j] += kn[i] * s[h][i][j]`
      - Вычисление ВТ: `vt[i] = (vh[i] - kS[i]) * beta[h]`
      - Развернуть состояние: `s[h][i][j] += kn[i] * vt[j]`
      - Объединить вывод: `oh[j] += qn[i] * s[h][i][j]`
   д. RMSNorm на голову + сигмовидный вентиль на выходе: `on[h*hd+i] = oh[i] * rmsnorm_factor * onw[i] * sigmoid(gp)`
3. **Пакетный вывод**: `w_matmul(out, on, &a->o, C)`

**Анализ целей по отправке металла:**
- **Проекции (q, k, v, g, o)**: Металл уже отправлен через `w_matmul` (Фаза 5). 5 квантованных матмулов, O(S × скрытый × проект).
- **Низкий ранг (fa, fb, bp)**: Металл отправляется через `k3_matmul_f32` (Фаза 8.1). 3 матмулы f32, O(S × скрытый × hd).
- **Conv1d+SiLU**: Металл отправляется через `kda_conv_silu` (Фаза 8.3). O(C × P × K), 3 отправки/токен.- **Нормализация L2**: только процессор. О(С × Н × hd). За токен, за голову. Можно пакетировать по C, но не по H без реструктуризации.
- **Очистка состояния**: только процессор. О(С × Н × hd²). Узкое место ядра. Последовательно по токенам, параллельно по головкам.
- **RMSNorm + Gate**: только CPU. О(С × Н × hd). Легкий, объединенный в цикл состояний.

### 8.2 — Повторение состояния внимания ✅ ВЫПОЛНЕНО

Для Kimi K3 KDA «показатель внимания» — это повторяемость состояний для каждой головы: затухание, обновление, слияние.
штат `[hd × hd]` на душу населения. В отличие от MLA, где внимание максимально ориентировано на оценку (Q·K), KDA
«оценка» — это переход в пространство состояний: `s_new = alpha * s_old + kn ⊗ vt`.

**Реализация CPU (заменено):** Развертка состояния каждой головки (строки ~817–864 из `kda_forward()`),
запускает 96 параллельных головок в состоянии `[hd × hd]`. Для hd=128 это 96 × 128² = 1,57M операций умножения и сложения.
за токен. При 69 слоях KDA × 1 токен/декодирование это примерно 108 млн операций только при проверке состояния.

**Конструкция металлического ядра (РЕАЛИЗОВАНА):**
Повторение состояния `s[h][hd][hd]` последовательно для всех токенов, но полностью параллельно для голов и
государственные размеры. Ядро распределяет `[H, hd]` групп потоков — по одной группе потоков на голову, `hd` потоков.
на группу потоков. Каждый поток обрабатывает один элемент `(i, j)` вывода `[hd × hd]`.

Подпись ядра (`k3_kda_state` в строке SHADER `backend_metal.mm`):
```
kernel void k3_kda_state(
    device float4 *S,          // 0: [H*hd*hd], float4-strided state (mutable)
    device const float4 *qn,  // 1: [H*hd], float4-strided normalized Q
    device const float4 *kn,  // 2: [H*hd], float4-strided normalized K
    device const float4 *vh,  // 3: [H*hd], float4-strided gated V (vh - kS) * beta
    device const float4 *alpha, // 4: [H*hd], float4-strided decay factors
    device const float *beta, // 5: [H], per-head gate
    constant const int2 &dims // 6: {H, hd}
)
```

**Математическая декомпозиция (два прохода, без памяти группы потоков):**
Повторение состояния имеет присущие зависимости: проход 2 (расширение + накопление вывода) не может начаться до тех пор, пока
Проход 1 завершает полный набор затухания строк и накопления kS. Ядро сериализует два прохода внутри
каждая нить:

- **Проход 1** (затухание строки + накопление kS): каждый поток `(i,j)` затухает `S[i][j] *= alpha[i]`, затем
  накапливается `kS[i] += kn[j] * S[j][i]` при очистке всех строк столбца `i`.
- **вычисление vt**: `vt[i] = (vh[i] - kS[i]) * beta`.
- **Проход 2** (расширение состояния + объединение вывода): каждый поток `(i,j)` расширяет состояние.
  `S[i][j] += kn[i] * vt[j]`, затем накапливает выход `oh[j] += qn[i] * S[i][j]`.

Никакой памяти или барьеров для группы потоков не требуется — каждый проход использует последовательный цикл внутри потока.
по зависимой оси, тогда как независимые оси распараллеливаются по группам потоков.

**Новая инфраструктура в `backend_metal.h`:**
| Дополнение | Цель |
|---|---|
| `int coli_metal_kda_state(float *S, const float *meta_qn, const float *meta_kn, const float *meta_vh, const float *meta_alpha, const float *meta_beta, int H, int hd)` | Отправка ядра повторения состояния Metal для одного фрагмента токенов C=1 |

| `P("k3_kda_state")` в `coli_metal_init()` | Конвейерная компиляция |

### 8.3 — Нормализация Conv1d + SiLU + L2 ✅ ГОТОВО

Фаза подготовки каждого токена между прогнозами и проверкой состояния:
(a) conv1d по глубине + шлюз SiLU на q/k/v, (b) нормализация L2 для каждой головы q и k.

**Реализация CPU (заменено):** `#pragma omp parallel for` по P затемняется на конв, затем на голову циклов L2.
Операции для каждого токена небольшие (P=2048, H=96, hd=128), но выполняются каждый токен.

**Конструкция металлического ядра (РЕАЛИЗОВАНА):**

**`kda_conv_silu`** — Одна резьба на размер `d` в `[0, P)`. Для каждого измерения:
окно сдвига `conv_win[d*K: d*K+K]` влево на 1, сохранить `vec[d]` в `K-1` (добавляет новый ввод),
вычислите скалярное произведение с `taps[d*K:d*K+K]`, примените SiLU (`x / (1 + exp(-x))`), запишите результат в `vec[d]`.
Отправляется один раз за проекцию (всего q, k, v → 3 отправки).

**`kda_l2_norm`** — Одна резьба на головку `h` в `[0, H)`. Для каждой головы:
просуммируйте `qh[i]^2` и `kh[i]^2` по `hd` тусклым, вычислите обратный квадратный корень `1/sqrt(sum + eps)`
(`eps = 1e-6`), масштабируйте Q на `norm * qscale` (`qscale = 1/sqrt(hd)`) и K на `norm`.
Записывает q/k на месте. Единая рассылка для всех руководителей.

**Новая инфраструктура в `backend_metal.h`:**
| Дополнение | Цель |
|---|---|
| `int coli_metal_kda_conv_silu(float *conv_win, float *vec, const float *taps, int P, int K)` | Окно смены, точечные краны, ворота SiLU — одна проекция |
| `int coli_metal_kda_l2_norm(float *q, float *k, int H, int hd, float qscale)` | Нормализация L2 на месте для каждой головы для q и k |

**Новая инфраструктура в `backend_metal.mm`:**
| Дополнение | Цель |
|---|---|
| `kda_conv_silu` в строке SHADER | Металлическое ядро: conv1d по глубине + SiLU для затемнения `[P]` |
| `kda_l2_norm` в строке SHADER | Металлическое ядро: норма L2 для `[H]` головок Q и ​​K |
| `g_kda_conv_silu`, `g_kda_l2_norm` | Глобальные параметры состояния конвейера |
| `P("kda_conv_silu")`, `P("kda_l2_norm")` в `coli_metal_init()` | Конвейерная компиляция |
| `coli_metal_kda_conv_silu()` | Диспетчеризация хоста: связывает 3 буфера + 2 скалярных параметра, threads=P |
| `coli_metal_kda_l2_norm()` | Диспетчеризация хоста: связывает 2 буфера + 3 скалярных параметра, threads=H |

**Изменения в `kda_forward()` (kimi_k3.c):**
- Когда установлено `g_k3_metal` (внутри цикла для каждого токена):
  - Вызов `coli_metal_kda_conv_silu()` в цикле из 3 (проекции q, k, v), заменяя цикл конвирования OMP.

<a id="fmt0-scales-null-crash-in-coli_metal_matmul"></a>
### fmt=0 масштабирует NULL-сбой в `coli_metal_matmul()`

**Симптом:** Вывод металла произошел сбой с помощью SIGSEGV (выход 139) по адресу `newBufferWithBytes` внутри `wrap()` во время 5-го вызова matmul для каждого слоя (активация tanh, `fmt=0`). Все 4 квантованные проекции (fmt=4) прошли успешно; каждый слой зависал при вызове tanh.

**Основная причина:** `fmt_scale_bytes(fmt=0, I=7168, O=128, gs)` вернул `O * sizeof(float) = 512` байт (отличных от нуля), что привело к появлению `wrap(scales=NULL, 512)` внутри пути создания тензора. В сегменте `newBufferWithBytes:NULL length:512` Metal произошел сбой, когда графический процессор попытался прочитать данные с адреса 0.

Вызывающий объект (`w_matmul()` в `kimi_k3.c:317`) правильно передает `scales=NULL` для fmt=0 (необработанный f32 не имеет шкалы). Ошибка заключалась в том, что `fmt_scale_bytes()` возвращал ненулевое значение для fmt=0, из-за чего сторона Металла предполагала, что шкалы существуют, хотя на самом деле это не так.

**Исправление:** `fmt_scale_bytes()` теперь возвращает `0` для `fmt==0`. Также добавлена ​​явная обработка: `fmt==1` возвращает масштабы по строкам (`O * sizeof(float)`), `fmt==4` возвращает сгруппированные масштабы (`O * ceil(I/gs) * sizeof(float)`), `fmt==6` возвращает 2-байтовые групповые масштабы (`O * ceil(I/gs) * 2`).

**Файлы изменены:**
- `c/backend_metal.mm:588` — `fmt_scale_bytes()` логика
- `c/kimi_k3.c:317` — сохранено `scales=NULL` для fmt=0 (уже было правильно)

**Подход отладки:** Многоуровневая трассировка dprintf на каждом этапе внутри `coli_metal_matmul()` выявила сбой на `[MT3]` (после переноса веса, перед переносом масштаба). Схема (4 вызова fmt=4 успешны, 1 вызов fmt=0 завершается сбоем) была идентична на всех 93 уровнях.

<a id="memory-management-fix-f_free-on-late-initialized-buffers"></a>
### Исправление управления памятью: f_free в буферах с поздней инициализацией.

**Симптом:** `f_free(uq, 256*14336)` вызывается в буфере, выделенном стеком в пути предварительного вычисления ядра объединенного токена, повреждая указатели `w_actual` и `w2_actual` для последующих вызовов.

**Основная причина:** Буферы с выравниванием по страницам, выделенные после `k3_matmul_f32` для `w_actual`/`w2_actual`, были преждевременно освобождены `_XLATE Case 8` в `w_addrow`, что сделало недействительными указатели, все еще используемые объединенным ядром.

**Исправление:** Только `f_free()`, когда буфер действительно был выделен в куче (флаг отслеживаемого выделения). Стековые/встроенные буферы пропускают `f_free`, чтобы избежать аннулирования указателя.

<a id="k3_x00-gpu-fallback-mode"></a>
### K3_X0=0 Резервный режим графического процессора

**Назначение:** При `K3_X0=0` графический процессор используется для объединенного ядра KDA (conv_silu, l2_norm, повторение состояния), но `w_matmul` возвращается к процессору matmul. Это обеспечивает контролируемый путь для изоляции корректности объединенного ядра от корректности проекции.

**Реализация:** `coli_metal_kda_fused_token()` обычно отправляет под `g_k3_metal`, а `w_matmul()` проверяет `g_k3_metal && coli_metal_available()` и переходит к CPU, когда `K3_X0=0` сбрасывает флаг отправки графического процессора.

**Производительность:** `K3_X0=0` режим подтвержден исправлением f_free — работает все 93 слоя с объединенным ядром GPU + проекциями CPU без повреждения указателя.

<a id="recommended-pr-structure"></a>
## Рекомендуемая структура PR

Этот проект хорошо подходит для многих небольших, проверяемых PR. Простой агент кодирования успешно выполняет следующие действия:

1. Анализ пробелов и документация
2. Внутренняя структура диспетчеризации (без изменений в выводах)
3. Металлические реализации плотных примитивов
4. Выполнение эксперта МЭ по металлу
5. Поддержка металлического КВ-кеша
6. Металлическое внимание KDA
7. Полная проверка уровня
8. Комплексный вывод Kimi K3 о металле
9. Оптимизация производительности и сравнительный анализ

<a id="guiding-principle"></a>
## Руководящий принцип

**Никогда не изобретайте новые алгоритмы.** Считайте реализацию CPU оракулом правильности, реализацию Vulkan — эталоном графического процессора, а существующую серверную часть Metal — шаблоном реализации. Каждый PR должен либо добавлять один примитив Metal, либо один тест, и каждый новый примитив должен пройти числовую четность CPU-Vulkan-Metal, прежде чем двигаться дальше.

Этот подход сводит к минимуму архитектуру, которую агент должен понимать в любой момент времени, и обеспечивает возможность независимой проверки каждого шага, что делает его хорошо подходящим для относительно простого автономного агента кодирования, работающего с большой базой кода C.
