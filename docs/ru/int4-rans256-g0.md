# `int4-rans256-g0` — уровень контейнера с энтропийным кодированием без потерь для экспертов int4 для каждой строки

Статус: спецификация формата + оффлайн инструменты, ПР 1 из 3-ПР лестницы. Этот пиар
добавляет кодек (`c/rans.h`), инструменты переупаковки/проверки
(`c/tools/repack_rans.py`, `c/tools/rans_verify.py`) и этот документ —
**пути кода ядра не меняются**. PR 2 (загрузчик + декодирование CPU при экспертной нагрузке)
и PR 3 (пакетное декодирование металла) основан на нем. Идентичность формата заключается в
строка НАЗВАНИЕ `int4-rans256-g0`; его строка в реестре с тех пор попала в
FORMATS.md с порядковым номером *(нет)* — числовой порядковый номер `fmt` не существует или не существует
заявлено до того, как код движка, использующий формат (PR 2), впервые сливается с
dev (см. «Строка реестра (приземленная)» ниже).

<a id="what-it-is-in-one-paragraph"></a>
## Что это такое, в одном абзаце

`int4-rans256-g0` энтропийно кодирует без потерь упакованные байты веса int4
прогнозы маршрутизированных экспертов (`gate_proj`/`up_proj`/`down_proj`) с
**одна статическая таблица RANS, общая для каждого сегмента**, спланированная как **256 независимых
потоки с циклическим перемежением на тензор** настолько широкие декодеры (линии SIMD,
группы потоков графического процессора) получают объединенный вывод. При полной переписи населения по каждому ряду
int4 GLM-5.2 достигнутое соотношение составляет ~0,76 (≈24% меньше байтов к
хранение и поток), с побайтовой реконструкцией — это кодек, а не
квантователь: декодирование всегда точно воспроизводит исходные упакованные байты.

Разбивка имени: `int4` — исходный алфавит представляет собой 4-битные коды квантования.
(номинально 16, фактически 15 символов: симметричный квантователь никогда не излучает
кодовую точку -8, и таблица обрабатывает это автоматически через ноль.
частота); `rans256` — энтропийное кодирование RANS, 256-стороннее чередование; `g0` —
общая статическая таблица, поколение 0.

<a id="container-shape"></a>
## Форма контейнера

На выходе — **обычные осколки защитных тензоров**. Каждый энтропийно-кодированный весовой тензор
сохраняет свое **исходное, немодифицированное логическое имя** (поэтому любой загрузчик с индексом имени
находит его без специального регистра), сохраняется как dtype `U8`, shape
`[record_len]` — непрозрачный байтовый объект, содержимым которого является запись чанка.
ниже. Коляски в масштабе `.qs` для каждого ряда представляют собой **неизмененный необработанный F32** (они
~0,1% потока байтов при построчной геометрии; кодировать их не стоит
второй путь кодека в v1).

<a id="chunk-record-one-record-one-weight-tensors-bytes"></a>
### Запись чанка (одна запись = один байт тензора веса)

Все целые числа имеют прямой порядок байтов, включая `n_symbols` и
поля `packed_bytes` u64 и каждые `stream_offsets` u32 (то же самое
порядок байтов указывается в поле base64 `slot_to_symbol`). `N` = 256
потоки. Эталонная реализация C читает/записывает их с помощью
доступ в собственном порядке и поэтому отказывается компилировать с прямым порядком байтов.
хост, а не выдавать записи с переставленными байтами.

```
offset 0:  n_symbols     u64   -- nibble count for this tensor
offset 8:  packed_bytes  u64   -- original packed-byte count (= ceil(n_symbols/2)),
                                  stored so a reader can size its output buffer
offset 16: stream_offsets[N+1]  u32 x (N+1)
                                -- offsets[i] = byte offset, relative to the start
                                   of `payload`, where stream i begins;
                                   offsets[N] = total payload length
then:      zero-pad to the next 16-byte boundary (derived, never stored)
payload:   N independent rANS byte streams, concatenated in stream order:
           stream i is payload[offsets[i] : offsets[i+1]]
then:      zero-pad to the next 16-byte boundary (derived, never stored)
```

Два прогона заполнения вычисляются одинаково записывающим и читающим
(`round16()`), никогда не сохраняется — сохраненная длина может не соответствовать
производное значение. Валидаторы отказываются от ненулевых байтов заполнения. Выравнивание
**относительно записи**, а не абсолютно к файлу: безопасные тензоры не выравниваются по 16
тензорные смещения, поэтому потребитель, которому нужен выровненный доступ u32/u64, должен прочитать или
сопоставить байты тензора в выровненное распределение (любой `malloc`/GPU-буфер
распределение соответствует критериям; анализатор ссылок отклоняет буфер, который не находится по адресу
выровнено не менее 4 байтов, а не выполнять невыровненный доступ).

Правила достоверности, которым удовлетворяет каждая соответствующая запись (и соблюдают валидаторы):

- `packed_bytes == ceil(n_symbols / 2)`, вычисляется в форме без переноса
  (`n/2 + (n & 1)`), поэтому `n_symbols = 2^64 - 1` не может подделать совпадение;
- `stream_offsets[0] == 0`, смещения не уменьшаются, и **каждый поток находится нане менее 4 байт** — даже поток, кодирующий нулевые символы, несет свою
  4 сброшенных байта состояния;
- общая длина записи точно равна полученному кадру (без замыкающих
  байты), и каждый производный байт заполнения равен нулю. Эта длина и есть
  **физический размер**, известный из сохраненного кадра перед декодированием, а не
  вывод об идентичности, который запрещает раздел штампов (`expected_bytes(O, I)`);
- **ограничение усиления**: ни одна допустимая таблица не может кодировать более
  `payload_len * 8 * M_max` символов в полезную нагрузку (`M_max = 2^15`,
  наибольший размер таблицы формата — стоимость символа ограничена снизу
  `log2(M / (M-1))` бит). Заголовок, в котором указано больше `n_symbols`, чем есть
  декомпрессионная бомба, от которой необходимо отказаться *прежде* любых размеров буферов
  от этого.

<a id="interleaving"></a>
### Чередование

Полубайты распаковываются в порядке очереди (`nib[2k] = byte[k] & 0xF`,
`nib[2k+1] = byte[k] >> 4`). Полубайт по логическому индексу `j` принадлежит потоку.
`j % N` и является `(j / N)`-м символом этого потока. Каждый поток — это
обычный автономный поток RANS с одним состоянием через один и тот же общий
таблица — без поперечной связи. Циклическое (не блочное) назначение – это
свойство, которое делает вывод широкого декодирования объединенным: полоса `l` группы на основе
в потоке `b` выдает логическую позицию `r*N + b + l` в раунде `r`, поэтому
Группа G-полос записывает G последовательных полубайтов = G/2 целых упакованных байтов.

<a id="per-stream-codec"></a>
### Кодек для каждого потока

конструкция в стиле ryg_rans (общедоступная ссылка Фабиана Гизена)
дизайн): 32-битное состояние, перенормировка байтов, `L = 2^23`,
`scale_bits = 14` (`M = 16384`).

- encode пропускает ввод назад, записывает байты назад, сбрасывает
  окончательное 4-байтовое состояние. По символу `s` (это полный рецепт
  бит-идентичные сторонние **писатели** потребности): с состоянием
  `x` (инициализируется как `L`), сначала перенормируем, выдавая младшие байты —
  `x_max = ((L >> scale_bits) << 8) * freq[s]`;
  `while (x >= x_max) { emit byte x & 0xFF; x >>= 8; }` — затем обновить
  `x = ((x / freq[s]) << scale_bits) + (x % freq[s]) + start[s]`
  (целое деление). После последнего (т. е. первого в потоке) символа
  выдает оставшееся 32-битное состояние в виде 4 байтов, последний младший байт. Испускаемый
  Последовательность байтов, перевернутая в прямой порядок, представляет собой поток. В худшем случае
  Символ `freq = 1` излучает `scale_bits` бит, поэтому поток символов `n`
  никогда не превышает `ceil(n * scale_bits / 8) + 4` байт;
- декодирование читает вперед:
  `x = 4 bytes big-endian`, затем по символу:
  `slot = x & (M-1)`; `s = slot_to_symbol[slot]`;
  `x = freq[s]*(x >> scale_bits) + slot - start[s]`;
  `while (x < L) { if bytes remain: x = (x<<8)|next byte; else break; }`.
- `else break` является несущей: конечные символы потока правильно декодируются.
  с `x < L`; декодер, который читает за концом потока, выдает неверные результаты
  символы хвоста.
- Поддающиеся проверке инварианты любого подлинного вывода кодера (их используют валидаторы).
  для отказа от коррупции **без байтов истинности**): начальные 4 байта
  состояние находится в `[L, 256L)`; декодирование потребляет поток точно; финал
  состояние ровно `L`.

<a id="shared-table-in-shard-metadata"></a>
### Общая таблица в метаданных сегмента

Таблица поставляется **один раз за осколок** в
`__metadata__["colibri.int4-rans256-g0.table"]`, строка JSON:

```json
{
  "table_id": "g0",
  "n_streams": 256,
  "scale_bits": 14,
  "M": 16384,
  "freq": [16 uint32, summing to M],
  "start": [16 uint32, the exclusive prefix sum of freq],
  "slot_to_symbol_b64": "<base64 of M x uint16, little-endian>",
  "table_crc32": "<hex crc32 of the raw slot_to_symbol bytes>"
}
```

Декодирование всегда локально для сегмента: каждая запись в сегменте декодируется с учетом этого
встроенная копия шарда, без зависимости между шардами или внешними файлами. А
многооскольчатый автор должен проштамповать идентичную по байтам таблицу в каждый ее шард
выдает (инструмент перепаковки строит таблицу один раз из объединенной гистограммы
каждый выбранный тензор и повторно использует одну и ту же строку JSON). `table_crc32`
позволяет инструменту подтвердить, что два сегмента использовали одну и ту же таблицу без различий
большой двоичный объект base64. `table_id` — метаданные происхождения (перенастроенная таблица будущего
будет отправлен как `g1`); читатели никогда не решают эту проблему извне.## ПЕЧАТЬ ОБЯЗАТЕЛЬНА (отличие несущей способности от fmt=8)

`__metadata__["colibri.fmt"]` отображает каждый энтропийно-кодированный тензор **веса**
имя (никогда `.qs`) в строку `int4-rans256-g0`, закодированную в формате JSON с помощью
отсортированные ключи.

Для существующих форматов движок может определить идентичность на основе байтовой арифметики.
(`weight bytes == formula(O, I)`), а штамп — это максимум перекрестная проверка.
**Этот вывод здесь структурно невозможен**: энтропийно-кодированный размер равен
зависит от данных — нет `expected_bytes(O, I)` для сравнения.
Таким образом, штамп является **единственным** сигналом о том, что тензор `U8` энтропийно закодирован.
вообще. Зависимость от данных применяется к **выведению идентичности**, а не к **степени**:
физическая длина записи полностью определяется сохраненным кадром перед
декодирование (заголовок, смещения потока, полезная нагрузка, две площадки `round16()`; см.
правил достоверности выше: «общая длина записи равна производному кадрированию
точно"), поэтому ввод-вывод с выравниванием по страницам (экстенты, дополненные 4 КиБ, `O_DIRECT`) остается
доступен. Штамп по-прежнему является обязательным, поскольку главное — это идентичность, а не размер.
нельзя сделать вывод. Последствия, которые должен учитывать любой потребитель:

- *нештампованный* тензор `U8` ни в коем случае не должен считаться энтропийно-кодированным.
  эвристика размера;
- будущий путь чтения движка нуждается в отправке с контролем штампа **перед**
  вывод байт-арифметического формата: проштамповано `int4-rans256-g0` → декодирование rans
  путь; все остальное → сегодняшний вывод, совершенно не изменившийся. Получение
  этот неправильный порядок приведет к ошибочному восприятию сжатого объекта как формата с фиксированным соотношением сторон.
  и всякую гирю испортить без ошибки;
- валидаторы отказываются от шарда, штампы и таблица которого отсутствуют и
  когерентный (`tools/rans_verify.py` — валидатор ссылок с именованным
  отказ по классу коррупции).

## Область применения (v1)

Только экспертные контейнеры int4 для каждой строки ("gs=0"). Для каждой группы (класс g64)
контейнеры выходят за рамки: их лучше нормализованные коды измеряют гораздо
более слабое соотношение (~ 0,89 против ~ 0,76), а их масштабные массивы на два порядка больше
доля потока — для того, чтобы раунд G64 стоил того, потребуется масштабное кодирование
делать, что является его собственным замыслом. Инструмент репаковки *отказывает* (по имени)
тензор, соотношение весовых байтов и строк масштаба которого является сигнатурой g64, а не
молча кодируя его под идентификатором этого формата.

<a id="reference-implementation-map"></a>
## Проверка всего артефакта

Проверка каждой записи (кадрирование, инварианты потока, вывод перекодирования) доказывает
запись является *правильным* артефактом этого формата — она не может доказать, что это так.
*запись, произведенная данным тиражом: правильно сформированная запись, замененная
с другой контрольной точки проходит все указанные выше проверки. Для этого писатель
`repack-manifest.json` (маркер завершения, пишется последним, детерминированный)
содержит в каждом фрагменте весь файл `sha256` (полные `.safetensors` байты,
хэшируется во время потоковой записи — он включает в себя побочные программы `.qs`,
заголовок и заполнение, ни одно из которых не видно в дайджестах для каждой записи) плюс
`records` map — исходное имя тензора → sha256 выпущенных байтов записи
именно так, как написано — для детальной диагностики. `rans_verify.py` проверяет
сначала хэш файла, затем каждая запись в его дайджесте, всякий раз, когда
манифест находится рядом с шардами (именные отказы:
`E_SHARD_DIGEST_MISMATCH`, `E_DIGEST_MISMATCH`, `E_DIGEST_MISSING`,
`E_MANIFEST_MALFORMED`); манифест без дайджестов или отсутствие манифеста означает
никакая проверка невозможна (примечание, никогда не ошибка), и
`repack_rans.py --manifest-only <dir>` ретро-генерирует дайджесты для
уже созданные каталоги путем хеширования осколков на месте. Это **сборка
целостность** — именно эти байты были получены в результате этого запуска; контейнер
*собственная личность* остается указанной выше родословной штампа/реестра, а
Проверка нагрузки со стороны движка поставляется с комплектом поставки потребителя. Формат провода записи
не затронут всем этим: манифест представляет собой дополнительный файл.
